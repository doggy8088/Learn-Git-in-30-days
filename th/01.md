# วันที่ 01: ทำความเข้าใจการควบคุมเวอร์ชันด้วย Git

ผมใช้ Subversion (SVN) มาเกือบ 10 ปี และไม่เคยรู้สึกว่าจำเป็นต้องเปลี่ยนไปใช้แพลตฟอร์มควบคุมเวอร์ชันอื่นเลย จนกระทั่งเมื่อไม่กี่ปีก่อน ผมค่อย ๆ เริ่มนำการควบคุมเวอร์ชันของ TFS (TFS Service) มาใช้เพื่อตอบรับการเปลี่ยนแปลงสู่ยุคคลาวด์ การเปลี่ยนผ่านเป็นไปอย่างราบรื่น เพราะ SVN และ TFS มีแนวคิดการควบคุมเวอร์ชันที่คล้ายกัน ทั้งคู่เป็นระบบควบคุมเวอร์ชันแบบรวมศูนย์ (Centralized) ระบบควบคุมเวอร์ชันแบบรวมศูนย์เหล่านี้ใช้งานง่าย เข้าใจได้โดยสัญชาตญาณ และจัดการสิทธิ์ได้ง่าย พูดกันตรง ๆ ในสถานการณ์การพัฒนาส่วนใหญ่ Subversion หรือ TFS ก็เพียงพอแล้ว แล้วโอกาสหรือความต้องการอะไรที่บังคับให้เราต้องเปลี่ยนมาใช้การควบคุมเวอร์ชันด้วย Git? ผมเชื่อว่าแต่ละคนมีเหตุผลในการหันมาใช้ Git เป็นของตัวเอง บางคนเห็นว่าสนุก บางคนเห็นว่าแปลกใหม่ และบางคนเห็นว่าทรงพลัง ไม่ว่าจะด้วยเหตุผลใด ตราบใดที่เหตุผลนั้นสนับสนุนให้คุณเรียนรู้เทคโนโลยีที่ไม่คุ้นเคยอย่างกระตือรือร้น ก็ถือเป็นเรื่องดี บทความนี้ไม่เพียงจะแนะนำกลไกการควบคุมเวอร์ชันของ Git ให้คุณรู้จัก แต่ยังจะแบ่งปันเหตุผลที่ผมอยากเปลี่ยนมาใช้ Git อีกด้วย

## วัตถุประสงค์ของบทความ

ในแวดวงการพัฒนาซอฟต์แวร์ การควบคุมเวอร์ชันของซอร์สโค้ดเป็นเรื่องที่สำคัญมาก ต่างจากระบบควบคุมเวอร์ชันแบบรวมศูนย์อย่าง Subversion หรือ TFVC (Team Foundation Version Control) ตรงที่ Git เป็นระบบควบคุมเวอร์ชันแบบกระจายศูนย์ (DVCS; Distributed Version Control System) ซึ่งนำข้อดีมากมายมาสู่การควบคุมเวอร์ชัน และแก้ไขข้อด้อยของการควบคุมเวอร์ชันแบบรวมศูนย์ดั้งเดิม เช่น รองรับการทำงานแบบโลคัล สำรองข้อมูลได้ง่าย การแยก Branch และการ Merge ที่ทรงพลังและยืดหยุ่น และอื่น ๆ อีกมากมาย อย่างไรก็ตาม เนื่องจากการควบคุมเวอร์ชันด้วย Git แตกต่างจากเครื่องมือควบคุมเวอร์ชันแบบรวมศูนย์ดั้งเดิมอย่างมาก ทั้งในแง่แนวคิดการควบคุมเวอร์ชันและวิธีการใช้เครื่องมือ จึงทำให้มีช่วงการเรียนรู้ที่ค่อนข้างชัน

แม้หัวข้อของบทความชุดนี้คือ "เชี่ยวชาญ Git ใน 30 วัน" แต่พูดกันตรง ๆ นี่อาจเป็นการกล่าวเกินจริงไปบ้าง เพราะ Git นั้นกว้างใหญ่และลึกซึ้ง มีรายละเอียดให้สำรวจอีกมากมาย หากคุณต้องการนำไปใช้ในการทำงานจริง ๆ จะต้องใช้เวลาเรียนรู้กี่วันจึงจะเชี่ยวชาญอย่างแท้จริง? การเรียนรู้วันละนิดเป็นเวลา 30 วันติดต่อกันดูเหมือนเป็นตัวเลขที่สมเหตุสมผล (หรือมากเกินไป?) หากมีเครื่องมือที่ทุกคนจำเป็นต้องใช้และต้องเชี่ยวชาญในทันที แต่หลังจากเรียนรู้ไป 30 วันแล้วยังใช้ไม่คล่อง แสดงว่าช่วงการเรียนรู้นั้นสูงเกินไป ดังนั้น ผมคิดว่าจุดเน้นหลักของบทความชุดนี้คือ "วิธีเรียนรู้การควบคุมเวอร์ชันด้วย Git ภายใน 30 วัน และต้องสามารถนำไปใช้อย่างชำนาญในงานพัฒนาจริงได้" นี่คือวัตถุประสงค์ที่แท้จริงของบทความชุดนี้ ผมจะไม่เน้นรายละเอียดที่น่าเบื่อเหล่านั้นเป็นพิเศษ แต่ก็มีแนวคิดและรายละเอียดสำคัญบางอย่างที่พลาดไม่ได้เสมอ ผมจะพยายามกล่าวถึงบางส่วนในแต่ละหัวข้อ และเจาะลึกเมื่อมีโอกาส ผมหวังว่าทุกคนจะได้เรียนรู้ไปพร้อมกับการลงมือทำ และสัมผัสเสน่ห์อันทรงพลังของการควบคุมเวอร์ชันด้วย Git อย่างลึกซึ้ง

## โอกาสในการเปลี่ยนผ่าน

ในช่วงไม่กี่เดือนที่ผ่านมา บริษัทของเรามีโปรเจกต์ขนาดใหญ่ที่มีนักพัฒนามากกว่า 12 คนเข้าร่วม ในที่สุดทุกคนตัดสินใจนำ Git มาใช้เป็นกลไกการควบคุมเวอร์ชันสำหรับโปรเจกต์นี้ แทนที่จะบอกว่าเรานำการควบคุมเวอร์ชันด้วย Git มาใช้ เหตุผลที่แท้จริงของการนำมาใช้คือ "เราเลือกใช้ GitHub เป็นแพลตฟอร์มควบคุมเวอร์ชันของเรา" เพราะแพลตฟอร์ม GitHub ผสานการทำงานไว้ด้วยกันได้ดีมาก มีการรองรับการควบคุมเวอร์ชันด้วย Git อย่างครบถ้วน การติดตามและจัดการ Issue การจัดการเอกสาร Wiki ออนไลน์ และอินเทอร์เฟซสำหรับรีวิวซอร์สโค้ดที่ใช้งานง่าย คุณสมบัติเหล่านี้ช่วยลดปัญหาการสื่อสารในทีมระหว่างการพัฒนาแบบร่วมมือกันหลายคนได้อย่างมีประสิทธิภาพ

การเริ่มต้นใช้ Git นั้นค่อนข้างยาก เพราะแนวคิดการควบคุมเวอร์ชันของ Git แตกต่างจาก Subversion มาก จนยากที่จะเข้าใจความแตกต่างได้โดยสัญชาตญาณ แม้จะมีเครื่องมืออินเทอร์เฟซกราฟิกแบบ GUI ให้ใช้ คุณก็อาจไม่รู้วิธีใช้มันอยู่ดี คุณก็รู้ว่าเมื่อมีเครื่องมือที่ทรงพลังและมีประโยชน์อยู่ในมือ "การใช้มันอย่างไม่ถูกต้อง" นั้นน่ากลัวกว่า "การไม่รู้วิธีใช้มัน" เสียอีก! พูดง่าย ๆ คือ คุณต้องสร้างกรอบความคิด (Mindset) ให้ได้ก่อน ทำความเข้าใจหลักการทำงานของ Git แล้วจึงเริ่มใช้เครื่องมือที่เกี่ยวข้องกับ Git (ไม่ว่าจะเป็นเครื่องมือแบบ Command Line หรือเครื่องมืออินเทอร์เฟซกราฟิก) นี่แหละคือวิธีที่ถูกต้อง!

## วิธีการเรียนรู้

ตอนที่ผมเริ่มเรียนรู้ Git ครั้งแรก ผมอ่านหนังสือหลายเล่ม (จริง ๆ คือเลือกอ่านเฉพาะประเด็นสำคัญ) อ่านบทความและงานนำเสนอออนไลน์มากมาย และยังดูวิดีโอสอนอีกหลายคลิป การดูและเรียนรู้ไปพร้อมกันทำให้ผมเรียนรู้วิธีใช้เครื่องมือ Git ได้จริง และไม่ได้รู้สึกว่ามันยากเกินไปนัก อย่างไรก็ตาม Git มีคำสั่งและพารามิเตอร์มากมาย เกินขอบเขตที่สมองจะจดจำได้ทั้งหมด เว้นแต่คุณจะใช้มันทุกวัน ไม่อย่างนั้นจะเป็นไปได้อย่างไรที่จะพิมพ์คำสั่งควบคุมเวอร์ชันทั้งวัน? หากทุกครั้งที่ต้องการใช้คำสั่ง Git ต้องเปิดหนังสือดู นั่นก็ไม่มีประสิทธิภาพเอาเสียเลย ในตอนนั้น ผมคิดโดยสัญชาตญาณว่าการเรียนรู้ Git สุดท้ายควรกลับไปสู่เครื่องมือ GUI ที่มีประโยชน์ ไม่เช่นนั้นสิ่งนี้อาจไม่ง่ายที่จะผลักดันให้ใช้กันในทีม

ยิ่งไปกว่านั้น เนื่องจาก Git เป็นกลไก "การควบคุมเวอร์ชันแบบกระจายศูนย์" เมื่อจำนวนนักพัฒนาเริ่มเพิ่มขึ้น และแต่ละคนเริ่มมีสำเนา Repository เป็นของตัวเอง ทุกคนจะลำบากในช่วงแรกของกระบวนการแยก Branch และ Merge กันหลายคน และเป็นเช่นนั้นอยู่พักใหญ่ แม้จะมีการแบ่งปันทางเทคนิคภายในบริษัท แต่เนื่องจากทุกคนเรียนรู้เป็นครั้งแรก แนวคิดนามธรรมเหล่านั้นของ Git จึงไม่สามารถหยั่งรากลึกในใจผู้คนได้ พวกเขาทำได้เพียงแบ่งปันตามวิธีการใช้งาน Git เช่น วิธีใช้เครื่องมือ คำสั่งที่ใช้บ่อยคืออะไร ควรใช้คำสั่งอะไรในสถานการณ์พิเศษ เป็นต้น แม้จะมีการอธิบายหลักการที่ซับซ้อนในระหว่างกระบวนการ แต่เนื่องจากความเข้าใจ Git ของทุกคนยังคลุมเครือ ความเข้าใจของแต่ละคนเกี่ยวกับวิธีการควบคุมเวอร์ชันด้วย Git จึงไม่เหมือนกัน และความรู้กับแนวคิดที่ซึมซับได้ก็ไม่จำเป็นต้องสอดคล้องกัน ดังนั้นแม้หลังจบคอร์ส ทุกคนยังต้องใช้เวลาอีกหลายวันในการปรับตัวอย่างต่อเนื่อง พูดคุยกัน และแก้ปัญหาร่วมกัน หากคุณเป็นคนเดียวที่ใช้ Git คุณจะรู้สึกถึงประโยชน์ที่ Git มอบให้ได้ยากจริง ๆ และอาจไม่สามารถทำต่อไปได้

ดังนั้น ผมคิดว่าการจะเรียนรู้การควบคุมเวอร์ชันด้วย Git ให้ดี อาจเรียนรู้ได้ง่ายขึ้นหากคุณรู้ประเด็นต่อไปนี้ก่อน:

* ประการแรก ต้องมีแนวคิดพื้นฐานของ Git การเรียนรู้ผ่านคำสั่งเป็นวิธีที่เร็วที่สุด อย่าข้ามส่วนนี้ไป
* หาคนมาเรียนรู้การควบคุมเวอร์ชันด้วย Git ไปพร้อมกับคุณให้มากขึ้น โดยควรใช้มันในงานพัฒนาจริงโดยตรง
* ควรมีหน่วยล่วงหน้า (Advance Troops) สักสองสามคนในทีมที่สามารถเรียนรู้แนวคิด Git ได้มากกว่าคนอื่น เพื่อแบ่งปันกับผู้อื่นหรือให้ความช่วยเหลือได้ทันท่วงทีเมื่อมีใครติดขัด
* เข้าใจว่า Git คือ "การควบคุมเวอร์ชันแบบกระจายศูนย์" และทุกคนมี Repository ที่สมบูรณ์ ดังนั้นคุณต้อง Merge ไฟล์บ่อย ๆ
* เมื่อใช้ Git การแยก Branch และ Merge เป็นเรื่องปกติ แต่เมื่อใดก็ตามที่มีการ Merge ก็จะมี Conflict เกิดขึ้น จงเรียนรู้วิธีแก้ไข Conflict

## ทำความเข้าใจการควบคุมเวอร์ชันด้วย Git

Git ถือกำเนิดจาก Linus Torvalds บิดาแห่ง Linux ในขณะที่เขากำลังพัฒนา Linux Kernel เนื่องจากวิธีการควบคุมเวอร์ชันในยุคแรกไม่มีประสิทธิภาพและเป็นแบบรวมศูนย์ จึงเกิดปัญหามากมายเมื่อต้องจัดการการควบคุมเวอร์ชันสำหรับโปรเจกต์ที่ซับซ้อนและมีขนาดใหญ่อย่าง Linux Kernel ในช่วงแรก Linux Kernel ใช้ BitKeeper ในการควบคุมเวอร์ชัน แต่ต่อมา Linus Torvalds ได้ออกแบบระบบควบคุมเวอร์ชัน Git ที่ดีกว่าขึ้นจากประสบการณ์ของเขากับ BitKeeper และ Monotone เดิมที Git ถูกออกแบบมาให้เป็นเพียงเครื่องมือควบคุมเวอร์ชันระดับต่ำ เพื่อใช้เป็นเครื่องมือปฏิบัติการสำหรับระบบควบคุมเวอร์ชันอื่น ๆ (SCM) และต่อมาก็ค่อย ๆ พัฒนากลายเป็นระบบควบคุมเวอร์ชันที่สมบูรณ์

ที่น่าสนใจคือ เมื่อ Linus Torvalds เปลี่ยนมาใช้ Git ในการควบคุมเวอร์ชันครั้งแรก Git นั้นซับซ้อนเกินไป และแนวคิดการควบคุมเวอร์ชันหลายอย่างแตกต่างจากเดิมมากเกินไป ซึ่งก็พบกับแรงต่อต้านจากชุมชนโอเพนซอร์สทั่วโลกเช่นกัน อย่างไรก็ตาม หลังจากความพยายามและการพัฒนาหลายปี เครื่องมือสำหรับใช้งาน Git ก็มีความสมบูรณ์มากขึ้นเรื่อย ๆ จนค่อย ๆ ทำให้แรงต่อต้านสงบลง จากการวิจัยตลาดในปี 2013 พบว่า 30% ของโปรเจกต์โอเพนซอร์สทั่วโลกเปลี่ยนมาใช้ Git ในการควบคุมเวอร์ชัน นี่เป็นส่วนแบ่งตลาดที่น่าทึ่ง หมายความว่า Git มีคุณสมบัติที่น่าตื่นตาตื่นใจอย่างแน่นอน และคุ้มค่าที่จะศึกษาให้ดี!

เมื่อพูดถึงสถาปัตยกรรมของ Git มันสร้างขึ้นบนประสบการณ์ของ Linus Torvalds ในการดูแลโปรเจกต์ขนาดใหญ่อย่าง Linux Kernel และประสบการณ์อันล้นเหลือของเขาในการปรับแต่งระบบไฟล์ (File System) ให้เหมาะสมอย่างสมบูรณ์ ด้วยเหตุนี้ Git จึงมีการออกแบบที่สำคัญดังต่อไปนี้:

* รองรับโมเดลการพัฒนาแบบไม่เป็นเชิงเส้น (Non-linear) อย่างแข็งแกร่ง (โมเดลการพัฒนาแบบกระจายศูนย์)
  * Git มีกลไกการแยก Branch และ Merge ที่รวดเร็ว รวมถึงเครื่องมือกราฟิกสำหรับแสดงเส้นทางประวัติการเปลี่ยนแปลงของเวอร์ชัน
  * Git ให้ความสำคัญกับการแยก Branch และ Merge เป็นอย่างมาก ดังนั้นในกระบวนการควบคุมเวอร์ชัน คุณจะทำการแยก Branch และ Merge อยู่ตลอดเวลา
  * กลไก Branch ของ Git นั้นเบามาก (Lightweight) ไม่มีภาระ แต่ละ Branch เป็นเพียงพอยน์เตอร์อ้างอิง (Reference Pointer) ไปยัง Commit หนึ่ง ๆ เท่านั้น
* โมเดลการพัฒนาแบบกระจายศูนย์
  * ทุกคนที่เข้าร่วมการพัฒนาด้วย Git จะมีประวัติการพัฒนาที่สมบูรณ์
  * เมื่อนักพัฒนา Clone Git Repository เป็นครั้งแรก มันเทียบเท่ากับ "การสำรองข้อมูลอย่างสมบูรณ์" ของ Git Repository นั้นเลยทีเดียว
  * ไฟล์ที่เปลี่ยนแปลงและบันทึกประวัติทั้งหมดใน Repository ทั้งหมดจะถูกเก็บไว้ใน Local Repository
* เข้ากันได้กับระบบปฏิบัติการที่มีอยู่
  * Git Repository จริง ๆ แล้วเป็นเพียงโฟลเดอร์ที่มีไฟล์กำหนดค่าต่าง ๆ ที่เกี่ยวข้อง และไฟล์ Blob Object ต่าง ๆ
  * Git Repository สามารถเผยแพร่ได้ทุกวิธี ดังนั้นคุณสามารถใช้ HTTP, FTP, rsync, SSH หรือแม้แต่ Git Protocol เป็นสื่อกลางในการเข้าถึง Git Repository ได้ โดยมีความเข้ากันได้สูงมาก
* จัดการโปรเจกต์ขนาดใหญ่ได้อย่างมีประสิทธิภาพ
  * เนื่องจาก Repository ที่สมบูรณ์จะถูก Clone มาที่เครื่องโลคัล และ Repository นั้นประกอบด้วยไฟล์และบันทึกการเปลี่ยนแปลงเวอร์ชันอย่างครบถ้วน ความเร็วในการดำเนินการกับไฟล์ต่าง ๆ ในการควบคุมเวอร์ชันจึงเร็วกว่าการเข้าถึงระยะไกลโดยตรงหลายร้อยเท่า
  * นี่หมายความว่าการควบคุมเวอร์ชันด้วย Git จะไม่ช้าลงเมื่อโปรเจกต์มีขนาดใหญ่ขึ้นและมีไฟล์มากขึ้น
* การปกป้องบันทึกประวัติ
  * ในกระบวนการควบคุมเวอร์ชันด้วย Git แต่ละ Commit จะสร้างหมายเลข Hash ID ขึ้นมา และทุกเวอร์ชันในกระบวนการเปลี่ยนแปลงจะอ้างอิงถึง Hash ID นี้ ตราบใดที่ Hash ID ไม่ตรงกัน Git ก็จะทำงานไม่ได้ ดังนั้นเมื่อโปรเจกต์มีขนาดใหญ่ขึ้นและมีการ Clone สำเนาของ Repository มากขึ้นเรื่อย ๆ คุณแทบจะไม่สามารถดัดแปลงเนื้อหาไฟล์หรือบันทึกเวอร์ชันได้เลย
  * **โปรดจำไว้: ทุกคนมี Repository ที่สมบูรณ์ หากคุณเปลี่ยนแปลงต้นฉบับ Repository ของทุกคนก็จะไม่สามารถ Merge กลับไปยัง Repository ต้นฉบับได้อีก ดังนั้นคุณแทบจะไม่สามารถดัดแปลงบันทึกเวอร์ชันตามอำเภอใจได้เลย**
* การออกแบบเชิงชุดเครื่องมือ (Toolkit-based)
  * Git ถูกออกแบบมาเป็นชุดซอฟต์แวร์เครื่องมือ (เครื่องมือแบบ Command Line) คุณสามารถผสมผสานการใช้เครื่องมือต่าง ๆ เข้าด้วยกันได้อย่างง่ายดายและยืดหยุ่นมาก
* กลยุทธ์การ Merge แบบเสียบปลั๊กได้ (Pluggable)
  * Git มีกลไก "การ Merge แบบไม่สมบูรณ์" ที่ออกแบบมาอย่างดี และอัลกอริทึมหลายแบบที่สามารถทำการ Merge ให้เสร็จสมบูรณ์ได้ และสุดท้ายจะแจ้งให้ผู้ใช้ทราบว่าเหตุใดการ Merge อัตโนมัติจึงไม่สามารถทำได้ หรือแจ้งให้คุณทราบว่าจำเป็นต้อง Merge ด้วยตนเอง
* กลไกการเก็บขยะแบบพาสซีฟ (Passive Garbage Collection)
  * เมื่อใช้ Git หากคุณต้องการขัดจังหวะการดำเนินการปัจจุบันหรือกู้คืนการดำเนินการก่อนหน้า ก็สามารถทำได้ คุณไม่ต้องกังวลว่าอาจใช้คำสั่งผิดหรือคำสั่งค้างกลางคันขณะกำลังดำเนินการ
  * กลไก Garbage Collection ของ Git จริง ๆ แล้วคือไฟล์ที่ไร้ประโยชน์เหล่านั้นที่เหลืออยู่ในระบบไฟล์ กลไก Garbage Collection นี้จะทำงานโดยอัตโนมัติก็ต่อเมื่อ Object ที่ไร้ประโยชน์เหล่านี้สะสมเป็นระยะเวลาหนึ่ง หรือคุณสามารถออกคำสั่งเพื่อล้างมันด้วยตัวเองก็ได้ ตัวอย่างเช่น: git gc --prune
* การแพ็ก Object เป็นระยะ (Regular Packing)
  * "Object" ที่เราพูดถึงใน Git จริง ๆ แล้วหมายถึงไฟล์ใน Repository ในกระบวนการเปลี่ยนแปลงเวอร์ชัน โค้ดหรือไฟล์อื่น ๆ ในโปรเจกต์จะถูกอัปเดต ทุกครั้งที่มีการอัปเดต ตราบใดที่เนื้อหาไฟล์แตกต่างกัน "Object" ใหม่ก็จะถูกสร้างขึ้น และไฟล์ทั้งหมดที่มีเนื้อหาแตกต่างกันเหล่านี้จะถูกเก็บรักษาไว้
  * คุณคงจินตนาการได้ว่าเมื่อโปรเจกต์มีขนาดใหญ่ขึ้นและมีเวอร์ชันมากขึ้น ก็จะมี Object มากขึ้นเรื่อย ๆ แม้ว่าแต่ละไฟล์จะสามารถบีบอัดแยกกันเพื่อให้ไฟล์มีขนาดเล็กลงได้ แต่ไฟล์ที่มากเกินไปก็ยังทำให้การเข้าถึงไฟล์มีประสิทธิภาพน้อยลงเรื่อย ๆ ดังนั้น การออกแบบของ Git จึงมีกลไกที่สามารถแพ็กกลุ่ม Object เก่า ๆ ให้เป็น Packfile โดยอัตโนมัติเพื่อปรับปรุงประสิทธิภาพการเข้าถึงไฟล์
  * ไฟล์ที่เพิ่มเข้ามาใหม่เหล่านั้นจะยังคงอยู่ในรูปของไฟล์เดี่ยว ซึ่งหมายความว่า "ไฟล์" ใน Git Repository คือ Git "Object" แต่จำเป็นต้อง Repack เป็นระยะ ๆ
  * สันนิษฐานได้ว่า Git จะดำเนินการต่าง ๆ เช่น การ Repack โดยอัตโนมัติ แต่คุณยังสามารถออกคำสั่งเพื่อดำเนินการด้วยตัวเองได้ ตัวอย่างเช่น: git gc
  * หากคุณต้องการตรวจสอบว่าระบบไฟล์ที่ Git ดูแลอยู่นั้นสมบูรณ์หรือไม่ คุณสามารถดำเนินการคำสั่งต่อไปนี้: git fsck

เกี่ยวกับระบบควบคุมเวอร์ชันแบบกระจายศูนย์ของ Git ขอย้ำอีกสองสามเรื่อง:

* Git สามารถดำเนินการควบคุมเวอร์ชันได้อย่างสมบูรณ์โดยไม่ต้องมีการสนับสนุนจากฝั่งเซิร์ฟเวอร์ เพราะทุกคนมีสำเนา Repository ที่สมบูรณ์
* เนื่องจากทุกคนมีสำเนา Repository ที่สมบูรณ์ ทุกครั้งที่คุณ Commit การเปลี่ยนแปลงเวอร์ชัน คุณจะ Commit ไปยัง Local Repository เท่านั้น ความเร็วในการ Commit จึงรวดเร็วมาก และคุณไม่จำเป็นต้องเชื่อมต่อเครือข่าย ซึ่งช่วยประหยัดเวลาในการพัฒนาได้อย่างมาก
* เนื่องจากทุกคนมีสำเนา Repository ที่สมบูรณ์ นั่นหมายความว่าเมื่อใช้การควบคุมเวอร์ชันด้วย Git จะไม่มีสิ่งที่เรียกว่า "การควบคุมสิทธิ์ (Permission Control)" สมาชิกทุกคนสามารถ Clone Repository และสามารถ Commit การเปลี่ยนแปลงในเครื่องของตนได้โดยไม่มีข้อจำกัดด้านสิทธิ์ใด ๆ เมื่อใช้ Git สิทธิ์เดียวที่สามารถตั้งค่าได้คือ คุณมีสิทธิ์เข้าถึง Upstream Repository หรือ Remote Repository หรือไม่
* หากคุณต้องการแลกเปลี่ยนเวอร์ชันที่เปลี่ยนแปลงกับผู้อื่น คุณสามารถทำได้ผ่าน "การ Merge" ได้ทุกเมื่อ Git มีความสามารถในการติดตามการ Merge ที่ทรงพลังมาก
* ในการ Merge เวอร์ชันของหลาย ๆ คน คุณเพียงต้องมีสิทธิ์หรือเข้าถึง Shared Repository ได้เท่านั้น
  **ตัวอย่างเช่น: บนเซิร์ฟเวอร์เดียวกัน คุณสามารถแชร์ผ่านสิทธิ์ของโฟลเดอร์ หรือเข้าถึง Git Repository ของเซิร์ฟเวอร์อื่นจากระยะไกลผ่าน SSH หรือแชร์ Git Repository ผ่านเว็บเซิร์ฟเวอร์ เป็นต้น**

## สรุปของวันนี้

บทความของวันนี้เป็นเพียงบทนำโดยทั่วไป หากคุณยังไม่ค่อยเข้าใจปรัชญาการออกแบบของ Git ก็ไม่เป็นไร คุณสามารถกลับมาอ่านบทความนี้อีกครั้งหลังจากใช้งานไปสักพัก และอาจมีความเข้าใจที่ลึกซึ้งยิ่งขึ้น

ผมคิดว่าการเขียนเรื่อง "ทำความเข้าใจการควบคุมเวอร์ชันด้วย Git" นั้นยากกว่าการสอนทุกคนให้รู้วิธีใช้มันมาก ด้านล่างนี้ผมได้รวบรวมลิงก์ที่เกี่ยวข้องกับ Git บางส่วนไว้สำหรับการเรียนรู้เพิ่มเติม
