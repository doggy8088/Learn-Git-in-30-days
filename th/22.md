# วันที่ 22: แก้ไขประวัติเวอร์ชันที่ Commit แล้ว ตอนที่ 4 (rebase)

เราได้พูดคุยกันไปแล้วถึงสามวิธีในการแก้ไขเวอร์ชัน พูดกันตามตรง `git revert` และ `git cherry-pick` ไม่ได้ "แก้ไขบันทึกประวัติเวอร์ชัน" อย่างแท้จริง พวกมันนำเวอร์ชันที่ Commit ไปแล้วมาใช้ ไม่ว่าจะเป็นการ "นำมาใช้ซ้ำ" หรือ "นำมาใช้แบบย้อนกลับ" บทความนี้จะอธิบายกลไก Rebase ของ Git ซึ่งใช้สำหรับแก้ไขบันทึก Commit อย่างแท้จริง คุณสมบัตินี้สำคัญและทรงพลัง

## ทำความเข้าใจ git rebase

Rebase เป็นหนึ่งในคุณสมบัติที่ทรงพลังที่สุดของ Git แต่ก็อาจเป็นอันตรายได้เช่นกัน มันช่วยให้คุณเขียนประวัติ Commit ใหม่ ทำให้ประวัติสะอาดและเป็นเส้นตรงมากขึ้น

Rebasing คือกระบวนการย้ายหรือรวมชุดของ Commit ไปยัง Commit ฐาน (Base) ใหม่ ต่างจาก Merging ซึ่งรักษาประวัติไว้อย่างสมบูรณ์ Rebasing เขียนประวัติใหม่เพื่อสร้างลำดับที่เป็นเส้นตรง

## Rebase พื้นฐาน

การดำเนินการ Rebase พื้นฐาน:

```
# On feature branch
git checkout feature-branch

# Rebase onto main
git rebase main
```

สิ่งนี้จะเล่น Commit ทั้งหมดจาก `feature-branch` ซ้ำบน `main`

## Rebase ทำงานอย่างไร

เมื่อคุณ Rebase:

1. Git ค้นหาบรรพบุรุษร่วม (Common Ancestor) ของ Branch ของคุณและ Branch เป้าหมาย
2. มันบันทึก Commit ทั้งหมดจาก Branch ของคุณตั้งแต่บรรพบุรุษร่วมนั้น
3. มัน Reset Branch ของคุณไปยัง Branch เป้าหมาย
4. มันนำ Commit ที่บันทึกไว้กลับมาใช้ซ้ำทีละรายการ

## Rebase เทียบกับ Merge

**Merge**:
* รักษาประวัติไว้อย่างสมบูรณ์
* แสดงให้เห็นว่า Branch แยกออกและ Merge กันเมื่อใด
* ปลอดภัยสำหรับ Branch ที่แชร์กัน
* สร้าง Merge Commit

**Rebase**:
* สร้างประวัติที่เป็นเส้นตรง
* สะอาดและเข้าใจง่ายกว่า
* เขียนประวัติใหม่ (อันตรายสำหรับ Branch ที่แชร์กัน)
* ไม่มี Merge Commit

เปรียบเทียบด้วยภาพ:

```
# Before rebase
     C---D feature
    /
A---B---E---F main

# After git rebase main (on feature)
             C'---D' feature
            /
A---B---E---F main

# After git merge feature (on main)
     C---D 
    /     A---B---E---F---G main
```

## การจัดการ Conflict ระหว่าง Rebase

หากเกิด Conflict ขึ้น:

```
# Git pauses the rebase
# Resolve conflicts in the files
# Stage the resolved files
git add <resolved-files>

# Continue the rebase
git rebase --continue
```

ในการยกเลิก Rebase:

```
git rebase --abort
```

ในการข้าม Commit ปัจจุบัน:

```
git rebase --skip
```

## Interactive Rebase

Interactive Rebase ให้คุณควบคุม Commit ได้อย่างเต็มที่:

```
git rebase -i HEAD~3
```

สิ่งนี้จะเปิด Editor ขึ้นมา ซึ่งคุณสามารถ:

* **pick**: เก็บ Commit ไว้ตามเดิม
* **reword**: เปลี่ยนข้อความ Commit
* **edit**: หยุดเพื่อแก้ไข Commit
* **squash**: รวมกับ Commit ก่อนหน้า โดยเก็บข้อความทั้งสองไว้
* **fixup**: รวมกับ Commit ก่อนหน้า โดยทิ้งข้อความของรายการนี้
* **drop**: ลบ Commit ออกทั้งหมด

ตัวอย่าง Editor ของ Interactive Rebase:

```
pick abc123 Add feature A
reword def456 Add feature B
squash ghi789 Fix typo in feature B
drop jkl012 Experimental change
```

## งาน Interactive Rebase ที่พบบ่อย

### การรวม Commit (Squashing)

รวมหลาย Commit ให้เป็นรายการเดียว:

```
git rebase -i HEAD~3

# In the editor, change:
pick abc123 First commit
pick def456 Second commit
pick ghi789 Third commit

# To:
pick abc123 First commit
squash def456 Second commit
squash ghi789 Third commit
```

### การจัดลำดับ Commit ใหม่

เพียงจัดลำดับบรรทัดใหม่ใน Editor ของ Interactive Rebase

### การแก้ไข Commit

```
git rebase -i HEAD~3

# Change "pick" to "edit" for the commit you want to modify
# Git will stop at that commit
# Make your changes
git add .
git commit --amend
git rebase --continue
```

## Rebase ไปยัง Branch อื่น

```
git rebase --onto new-base old-base feature-branch
```

สิ่งนี้จะย้าย Commit จาก `feature-branch` ที่อยู่หลัง `old-base` ไปยัง `new-base`

## Autosquash

Squash Commit แบบ Fixup โดยอัตโนมัติ:

```
# Create a fixup commit
git commit --fixup <commit-to-fix>

# Later, rebase with autosquash
git rebase -i --autosquash main
```

## กฎทองของ Rebase

**ห้าม Rebase Commit ที่ถูก Push ไปยัง Repository ที่แชร์กันแล้วเด็ดขาด!**

Rebasing เขียนประวัติใหม่ ซึ่งอาจก่อให้เกิดปัญหาใหญ่กับผู้อื่นที่ทำงานต่อยอดจาก Commit เหล่านั้น

ปลอดภัยสำหรับ:
* Commit ในเครื่องที่ยังไม่ได้ Push
* Feature Branch ที่คุณเป็นเจ้าของ
* การเก็บกวาดก่อนสร้าง Pull Request

อันตรายสำหรับ:
* Branch main/master
* Feature Branch ที่แชร์กัน
* Commit ใด ๆ ที่ผู้อื่นอาจทำงานต่อยอดจากมัน

## การกู้คืนจากความผิดพลาดของ Rebase

หาก Rebase ผิดพลาด:

```
# Find the commit before the rebase
git reflog

# Reset to that commit
git reset --hard HEAD@{2}
```

## แนวปฏิบัติที่ดีที่สุด

1. **Rebase ก่อน Push**: เก็บกวาด Commit ในเครื่องของคุณก่อนแชร์
2. **อย่า Rebase ประวัติสาธารณะ**: Rebase เฉพาะ Commit ในเครื่องเท่านั้น
3. **สำรองข้อมูลก่อน Rebase ครั้งใหญ่**: สร้าง Branch ไว้ก่อน
4. **สื่อสาร**: แจ้งให้ทีมของคุณทราบหากคุณจำเป็นต้อง Rebase โค้ดที่แชร์กัน
5. **ฝึกฝน**: ลอง Rebase บน Branch ที่ทิ้งได้ก่อน

## สรุปของวันนี้

Rebasing เป็นเครื่องมือที่ทรงพลังสำหรับการสร้างประวัติ Commit ที่สะอาดและเป็นเส้นตรง แม้มันจะยอดเยี่ยมสำหรับงานในเครื่องและการเตรียม Branch สำหรับการ Merge แต่ก็ต้องใช้อย่างระมัดระวังเพื่อหลีกเลี่ยงการเขียนประวัติที่แชร์กันใหม่ การทำความเข้าใจว่าเมื่อใดและอย่างไรควรใช้ Rebase เป็นสิ่งสำคัญสำหรับ Workflow ของ Git ขั้นสูง

ขอผมเรียบเรียงคำสั่งและพารามิเตอร์ Git ที่เรียนรู้ในวันนี้อีกครั้ง:

* git rebase
* git rebase main
* git rebase -i
* git rebase --continue
* git rebase --abort
* git rebase --skip
* git rebase --onto
* git rebase --autosquash
* git commit --fixup
