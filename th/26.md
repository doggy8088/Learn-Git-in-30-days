# วันที่ 26: หลายคนทำงานใน Remote Repository เดียวกัน

เมื่อมีหลายคนทำงานใน Repository เดียวกัน การประสานงานและความเข้าใจ Workflow ของ Git จะกลายเป็นสิ่งสำคัญ บทความนี้จะสำรวจแนวปฏิบัติที่ดีที่สุดและสถานการณ์ที่พบบ่อยสำหรับการทำงานร่วมกันเป็นทีม

## ความท้าทายที่พบบ่อยในการทำงานร่วมกันเป็นทีม

1. **Merge Conflict**: หลายคนแก้ไขไฟล์เดียวกัน
2. **Branch ที่แยกออกจากกัน**: Local และ Remote ไม่ตรงกัน
3. **Commit ที่สูญหาย**: เขียนทับงานของผู้อื่นโดยไม่ได้ตั้งใจ
4. **ช่องว่างในการสื่อสาร**: ไม่รู้ว่าผู้อื่นกำลังทำอะไรอยู่

## Workflow พื้นฐานของทีม

### Workflow ประจำวัน

```
# Morning: Get latest changes
git pull origin main

# Create feature branch
git checkout -b feature-name

# Work and commit frequently
git add .
git commit -m "Progress on feature"

# Before finishing: update with latest main
git checkout main
git pull origin main
git checkout feature-name
git merge main

# Resolve any conflicts

# Push your branch
git push origin feature-name

# Create pull request for review
```

### การทำให้ทันสมัยอยู่เสมอ

Fetch การเปลี่ยนแปลงเป็นประจำ:

```
# Check what's changed
git fetch origin

# View remote changes
git log main..origin/main

# Merge if appropriate
git merge origin/main
```

## การจัดการงานที่ทำพร้อมกัน

### สถานการณ์ที่ 1: ไฟล์เดียวกัน คนละบรรทัด

โดยปกติจะ Merge โดยอัตโนมัติ:

```
git pull origin main
# If auto-merge succeeds, you're done!
```

### สถานการณ์ที่ 2: ไฟล์เดียวกัน บรรทัดเดียวกัน

ต้องแก้ด้วยตนเอง:

```
git pull origin main
# Conflict!

# Edit conflicting files
# Remove markers: <<<<<<<, =======, >>>>>>>
# Keep the correct changes

# Stage resolved files
git add resolved-file.txt

# Complete the merge
git commit
```

### สถานการณ์ที่ 3: มีคน Rebase

อาจก่อให้เกิดปัญหาใหญ่ได้หาก Branch นั้นแชร์กัน:

```
# If someone rebased a shared branch
git fetch origin

# You need to rebase your work
git rebase origin/feature-branch

# Or start fresh
git reset --hard origin/feature-branch
```

## กระบวนการ Review โค้ด

### การสร้าง Pull Request ที่ดี

1. **ชื่อเรื่องที่สื่อความหมาย**: "Add user authentication feature"
2. **คำอธิบายโดยละเอียด**:
   * PR นี้ทำอะไร?
   * ทำไมจึงต้องมีการเปลี่ยนแปลงนี้?
   * ทดสอบอย่างไร?
3. **ทำให้เล็ก**: Review ได้ง่ายกว่า
4. **หนึ่งประเด็นต่อหนึ่ง PR**: อย่าผสม Feature และการแก้ไขเข้าด้วยกัน
5. **อัปเดตกับ main**: ให้แน่ใจว่า Merge ได้อย่างราบรื่น

### การ Review Pull Request

1. **ตรวจสอบโค้ด** ทั้งตรรกะและรูปแบบ
2. **ทดสอบในเครื่อง** หากเป็นไปได้
3. **ให้ Feedback ที่สร้างสรรค์**
4. **อนุมัติหรือขอให้เปลี่ยนแปลง**
5. **Merge เมื่อพร้อม**

## การแก้ Conflict ในทีม

### สื่อสารก่อน

* **พูดคุยกับทีมของคุณ**: มักป้องกันปัญหาได้
* **ใช้ความคิดเห็นใน PR**: ถามคำถาม พูดคุยถึงแนวทาง
* **บันทึกการตัดสินใจ**: อัปเดตคำอธิบายหรือความคิดเห็นใน PR

### วิธีแก้เชิงเทคนิค

#### แก้ Conflict

```
# Update your branch
git fetch origin
git merge origin/main

# Resolve conflicts in files
# Stage changes
git add .

# Complete merge
git commit
```

#### ยกเลิกแล้วเริ่มใหม่

```
# If resolution is too complex
git merge --abort

# Talk to the other developer
# Coordinate who makes what changes
```

## กฎการป้องกัน Branch

บน GitHub ป้องกัน Branch ที่สำคัญ:

1. **กำหนดให้ต้องมี Review ใน Pull Request**
2. **กำหนดให้ต้องผ่าน Status Check** (CI/CD)
3. **บังคับใช้ประวัติที่เป็นเส้นตรง**
4. **รวมถึงผู้ดูแลระบบด้วย**

กำหนดค่าได้ที่: Settings > Branches > Branch protection rules

## Continuous Integration

ใช้ CI เพื่อจับปัญหาได้ตั้งแต่เนิ่น ๆ:

```yaml
# Example .github/workflows/test.yml
name: Tests
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v2
      - run: npm install
      - run: npm test
```

## เครื่องมือสื่อสาร

### ข้อความ Commit

ทำตามหลักการ:

```
<type>(<scope>): <subject>

<body>

<footer>
```

ตัวอย่าง:

```
feat(auth): add user login functionality

Implement JWT-based authentication with email and password.
Includes password hashing with bcrypt and token refresh.

Closes #123
```

### Pull Request Template

สร้าง `.github/pull_request_template.md`:

```markdown
## Description
<!-- Describe your changes -->

## Type of Change
- [ ] Bug fix
- [ ] New feature
- [ ] Breaking change

## Testing
<!-- How was this tested? -->

## Checklist
- [ ] Tests pass
- [ ] Documentation updated
- [ ] No merge conflicts
```

## การจัดการทีมขนาดใหญ่

### Feature Flags

Deploy โค้ดที่ยังไม่พร้อมใช้งาน:

```javascript
if (featureFlags.newUI) {
  return <NewUI />;
} else {
  return <OldUI />;
}
```

### Release Branch

แยกการพัฒนาออกจาก Release:

```
main (production)
├── release/v2.0
├── release/v1.9
└── develop (integration)
    ├── feature/login
    ├── feature/dashboard
    └── feature/reports
```

## สรุปแนวปฏิบัติที่ดีที่สุด

1. **Pull ก่อน Push**: รับการเปลี่ยนแปลงล่าสุดก่อนเสมอ
2. **Commit บ่อย ๆ**: Commit ขนาดเล็กและมีเหตุผล
3. **Push เป็นประจำ**: แชร์งานของคุณ รับ Feedback
4. **ใช้ Branch**: รักษา main ให้เสถียร
5. **เขียน Test**: จับปัญหาก่อนที่ผู้อื่นจะเจอ
6. **Review โค้ด**: เรียนรู้จากกันและกัน
7. **สื่อสาร**: สื่อสารมากเกินไปหากจำเป็น
8. **บันทึกเอกสาร**: README, Wiki, ความคิดเห็น
9. **อดทน**: Conflict เกิดขึ้นได้ ค่อย ๆ ทำงานผ่านมันไป
10. **ช่วยเหลือผู้อื่น**: ความสำเร็จของทีมคือความสำเร็จของคุณ

## สรุปของวันนี้

การทำงานร่วมกันเป็นทีมด้วย Git ให้สำเร็จต้องอาศัยทั้งทักษะเชิงเทคนิคและการสื่อสารที่ดี การทำความเข้าใจ Workflow ที่พบบ่อย การจัดการ Conflict อย่างนุ่มนวล และการใช้เครื่องมืออย่าง Pull Request และ CI/CD จะช่วยให้ทีมของคุณทำงานร่วมกันได้อย่างราบรื่น

ขอผมเรียบเรียงคำสั่งและพารามิเตอร์ Git ที่เรียนรู้ในวันนี้อีกครั้ง:

* git pull origin main
* git fetch origin
* git merge origin/main
* git rebase origin/branch
* git push origin branch
* git log main..origin/main
