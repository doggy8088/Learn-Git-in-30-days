# วันที่ 18: แก้ไขประวัติเวอร์ชันที่ Commit แล้ว ตอนที่ 1 (reset & amend)

เมื่อใช้ Git ในการควบคุมเวอร์ชัน เราใช้ `git commit` เพื่อสร้างเวอร์ชันจำนวนมาก เนื่องจาก Git เป็นระบบควบคุมเวอร์ชันแบบกระจายศูนย์ เมื่อเทียบกับระบบควบคุมเวอร์ชันแบบรวมศูนย์อย่าง Subversion หรือ TFVC แล้ว Git มีการออกแบบสิทธิ์สำหรับการควบคุมเวอร์ชันน้อยกว่า Git มีกลไกสำหรับ "การแก้ไขบันทึกเวอร์ชัน" มากกว่า ซึ่งช่วยให้คุณจัดระเบียบสิ่งต่าง ๆ ล่วงหน้าก่อนที่จะ "แชร์" เวอร์ชันกับผู้อื่น

## หลักการพื้นฐานของการควบคุมเวอร์ชัน

เมื่อดำเนินการควบคุมเวอร์ชัน ไม่ว่าจะใช้ Git, Subversion หรือ TFVC การรักษาบันทึกเวอร์ชันที่ดีจะช่วยให้เราติดตามประวัติการอัปเดตของแต่ละเวอร์ชันได้ (เมื่อเราจำเป็นต้องทำเช่นนั้น) จากประสบการณ์ส่วนตัวของผม เราแทบไม่มีโอกาสหรือความต้องการที่จะติดตามกระบวนการพัฒนาซอฟต์แวร์ในโปรเจกต์เลย โปรเจกต์ของเราหลายโปรเจกต์สะสมบันทึกเวอร์ชันไว้หลายพันรายการ ใครจะมีเวลามาตรวจสอบประวัตินั้น?

อย่างไรก็ตาม ในทางปฏิบัติ เมื่อเกิด Bug ของซอฟต์แวร์ขึ้น เราจำเป็นต้องติดตามบันทึกประวัติของ Bug ที่ระบุเพื่อค้นหาสาเหตุที่แท้จริงของ Bug นี่คือช่วงเวลาที่การควบคุมเวอร์ชันมอบคุณค่ามากที่สุด

ดังนั้น วิธีรักษาบันทึก "เวอร์ชัน" ที่ดีจึงเป็นเรื่องสำคัญมากเช่นกัน นี่คือหลักการควบคุมบางประการที่จะแบ่งปัน:

* สร้างเวอร์ชันสำหรับการแก้ไขฟีเจอร์เล็ก ๆ แต่ละครั้ง ทำให้ติดตามการเปลี่ยนแปลงได้ง่ายขึ้น
* อย่าสะสมการแก้ไขจำนวนมากก่อนที่จะสร้าง "เวอร์ชันใหญ่"
* แก้ไขฟีเจอร์อย่างมีตรรกะและเป็นลำดับ ให้แน่ใจว่าการแก้ไขเวอร์ชันที่เกี่ยวข้องกันถูก Commit ตามลำดับเพื่อการติดตามที่ง่ายขึ้น

อย่างไรก็ตาม มนุษย์ย่อมทำผิดพลาดได้ ใครจะรับประกันได้ว่าทุกคนในทีมจะสามารถปฏิบัติตามหลักการข้างต้นในการควบคุมเวอร์ชันได้เสมอ? ใครบ้างที่จะไม่ "นึกอยากแก้ก็แก้"? ข้อกำหนดเช่นนี้จึงกลายเป็นเรื่องที่ไม่สามารถปฏิบัติได้จริง ดังนั้น เราจึงต้องการกลไกในการ "แก้ไขเวอร์ชัน" เพื่อที่ว่าเมื่อเวอร์ชันถูกส่งไปยังเซิร์ฟเวอร์ระยะไกล เวอร์ชันเหล่านั้นจะอยู่ในสถานะที่สมบูรณ์แบบอยู่แล้ว

## เหตุผลในการแก้ไขประวัติ Commit

จนถึงตอนนี้ เรายังไม่ได้กล่าวถึงรายละเอียดของ "Remote Repository" ดังนั้นการดำเนินการ Git ส่วนใหญ่จึงยังคงเน้นไปที่การดำเนินการในเครื่อง นั่นคือการควบคุมเวอร์ชันใน Working Directory โดย Repository นี้อยู่ในไดเรกทอรี `.git/` ของคุณ อย่างไรก็ตาม ในไม่ช้าเราจะพูดถึงการประยุกต์ใช้ "Remote Repository" ซึ่งเมื่อมีมากกว่าหนึ่งคนที่มี Repository ก็จะมีรายละเอียดที่ต้องใส่ใจมากขึ้น

การอนุญาตให้ทุกคนแก้ไขประวัติ Commit ได้ตามอำเภอใจอย่างสมบูรณ์อาจฟังดูแปลกสำหรับคนที่คุ้นเคยกับ Subversion หรือ TFVC เพราะทุกคนเคยเชื่อมต่อแบบรวมศูนย์ไปยังเซิร์ฟเวอร์ควบคุมเวอร์ชัน โดยใช้ Repository แบบรวมศูนย์ หากใครสามารถดัดแปลงบันทึกประวัติได้ตามอำเภอใจ มันจะยังเรียกว่าการควบคุมเวอร์ชันได้อีกหรือ?

อันที่จริง ในกระบวนการควบคุมเวอร์ชันด้วย Git แนวคิดก็เหมือนกัน ตราบใดที่ Repository เดียวกันถูกแชร์กันโดยหลายคน หากใครดัดแปลงเวอร์ชันตามอำเภอใจ การควบคุมเวอร์ชันด้วย Git ก็จะไม่สามารถทำงานได้อย่างถูกต้องเช่นกัน

แล้ว สถานการณ์การใช้งานใดบ้างที่จะต้องแก้ไขบันทึกเวอร์ชัน? คุณสามารถอ้างอิงประเด็นต่อไปนี้ได้

สมมติว่าตอนนี้เรามีสามเวอร์ชัน [A] -> [B] -> [C]:

* คุณอาจพบว่าเวอร์ชัน [C] ถูก Commit อย่างไม่ถูกต้อง และต้องลบการเปลี่ยนแปลงทั้งหมดในเวอร์ชันนี้
* คุณอาจค้นพบหลังจาก Commit [C] ไปแล้วว่า เวอร์ชันนี้มีเพียงโค้ดทดสอบเท่านั้น และคุณต้องการลบมัน
* ข้อความบันทึกของบางเวอร์ชันมีคำสะกดผิด และคุณต้องการแก้ไขข้อความโดยไม่ส่งผลกระทบต่อประวัติการเปลี่ยนแปลงไฟล์
* คุณอาจต้องการปรับลำดับ Commit ของเวอร์ชันเหล่านี้เป็น [A] -> [C] -> [B] เพื่อทำให้วิวัฒนาการของเวอร์ชันมีตรรกะมากขึ้น
* คุณพบว่าเวอร์ชัน [B] ลืมใส่ไฟล์สำคัญก่อนที่จะ Commit และคุณต้องการแก้ไขการเปลี่ยนแปลงนี้ในภายหลัง
* เมื่อคุณวางแผนจะ "แชร์" Branch คุณค้นพบข้อบกพร่องของโค้ด และสามารถแก้ไขมันได้ก่อนที่จะแชร์

## ข้อควรทราบที่สำคัญสำหรับการแก้ไขประวัติ Commit

Git ยังคงกลไกสำหรับ "การแก้ไขบันทึกประวัติเวอร์ชัน" ไว้ โดยหลัก ๆ แล้วหวังว่าหลังจากที่คุณ "จัดการเวอร์ชันด้วยตนเอง" ถึงระดับหนึ่งแล้ว คุณจะสามารถจัดระเบียบข้อมูลต่าง ๆ ในบันทึกเวอร์ชันได้ด้วยตัวเอง เพื่อที่ว่าหลังจากคุณ "เผยแพร่" เวอร์ชันเหล่านั้นแล้ว ผู้อื่นจะสามารถเข้าใจได้ชัดเจนยิ่งขึ้นว่าคุณทำการแก้ไขอะไรบ้างกับเวอร์ชันเหล่านี้

ดังนั้น เมื่อแก้ไขบันทึกประวัติเวอร์ชัน มีบางสิ่งที่ต้องให้ความสนใจเป็นพิเศษ:

* Repository สามารถมี Branch ได้หลาย Branch (ชื่อ Branch เริ่มต้นคือ `master`)
* หน่วยที่เล็กที่สุดสำหรับการแชร์ซอร์สโค้ด Git คือ "Branch"
* คุณสามารถแก้ไขเวอร์ชันบน Branch ได้ตามอำเภอใจ ตราบใดที่คุณยังไม่ได้ "แชร์" พวกมันกับผู้อื่น
* **เมื่อคุณ "แชร์" Branch ที่ระบุกับผู้อื่นแล้ว อย่าแก้ไขบันทึกประวัติเวอร์ชันที่ "แชร์" เหล่านั้นอีกต่อไป!**

## ทำความเข้าใจ git commit --amend

ตัวเลือก `--amend` ช่วยให้คุณแก้ไข Commit ล่าสุดได้ สิ่งนี้มีประโยชน์เมื่อคุณ:

* ต้องการเปลี่ยนข้อความ Commit
* ลืมใส่ไฟล์บางไฟล์
* ต้องการแก้ไขข้อผิดพลาดเล็ก ๆ ใน Commit ล่าสุด

### การเปลี่ยนข้อความ Commit ล่าสุด

```
git commit --amend -m "New commit message"
```

### การเพิ่มไฟล์เข้าไปใน Commit ล่าสุด

```
# Make changes or add forgotten files
git add forgotten-file.txt

# Amend the commit
git commit --amend --no-edit
```

แฟล็ก `--no-edit` จะคงข้อความ Commit เดิมไว้

### การ Amend แบบโต้ตอบ

ในการแก้ไขข้อความ Commit ในโปรแกรมแก้ไขของคุณ:

```
git commit --amend
```

คำสั่งนี้จะเปิดโปรแกรมแก้ไขที่คุณกำหนดค่าไว้ ซึ่งคุณสามารถแก้ไขข้อความ Commit ได้

## ทำความเข้าใจ git reset

`git reset` เป็นคำสั่งที่ทรงพลังซึ่งสามารถ:

* เลื่อนพอยน์เตอร์ของ Branch ปัจจุบัน
* แก้ไข Staging Area (Index)
* แก้ไข Working Directory

โหมดของ Reset มีสามโหมด:

1. **--soft**: เลื่อน HEAD คง Staging Area และ Working Directory ไว้ไม่เปลี่ยนแปลง
2. **--mixed** (ค่าเริ่มต้น): เลื่อน HEAD รีเซ็ต Staging Area คง Working Directory ไว้ไม่เปลี่ยนแปลง
3. **--hard**: เลื่อน HEAD รีเซ็ต Staging Area และ Working Directory

## Soft Reset

เลื่อนพอยน์เตอร์ของ Branch แต่คงให้การเปลี่ยนแปลงของคุณอยู่ใน Stage:

```
git reset --soft HEAD~1
```

คำสั่งนี้จะยกเลิก Commit ล่าสุดแต่คงให้การเปลี่ยนแปลงของคุณอยู่ใน Staging Area พร้อมที่จะ Commit ใหม่

## Mixed Reset

เลื่อนพอยน์เตอร์ของ Branch และนำการเปลี่ยนแปลงออกจาก Stage:

```
git reset HEAD~1
# or
git reset --mixed HEAD~1
```

คำสั่งนี้จะยกเลิก Commit ล่าสุดและนำการเปลี่ยนแปลงออกจาก Stage แต่การเปลี่ยนแปลงยังคงอยู่ใน Working Directory ของคุณ

## Hard Reset

ทิ้ง Commit และการเปลี่ยนแปลงทั้งหมดอย่างสมบูรณ์:

```
git reset --hard HEAD~1
```

**คำเตือน**: สิ่งนี้จะทิ้งการเปลี่ยนแปลงอย่างถาวร โปรดใช้ด้วยความระมัดระวัง!

## การ Reset ไปยัง Commit ที่ระบุ

คุณสามารถ Reset ไปยัง Commit ใด ๆ ก็ได้:

```
# Using commit hash
git reset --hard a1b2c3d

# Using relative reference
git reset --soft HEAD~3
```

## การนำไฟล์ออกจาก Stage

ในการนำไฟล์ออกจาก Stage โดยไม่สูญเสียการเปลี่ยนแปลง:

```
git reset HEAD file.txt
# or
git restore --staged file.txt
```

## การกู้คืนจาก Reset

หากคุณ Reset โดยไม่ได้ตั้งใจ โดยปกติคุณสามารถกู้คืนได้โดยใช้ Reflog:

```
git reflog
git reset --hard HEAD@{2}
```

## Reset กับ Revert

ความแตกต่างที่สำคัญ:

* **reset**: เขียนประวัติใหม่ (ใช้สำหรับ Commit ในเครื่องที่ยังไม่ได้ Push)
* **revert**: สร้าง Commit ใหม่ที่ยกเลิกการเปลี่ยนแปลง (ปลอดภัยสำหรับประวัติที่แชร์กัน)

## กรณีการใช้งานทั่วไป

### ยกเลิก Commit ล่าสุด คงการเปลี่ยนแปลงไว้

```
git reset HEAD~1
```

### ยกเลิก Commit ล่าสุด ทิ้งการเปลี่ยนแปลง

```
git reset --hard HEAD~1
```

### แยก Commit หนึ่งรายการออกเป็นหลายรายการ

```
git reset HEAD~1
git add file1.txt
git commit -m "First part"
git add file2.txt
git commit -m "Second part"
```

### เปลี่ยน Commit ล่าสุดสองสามรายการ

```
git reset --soft HEAD~3
# Make changes
git commit -m "Combined commit"
```

## คำเตือนและแนวปฏิบัติที่ดีที่สุด

1. **อย่า Reset ประวัติสาธารณะ**: อย่า Reset Commit ที่ถูก Push ไปยัง Repository ที่แชร์กันแล้ว
2. **ใช้ --amend ด้วยความระมัดระวัง**: Amend เฉพาะ Commit ที่ยังไม่ได้ Push เท่านั้น
3. **พิจารณาทางเลือกอื่น**: สำหรับประวัติที่แชร์กัน ให้ใช้ `git revert` แทน
4. **ตรวจสอบซ้ำ**: โดยเฉพาะก่อนใช้ `--hard`
5. **รู้จัก Reflog ของคุณ**: มันสามารถช่วยคุณจากความผิดพลาดได้

## สรุปของวันนี้

`git commit --amend` และ `git reset` เป็นเครื่องมือที่ทรงพลังสำหรับการแก้ไขประวัติ Commit ในเครื่อง `--amend` เหมาะอย่างยิ่งสำหรับการแก้ไขอย่างรวดเร็วใน Commit ล่าสุด ในขณะที่ `reset` ให้คุณควบคุม Commit หลายรายการได้มากกว่า อย่างไรก็ตาม ทั้งคู่ควรใช้ด้วยความระมัดระวัง โดยเฉพาะสำหรับ Commit ที่ถูกแชร์กับผู้อื่นแล้ว

ขอผมเรียบเรียงคำสั่งและพารามิเตอร์ Git ที่เรียนรู้ในวันนี้อีกครั้ง:

* git commit --amend
* git commit --amend --no-edit
* git reset --soft
* git reset --mixed
* git reset --hard
* git reset HEAD~n
* git reflog
