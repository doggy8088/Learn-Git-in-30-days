# Ngày 18: Sửa lịch sử phiên bản đã commit Phần 1 (reset & amend)

Khi sử dụng Git để quản lý phiên bản, chúng ta dùng `git commit` để tạo nhiều phiên bản. Vì Git là một hệ thống quản lý phiên bản phân tán, so với các hệ thống quản lý phiên bản tập trung như Subversion hay TFVC, Git có ít thiết kế về quyền hơn đối với quản lý phiên bản. Git cung cấp nhiều cơ chế hơn cho việc "sửa đổi các bản ghi phiên bản", cho phép bạn sắp xếp mọi thứ trước khi "chia sẻ" các phiên bản với người khác.

## Các nguyên tắc cơ bản của quản lý phiên bản

Khi thực hiện quản lý phiên bản, dù dùng Git, Subversion hay TFVC, việc duy trì các bản ghi phiên bản tốt giúp chúng ta theo dõi lịch sử cập nhật của mỗi phiên bản (khi chúng ta cần làm điều này). Theo kinh nghiệm cá nhân của tôi, chúng ta hiếm khi có cơ hội hoặc mong muốn theo dõi quá trình phát triển phần mềm trong một dự án. Nhiều dự án của chúng ta đã tích lũy hàng nghìn bản ghi phiên bản — ai có thời gian để điều tra lịch sử đó?

Tuy nhiên, trong thực tế, khi lỗi phần mềm xảy ra, chúng ta cần theo dõi các bản ghi lịch sử của những lỗi cụ thể để tìm ra nguyên nhân thực sự của lỗi. Đây là lúc quản lý phiên bản mang lại giá trị lớn nhất.

Vì vậy, cách duy trì các "bản ghi phiên bản" tốt cũng rất quan trọng. Dưới đây là một số nguyên tắc kiểm soát để chia sẻ:

* Tạo một phiên bản cho mỗi sửa đổi tính năng nhỏ, giúp việc theo dõi thay đổi dễ dàng hơn
* Không bao giờ tích lũy nhiều sửa đổi rồi mới tạo một "phiên bản lớn"
* Sửa các tính năng một cách logic và theo thứ tự, đảm bảo các bản sửa phiên bản liên quan được commit theo trình tự để dễ theo dõi hơn

Tuy nhiên, con người ai cũng mắc sai lầm — ai có thể đảm bảo rằng mọi người trong nhóm luôn có thể tuân theo các nguyên tắc trên để quản lý phiên bản? Ai mà chẳng "nghĩ đến đâu sửa đến đó"? Những yêu cầu như vậy trở nên không thực tế. Vì vậy, chúng ta cần một cơ chế để "sửa đổi các phiên bản" sao cho khi các phiên bản được gửi lên máy chủ từ xa, chúng đã ở trong trạng thái hoàn hảo.

## Lý do sửa lịch sử Commit

Cho đến nay, chúng ta chưa đề cập đến chi tiết của "remote repository", vì vậy hầu hết các thao tác Git vẫn tập trung vào các thao tác cục bộ, tức là quản lý phiên bản trong working directory, với repository này nằm trong thư mục `.git/` của bạn. Tuy nhiên, chúng ta sẽ sớm thảo luận về ứng dụng của "remote repository", khi đó nhiều người sẽ cùng có một repository, và nhiều chi tiết hơn sẽ cần được chú ý.

Việc hoàn toàn cho phép mọi người tùy ý sửa đổi lịch sử commit có thể nghe có vẻ lạ đối với những người quen thuộc với Subversion hoặc TFVC, bởi vì mọi người đã quen với việc kết nối tập trung tới một máy chủ quản lý phiên bản, sử dụng một repository tập trung. Nếu ai đó có thể tùy ý can thiệp vào các bản ghi lịch sử, liệu nó còn có thể được gọi là quản lý phiên bản không?

Thực ra, trong quản lý phiên bản bằng Git, khái niệm cũng giống như vậy. Miễn là cùng một repository được nhiều người chia sẻ, nếu ai đó tùy ý can thiệp vào các phiên bản, quản lý phiên bản bằng Git cũng sẽ không thể hoạt động đúng cách.

Vậy, những tình huống sử dụng nào sẽ yêu cầu sửa đổi các bản ghi phiên bản? Bạn có thể tham khảo các điểm sau.

Giả sử bây giờ chúng ta có ba phiên bản [A] -> [B] -> [C]:

* Bạn có thể thấy rằng phiên bản [C] đã được commit sai và phải xóa mọi thay đổi trong phiên bản này
* Bạn có thể phát hiện sau khi commit [C] rằng phiên bản này chỉ có mã kiểm thử, và bạn muốn xóa nó
* Một số thông điệp của bản ghi phiên bản có lỗi chính tả, và bạn muốn sửa nội dung thông điệp mà không ảnh hưởng tới lịch sử thay đổi tệp
* Bạn có thể muốn điều chỉnh thứ tự commit của các phiên bản này thành [A] -> [C] -> [B] để quá trình tiến hóa của phiên bản hợp lý hơn
* Bạn thấy rằng phiên bản [B] đã quên bao gồm một tệp quan trọng trước khi commit, và bạn muốn khắc phục thay đổi này sau đó
* Khi bạn dự định "chia sẻ" một branch, bạn phát hiện các khiếm khuyết trong mã nguồn và có thể sửa chúng trước khi chia sẻ

## Lưu ý quan trọng khi sửa lịch sử Commit

Git giữ lại cơ chế cho việc "sửa đổi các bản ghi lịch sử phiên bản", chủ yếu với hy vọng rằng sau khi bạn đã "tự quản lý các phiên bản" đến một mức độ nhất định, bạn có thể tự sắp xếp các thông tin khác nhau trong các bản ghi phiên bản, để sau khi bạn "công bố" các phiên bản, người khác có thể hiểu rõ hơn bạn đã thực hiện những sửa đổi gì đối với các phiên bản này.

Vì vậy, khi sửa đổi các bản ghi lịch sử phiên bản, có một số điều phải đặc biệt chú ý:

* Một repository có thể có nhiều branch (tên branch mặc định là `master`)
* Đơn vị tối thiểu để chia sẻ mã nguồn Git là theo "branch"
* Bạn có thể tùy ý sửa đổi các phiên bản trên một branch, miễn là bạn chưa "chia sẻ" chúng với người khác
* **Một khi bạn "chia sẻ" một branch cụ thể với người khác, đừng sửa đổi các bản ghi lịch sử phiên bản "đã chia sẻ" đó nữa!**

## Hiểu git commit --amend

Tùy chọn `--amend` cho phép bạn sửa đổi commit gần đây nhất. Điều này hữu ích khi bạn:

* Muốn thay đổi thông điệp commit
* Quên bao gồm một số tệp
* Cần sửa một sai sót nhỏ trong commit cuối cùng

### Thay đổi thông điệp của Commit cuối cùng

```
git commit --amend -m "New commit message"
```

### Thêm tệp vào Commit cuối cùng

```
# Make changes or add forgotten files
git add forgotten-file.txt

# Amend the commit
git commit --amend --no-edit
```

Cờ `--no-edit` giữ nguyên thông điệp commit hiện có.

### Amend tương tác

Để chỉnh sửa thông điệp commit trong trình soạn thảo của bạn:

```
git commit --amend
```

Lệnh này mở trình soạn thảo đã được cấu hình của bạn, nơi bạn có thể sửa đổi thông điệp commit.

## Hiểu git reset

`git reset` là một lệnh mạnh mẽ có thể:

* Di chuyển con trỏ branch hiện tại
* Sửa đổi khu vực stage (index)
* Sửa đổi working directory

Có ba chế độ reset:

1. **--soft**: Di chuyển HEAD, giữ nguyên khu vực stage và working directory không thay đổi
2. **--mixed** (mặc định): Di chuyển HEAD, đặt lại khu vực stage, giữ nguyên working directory không thay đổi
3. **--hard**: Di chuyển HEAD, đặt lại khu vực stage và working directory

## Soft Reset

Di chuyển con trỏ branch nhưng giữ các thay đổi của bạn ở trạng thái đã stage:

```
git reset --soft HEAD~1
```

Lệnh này hoàn tác commit cuối cùng nhưng để các thay đổi của bạn trong khu vực stage, sẵn sàng để commit lại.

## Mixed Reset

Di chuyển con trỏ branch và hủy stage các thay đổi:

```
git reset HEAD~1
# or
git reset --mixed HEAD~1
```

Lệnh này hoàn tác commit cuối cùng và hủy stage các thay đổi, nhưng các thay đổi vẫn còn trong working directory của bạn.

## Hard Reset

Loại bỏ hoàn toàn commit và mọi thay đổi:

```
git reset --hard HEAD~1
```

**Cảnh báo**: Điều này loại bỏ các thay đổi vĩnh viễn. Hãy sử dụng một cách thận trọng!

## Reset về một Commit cụ thể

Bạn có thể reset về bất kỳ commit nào:

```
# Using commit hash
git reset --hard a1b2c3d

# Using relative reference
git reset --soft HEAD~3
```

## Hủy Stage tệp

Để hủy stage một tệp mà không làm mất các thay đổi:

```
git reset HEAD file.txt
# or
git restore --staged file.txt
```

## Khôi phục sau Reset

Nếu bạn reset nhầm, bạn thường có thể khôi phục bằng reflog:

```
git reflog
git reset --hard HEAD@{2}
```

## Reset và Revert

Sự phân biệt quan trọng:

* **reset**: Viết lại lịch sử (dùng cho các commit cục bộ, chưa được push)
* **revert**: Tạo một commit mới hoàn tác các thay đổi (an toàn cho lịch sử đã chia sẻ)

## Các trường hợp sử dụng phổ biến

### Hoàn tác Commit cuối cùng, giữ các thay đổi

```
git reset HEAD~1
```

### Hoàn tác Commit cuối cùng, loại bỏ các thay đổi

```
git reset --hard HEAD~1
```

### Chia một Commit thành nhiều Commit

```
git reset HEAD~1
git add file1.txt
git commit -m "First part"
git add file2.txt
git commit -m "Second part"
```

### Thay đổi vài Commit cuối cùng

```
git reset --soft HEAD~3
# Make changes
git commit -m "Combined commit"
```

## Cảnh báo và thực hành tốt nhất

1. **Không bao giờ reset lịch sử công khai**: Đừng reset các commit đã được push lên các repository dùng chung
2. **Sử dụng --amend một cách cẩn thận**: Chỉ amend các commit chưa được push
3. **Cân nhắc các phương án thay thế**: Đối với lịch sử đã chia sẻ, hãy dùng `git revert` thay thế
4. **Kiểm tra hai lần**: Đặc biệt là trước khi dùng `--hard`
5. **Nắm rõ reflog của bạn**: Nó có thể cứu bạn khỏi các sai lầm

## Tóm tắt hôm nay

`git commit --amend` và `git reset` là những công cụ mạnh mẽ để sửa lịch sử commit cục bộ. `--amend` hoàn hảo cho các bản sửa nhanh đối với commit cuối cùng, trong khi `reset` cho bạn nhiều quyền kiểm soát hơn đối với nhiều commit. Tuy nhiên, cả hai đều nên được sử dụng một cách cẩn thận, đặc biệt đối với các commit đã được chia sẻ với người khác.

Hãy để tôi sắp xếp lại các lệnh và tham số Git đã học hôm nay:

* git commit --amend
* git commit --amend --no-edit
* git reset --soft
* git reset --mixed
* git reset --hard
* git reset HEAD~n
* git reflog
