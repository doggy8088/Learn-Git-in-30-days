# Hari 18: Memperbaiki Riwayat Versi yang Sudah Di-commit Bagian 1 (reset & amend)

Ketika menggunakan Git untuk kontrol versi, kita menggunakan `git commit` untuk membuat banyak versi. Karena Git adalah sistem kontrol versi terdistribusi, dibandingkan dengan sistem kontrol versi terpusat seperti Subversion atau TFVC, Git memiliki desain izin yang lebih sedikit untuk kontrol versi. Git menyediakan lebih banyak mekanisme untuk "memodifikasi catatan versi", memungkinkan Anda mengatur berbagai hal terlebih dahulu sebelum "berbagi" versi dengan orang lain.

## Prinsip Dasar Kontrol Versi

Ketika melakukan kontrol versi, baik menggunakan Git, Subversion, atau TFVC, mempertahankan catatan versi yang baik membantu kita melacak riwayat pembaruan setiap versi (ketika kita perlu melakukannya). Dalam pengalaman pribadi saya, kita jarang memiliki kesempatan atau keinginan untuk melacak proses pengembangan perangkat lunak dalam sebuah proyek. Banyak proyek kami telah mengumpulkan ribuan catatan versi — siapa yang punya waktu untuk menyelidiki riwayat itu?

Namun, dalam praktiknya, ketika bug perangkat lunak terjadi, kita perlu melacak catatan historis dari bug tertentu untuk menemukan penyebab sebenarnya dari bug tersebut. Pada saat inilah kontrol versi memberikan nilai terbesar.

Oleh karena itu, cara mempertahankan "catatan versi" yang baik juga sangat penting. Berikut adalah beberapa prinsip pengendalian untuk dibagikan:

* Buat versi untuk setiap modifikasi fitur kecil, sehingga lebih mudah melacak perubahan
* Jangan pernah mengumpulkan banyak modifikasi sebelum membuat "versi besar"
* Perbaiki fitur secara logis dan berurutan, memastikan perbaikan versi terkait di-commit secara berurutan untuk pelacakan yang lebih mudah

Namun, manusia membuat kesalahan — siapa yang dapat memastikan bahwa semua orang di tim selalu dapat mengikuti prinsip-prinsip di atas untuk kontrol versi? Siapa yang tidak hanya "memodifikasi sesuai pikiran"? Persyaratan seperti itu menjadi tidak praktis. Oleh karena itu, kita memerlukan mekanisme untuk "memodifikasi versi" sehingga ketika versi dikirimkan ke server remote, versi-versi tersebut sudah dalam keadaan sempurna.

## Alasan Memperbaiki Riwayat Commit

Sejauh ini, kita belum menyebutkan detail "repositori remote", jadi sebagian besar operasi Git masih berfokus pada operasi lokal, yaitu kontrol versi di direktori kerja, dengan repositori ini terletak di direktori `.git/` Anda. Namun, kita akan segera membahas penerapan "repositori remote", ketika lebih dari satu orang akan memiliki repositori, dan lebih banyak detail yang perlu diperhatikan.

Mengizinkan semua orang secara sewenang-wenang memodifikasi riwayat commit sepenuhnya mungkin terdengar aneh bagi orang yang terbiasa dengan Subversion atau TFVC, karena semua orang terbiasa terhubung secara terpusat ke server kontrol versi, menggunakan repositori terpusat. Jika seseorang dapat secara sewenang-wenang mengubah catatan historis, apakah itu masih dapat disebut kontrol versi?

Sebenarnya, dalam kontrol versi Git, konsepnya sama. Selama repositori yang sama dibagikan oleh banyak orang, jika seseorang secara sewenang-wenang mengubah versi, kontrol versi Git juga akan gagal bekerja dengan baik.

Jadi, skenario penggunaan apa yang memerlukan modifikasi catatan versi? Anda dapat merujuk ke poin-poin berikut.

Asumsikan kita sekarang memiliki tiga versi [A] -> [B] -> [C]:

* Anda mungkin menemukan bahwa versi [C] di-commit secara tidak benar dan harus menghapus semua perubahan dalam versi ini
* Anda mungkin menemukan setelah melakukan commit [C] bahwa versi ini hanya berisi kode pengujian, dan Anda ingin menghapusnya
* Beberapa pesan catatan versi memiliki kesalahan ketik, dan Anda ingin memodifikasi teks pesan tanpa memengaruhi riwayat perubahan file
* Anda mungkin ingin menyesuaikan urutan commit versi-versi ini menjadi [A] -> [C] -> [B] agar evolusi versi lebih logis
* Anda menemukan bahwa versi [B] lupa menyertakan file penting sebelum melakukan commit, dan Anda ingin memperbaiki perubahan ini sesudahnya
* Ketika Anda berencana untuk "berbagi" sebuah branch, Anda menemukan cacat kode dan dapat memperbaikinya sebelum berbagi

## Catatan Penting untuk Memperbaiki Riwayat Commit

Git mempertahankan mekanisme untuk "memodifikasi catatan riwayat versi", terutama berharap bahwa setelah Anda "mengelola versi sendiri" sampai tingkat tertentu, Anda dapat mengatur berbagai informasi dalam catatan versi sendiri, sehingga setelah Anda "menerbitkan" versi-versi tersebut, orang lain dapat lebih jelas memahami modifikasi apa yang Anda buat pada versi-versi ini.

Oleh karena itu, ketika memodifikasi catatan riwayat versi, beberapa hal harus mendapat perhatian khusus:

* Sebuah repositori dapat memiliki banyak branch (nama branch default adalah `master`)
* Unit minimum untuk berbagi kode sumber Git adalah berdasarkan "branch"
* Anda dapat secara sewenang-wenang memodifikasi versi pada sebuah branch, selama Anda belum "membagikannya" dengan orang lain
* **Setelah Anda "berbagi" branch tertentu dengan orang lain, jangan memodifikasi catatan riwayat versi yang "dibagikan" itu lagi!**

## Memahami git commit --amend

Opsi `--amend` memungkinkan Anda memodifikasi commit terbaru. Ini berguna ketika Anda:

* Ingin mengubah pesan commit
* Lupa menyertakan beberapa file
* Perlu memperbaiki kesalahan kecil pada commit terakhir

### Mengubah Pesan Commit Terakhir

```
git commit --amend -m "New commit message"
```

### Menambahkan File ke Commit Terakhir

```
# Make changes or add forgotten files
git add forgotten-file.txt

# Amend the commit
git commit --amend --no-edit
```

Flag `--no-edit` mempertahankan pesan commit yang ada.

### Amend Interaktif

Untuk mengedit pesan commit di editor Anda:

```
git commit --amend
```

Ini membuka editor yang telah Anda konfigurasikan di mana Anda dapat memodifikasi pesan commit.

## Memahami git reset

`git reset` adalah perintah yang kuat yang dapat:

* Menggerakkan penunjuk branch saat ini
* Memodifikasi area staging (indeks)
* Memodifikasi direktori kerja

Ada tiga mode reset:

1. **--soft**: Menggerakkan HEAD, menjaga area staging dan direktori kerja tidak berubah
2. **--mixed** (default): Menggerakkan HEAD, mereset area staging, menjaga direktori kerja tidak berubah
3. **--hard**: Menggerakkan HEAD, mereset area staging dan direktori kerja

## Soft Reset

Menggerakkan penunjuk branch tetapi menjaga perubahan Anda tetap berada di staging:

```
git reset --soft HEAD~1
```

Ini membatalkan commit terakhir tetapi meninggalkan perubahan Anda di area staging, siap untuk di-commit ulang.

## Mixed Reset

Menggerakkan penunjuk branch dan meng-unstage perubahan:

```
git reset HEAD~1
# or
git reset --mixed HEAD~1
```

Ini membatalkan commit terakhir dan meng-unstage perubahan, tetapi perubahan tetap berada di direktori kerja Anda.

## Hard Reset

Sepenuhnya membuang commit dan semua perubahan:

```
git reset --hard HEAD~1
```

**Peringatan**: Ini secara permanen membuang perubahan. Gunakan dengan hati-hati!

## Mereset ke Commit Tertentu

Anda dapat mereset ke commit mana pun:

```
# Using commit hash
git reset --hard a1b2c3d

# Using relative reference
git reset --soft HEAD~3
```

## Meng-unstage File

Untuk meng-unstage file tanpa kehilangan perubahan:

```
git reset HEAD file.txt
# or
git restore --staged file.txt
```

## Memulihkan dari Reset

Jika Anda mereset secara tidak sengaja, Anda biasanya dapat memulihkan menggunakan reflog:

```
git reflog
git reset --hard HEAD@{2}
```

## Reset vs Revert

Perbedaan penting:

* **reset**: Menulis ulang riwayat (gunakan untuk commit lokal yang belum di-push)
* **revert**: Membuat commit baru yang membatalkan perubahan (aman untuk riwayat bersama)

## Kasus Penggunaan Umum

### Membatalkan Commit Terakhir, Mempertahankan Perubahan

```
git reset HEAD~1
```

### Membatalkan Commit Terakhir, Membuang Perubahan

```
git reset --hard HEAD~1
```

### Memecah Satu Commit menjadi Beberapa

```
git reset HEAD~1
git add file1.txt
git commit -m "First part"
git add file2.txt
git commit -m "Second part"
```

### Mengubah Beberapa Commit Terakhir

```
git reset --soft HEAD~3
# Make changes
git commit -m "Combined commit"
```

## Peringatan dan Praktik Terbaik

1. **Jangan pernah mereset riwayat publik**: Jangan mereset commit yang telah di-push ke repositori bersama
2. **Gunakan --amend dengan hati-hati**: Hanya amend commit yang belum di-push
3. **Pertimbangkan alternatif**: Untuk riwayat bersama, gunakan `git revert` sebagai gantinya
4. **Periksa dua kali**: Terutama sebelum menggunakan `--hard`
5. **Ketahui reflog Anda**: Ini dapat menyelamatkan Anda dari kesalahan

## Ringkasan Hari Ini

`git commit --amend` dan `git reset` adalah alat yang kuat untuk memperbaiki riwayat commit lokal. `--amend` sempurna untuk perbaikan cepat pada commit terakhir, sedangkan `reset` memberi Anda lebih banyak kendali atas beberapa commit. Namun, keduanya harus digunakan dengan hati-hati, terutama untuk commit yang telah dibagikan dengan orang lain.

Izinkan saya menyusun kembali perintah dan parameter Git yang dipelajari hari ini:

* git commit --amend
* git commit --amend --no-edit
* git reset --soft
* git reset --mixed
* git reset --hard
* git reset HEAD~n
* git reflog
