# Hari 01: Memahami Kontrol Versi Git

Saya telah menggunakan Subversion (SVN) selama hampir 10 tahun dan tidak pernah merasa perlu beralih ke platform kontrol versi lain, hingga beberapa tahun yang lalu, ketika saya secara bertahap memperkenalkan kontrol versi TFS (TFS Service) sebagai respons terhadap perubahan berbasis cloud. Transisi tersebut berjalan mulus karena SVN dan TFS memiliki konsep kontrol versi yang mirip, keduanya merupakan sistem kontrol versi terpusat. Sistem kontrol versi terpusat ini sederhana, intuitif, dan mudah dalam pengelolaan izin. Sejujurnya, dalam sebagian besar skenario pengembangan, Subversion atau TFS sudah cukup memadai. Lalu kesempatan atau kebutuhan apa yang memaksa kami beralih ke kontrol versi Git? Saya percaya setiap orang memiliki alasannya sendiri untuk mengadopsi Git — ada yang menganggapnya menyenangkan, ada yang menganggapnya baru, dan ada yang menganggapnya kuat. Apa pun itu, selama alasan tersebut mendukung Anda untuk secara aktif mempelajari teknologi yang belum dikenal, itu baik. Artikel ini tidak hanya akan memperkenalkan mekanisme kontrol versi Git kepada Anda, tetapi juga berbagi alasan saya ingin beralih ke Git.

## Tujuan Artikel

Dalam bidang pengembangan perangkat lunak, kontrol versi kode sumber sangatlah penting. Berbeda dengan sistem kontrol versi terpusat seperti Subversion atau TFVC (Team Foundation Version Control), Git adalah sistem kontrol versi terdistribusi (DVCS; Distributed Version Control System) yang membawa banyak keunggulan pada kontrol versi dan mengatasi kekurangan kontrol versi terpusat tradisional, seperti dukungan untuk operasi lokal, pencadangan yang mudah, branching dan merging yang kuat dan fleksibel, dan banyak lagi. Namun, karena kontrol versi Git sangat berbeda dari alat kontrol versi terpusat tradisional, baik dalam konsep kontrol versi maupun penggunaan alatnya, hal ini menimbulkan kurva pembelajaran yang cukup tinggi.

Meskipun tema artikel ini adalah "Kuasai Git dalam 30 Hari," sejujurnya, ini agak berlebihan karena Git sangat luas dan mendalam dengan banyak detail untuk dijelajahi. Jika Anda benar-benar ingin menerapkannya dalam pekerjaan, berapa hari pembelajaran yang dibutuhkan untuk benar-benar menguasainya? Belajar sedikit setiap hari selama 30 hari berturut-turut tampaknya merupakan jumlah yang masuk akal (atau terlalu banyak?). Jika ada alat yang harus digunakan semua orang dan harus segera dikuasai, dan jika Anda masih belum tahu cara menggunakannya secara fleksibel setelah belajar selama 30 hari, maka kurva pembelajarannya terlalu tinggi. Oleh karena itu, saya pikir fokus utama dari seri artikel ini adalah "cara mempelajari kontrol versi Git dalam 30 hari dan harus dapat menerapkannya dengan mahir dalam pekerjaan pengembangan praktis." Inilah tujuan sebenarnya dari seri ini. Saya tidak akan secara khusus menekankan detail-detail yang membosankan itu, tetapi selalu ada beberapa konsep dan detail penting yang tidak boleh dilewatkan. Saya akan berusaha menyebutkannya dalam setiap topik dan menjelajahinya secara mendalam ketika ada kesempatan. Saya berharap semua orang dapat belajar sambil mempraktikkan dan merasakan secara mendalam pesona kuat dari kontrol versi Git.

## Kesempatan untuk Beralih

Dalam beberapa bulan terakhir, perusahaan kami memiliki proyek besar dengan lebih dari 12 pengembang yang berpartisipasi. Semua orang akhirnya memutuskan untuk mengadopsi Git sebagai mekanisme kontrol versi untuk proyek ini. Daripada mengatakan kami mengadopsi kontrol versi Git, alasan sebenarnya dari adopsi ini adalah "kami memilih untuk menggunakan GitHub sebagai platform kontrol versi kami" karena platform GitHub benar-benar terintegrasi dengan baik, dengan dukungan kontrol versi Git yang lengkap, pelacakan dan pengelolaan isu, pengelolaan dokumen Wiki secara online, dan antarmuka peninjauan kode sumber yang ramah pengguna. Fitur-fitur ini dapat secara efektif membantu kami mengurangi masalah komunikasi tim selama pengembangan kolaboratif banyak orang.

Memulai dengan Git cukup sulit karena konsep kontrol versi Git sangat berbeda dari Subversion sehingga sulit untuk memahami perbedaannya secara intuitif. Bahkan jika Anda diberi alat antarmuka grafis GUI, Anda belum tentu tahu cara menggunakannya. Anda tahu, ketika Anda memiliki alat yang kuat dan berguna di tangan Anda, "menggunakannya secara tidak benar" lebih mengerikan daripada "tidak tahu cara menggunakannya"! Sederhananya, Anda harus terlebih dahulu membangun pola pikir, memahami prinsip kerja Git, dan kemudian mulai menggunakan alat terkait Git (baik alat baris perintah maupun alat antarmuka grafis). Inilah cara yang benar!

## Metode Pembelajaran

Ketika pertama kali mempelajari Git, saya membaca beberapa buku (sebenarnya memilih poin-poin penting), juga membaca banyak artikel dan presentasi online, dan bahkan menonton beberapa video tutorial. Dengan menonton dan belajar, saya memang dapat mempelajari cara menggunakan alat Git, dan saya tidak merasa itu terlalu sulit. Namun, Git memiliki banyak perintah dan parameter, benar-benar di luar jangkauan ingatan otak. Kecuali Anda menggunakannya setiap hari, bagaimana mungkin Anda mengetik perintah untuk kontrol versi sepanjang hari? Jika Anda harus membuka buku setiap kali ingin menggunakan perintah Git, itu terlalu tidak efisien. Pada saat itu, saya secara intuitif berpikir bahwa mempelajari Git pada akhirnya harus kembali ke alat GUI yang berguna; jika tidak, hal ini mungkin tidak mudah dipromosikan dalam tim.

Selain itu, karena Git adalah mekanisme "kontrol versi terdistribusi," ketika jumlah pengembang mulai bertambah dan setiap orang mulai memiliki salinan repositori mereka sendiri, semua orang menderita selama proses branching dan merging banyak orang yang pertama, dan itu berlangsung cukup lama. Meskipun ada berbagi teknis di dalam perusahaan, karena semua orang belajar untuk pertama kalinya, konsep-konsep abstrak Git tersebut tidak dapat berakar dalam di hati orang-orang. Mereka hanya dapat berbagi berdasarkan metode penggunaan Git, seperti cara menggunakan alat, apa saja perintah yang umum digunakan, perintah apa yang harus digunakan dalam situasi khusus, dan sebagainya. Bahkan jika prinsip-prinsip yang kompleks dijelaskan selama proses tersebut, karena pemahaman semua orang tentang Git masih samar, pemahaman orang yang berbeda tentang metode kontrol versi Git tidaklah sama, dan pengetahuan serta konsep yang diserap belum tentu konsisten. Jadi bahkan setelah kursus, semua orang masih membutuhkan beberapa hari untuk terus beradaptasi, berdiskusi satu sama lain, dan memecahkan masalah bersama. Jika hanya Anda yang menggunakan Git, sangat sulit untuk merasakan manfaat yang dibawa Git, dan Anda mungkin tidak dapat bertahan.

Oleh karena itu, saya pikir untuk mempelajari kontrol versi Git dengan baik, mungkin akan lebih mudah mempelajarinya jika Anda mengetahui poin-poin berikut terlebih dahulu:

* Pertama, miliki konsep dasar Git. Belajar melalui perintah adalah cara tercepat. Jangan lewatkan bagian ini.
* Cari lebih banyak orang untuk mempelajari kontrol versi Git bersama Anda, sebaiknya gunakan langsung dalam pekerjaan pengembangan praktis.
* Sebaiknya ada beberapa pasukan pelopor dalam tim yang dapat mempelajari lebih banyak konsep Git untuk dibagikan kepada orang lain atau memberikan bantuan tepat waktu ketika seseorang mengalami kesulitan.
* Pahami bahwa Git adalah "kontrol versi terdistribusi," dan setiap orang memiliki repositori yang lengkap, jadi Anda harus sering menggabungkan (merge) file.
* Saat menggunakan Git, branching dan merging adalah hal yang normal, tetapi setiap kali ada merge, akan ada konflik. Pelajari cara menyelesaikan konflik.

## Memahami Kontrol Versi Git

Git berasal dari Linus Torvalds, bapak Linux, ketika ia sedang mengembangkan kernel Linux. Karena metode kontrol versi awal sangat tidak efisien dan terpusat, banyak masalah muncul ketika mengelola kontrol versi untuk proyek yang kompleks dan besar seperti kernel Linux. Kernel Linux paling awal menggunakan BitKeeper untuk kontrol versi, tetapi kemudian Linus Torvalds merancang sistem kontrol versi Git yang lebih baik berdasarkan pengalamannya dengan BitKeeper dan Monotone. Awalnya, Git hanya dirancang sebagai alat kontrol versi tingkat rendah untuk digunakan sebagai alat operasional bagi sistem kontrol versi lain (SCM), dan kemudian secara bertahap berkembang menjadi sistem kontrol versi yang lengkap.

Menariknya, ketika Linus Torvalds pertama kali beralih ke Git untuk kontrol versi, Git terlalu kompleks, dan banyak konsep kontrol versi terlalu berbeda dari sebelumnya, yang juga mendapat tentangan dari komunitas open source di seluruh dunia. Namun, setelah bertahun-tahun berusaha dan berkembang, alat untuk mengoperasikan Git menjadi semakin matang, dan secara bertahap meredakan tentangan tersebut. Menurut riset pasar pada tahun 2013, 30% proyek open source di seluruh dunia telah beralih ke Git untuk kontrol versi. Ini adalah pangsa pasar yang luar biasa, yang berarti Git pasti memiliki fitur-fitur yang menakjubkan, dan perlu dipelajari dengan baik!

Berbicara tentang arsitektur Git, arsitektur ini sepenuhnya didasarkan pada pengalaman Linus Torvalds dalam memelihara proyek besar seperti kernel Linux dan pengalamannya yang kaya dalam optimasi sistem file. Karena itu, Git mencakup desain-desain penting berikut:

* Dukungan kuat untuk model pengembangan non-linear (model pengembangan terdistribusi)
  * Git memiliki mekanisme branching dan merging yang cepat, termasuk alat grafis untuk menampilkan jalur historis perubahan versi.
  * Git sangat menekankan branching dan merging, jadi dalam proses kontrol versi, Anda akan terus-menerus melakukan operasi branching dan merging.
  * Mekanisme branching Git sangat ringan, tanpa beban. Setiap branch hanyalah sebuah pointer referensi ke commit tertentu.
* Model pengembangan terdistribusi
  * Setiap orang yang berpartisipasi dalam pengembangan Git akan memiliki riwayat pengembangan yang lengkap.
  * Ketika seorang pengembang pertama kali meng-clone repositori Git, itu sepenuhnya setara dengan "cadangan lengkap" dari repositori Git ini.
  * Semua file yang diubah dan catatan historis di seluruh repositori disimpan di repositori lokal.
* Kompatibel dengan sistem operasi yang ada
  * Repositori Git sebenarnya hanyalah sebuah folder dengan berbagai file konfigurasi terkait dan berbagai file objek blob.
  * Repositori Git dapat diterbitkan dengan cara apa pun, jadi Anda dapat menggunakan HTTP, FTP, rsync, SSH, atau bahkan protokol Git sebagai media untuk mengakses repositori Git, dengan kompatibilitas yang sangat tinggi.
* Penanganan proyek besar yang efisien
  * Karena repositori yang lengkap akan di-clone ke komputer lokal, dan repositori tersebut berisi file lengkap dan catatan perubahan versi, kecepatan berbagai operasi file dalam kontrol versi akan ratusan kali lebih cepat daripada akses remote langsung.
  * Ini juga berarti bahwa kontrol versi Git tidak akan melambat seiring proyek menjadi lebih besar dan file menjadi lebih banyak.
* Perlindungan catatan historis
  * Dalam proses kontrol versi Git, setiap commit menghasilkan nomor hash id, dan setiap versi dalam proses perubahan mengacu pada hash id ini. Selama hash id tidak dapat dicocokkan, Git tidak akan bekerja. Jadi seiring proyek menjadi lebih besar dan lebih banyak salinan repositori di-clone, Anda hampir tidak dapat mengubah isi file atau catatan versi.
  * **Ingat: Setiap orang memiliki repositori yang lengkap. Jika Anda mengubah yang asli, repositori semua orang tidak dapat lagi digabungkan kembali ke repositori asli, jadi Anda hampir tidak dapat mengubah catatan versi secara sembarangan.**
* Desain berbasis toolkit
  * Git dirancang sebagai serangkaian perangkat lunak alat (alat baris perintah). Anda dapat dengan mudah menggabungkan penggunaan alat yang berbeda dengan fleksibilitas yang besar.
* Strategi merge yang dapat dipasang (pluggable)
  * Git memiliki mekanisme "merge tidak lengkap" yang dirancang dengan baik dan berbagai algoritma yang dapat menyelesaikan merging, dan akhirnya memberi tahu pengguna mengapa merging otomatis tidak dapat diselesaikan atau memberi tahu Anda bahwa merging manual diperlukan.
* Mekanisme pengumpulan sampah pasif
  * Saat menggunakan Git, jika Anda ingin menghentikan operasi saat ini atau memulihkan operasi sebelumnya, itu mungkin dilakukan. Anda tidak perlu khawatir tentang kemungkinan menggunakan perintah yang salah atau perintah yang berhenti di tengah eksekusi.
  * Mekanisme pengumpulan sampah Git sebenarnya adalah file-file tidak berguna yang tertinggal di sistem file. Mekanisme pengumpulan sampah ini hanya akan dijalankan secara otomatis setelah objek-objek tidak berguna ini terakumulasi selama jangka waktu tertentu, atau Anda juga dapat mengeluarkan perintah untuk membersihkannya sendiri. Misalnya: git gc --prune
* Pemaketan objek secara berkala
  * "Objek" yang kami sebutkan di Git sebenarnya mewakili file dalam repositori. Dalam proses perubahan versi, kode atau file lain dalam proyek akan diperbarui. Setiap kali diperbarui, selama isi file berbeda, "objek" baru akan dibuat, dan semua file dengan isi berbeda ini akan dipertahankan.
  * Anda dapat membayangkan bahwa seiring proyek menjadi lebih besar dan memiliki lebih banyak versi, akan ada semakin banyak objek. Meskipun setiap file dapat dikompresi secara individual untuk membuat file lebih kecil, terlalu banyak file tetap akan membuat akses file semakin tidak efisien. Oleh karena itu, desain Git memiliki mekanisme yang dapat secara otomatis memaketkan sekelompok "objek" lama ke dalam packfile untuk meningkatkan efisiensi akses file.
  * File-file yang baru ditambahkan itu akan tetap ada sebagai file tunggal, yang juga berarti sebuah "file" dalam repositori Git adalah sebuah "objek" Git, tetapi perlu dipaketkan ulang sesekali.
  * Agaknya, Git akan secara otomatis melakukan tindakan seperti pemaketan ulang, tetapi Anda tetap dapat mengeluarkan perintah untuk menjalankannya sendiri. Misalnya: git gc
  * Jika Anda ingin memeriksa apakah sistem file yang dikelola oleh Git lengkap, Anda dapat menjalankan perintah berikut: git fsck

Mengenai sistem kontrol versi terdistribusi Git, izinkan saya menegaskan kembali beberapa hal:

* Git dapat sepenuhnya mengoperasikan kontrol versi tanpa dukungan sisi server karena setiap orang memiliki salinan repositori yang lengkap.
* Karena setiap orang memiliki salinan repositori yang lengkap, setiap kali Anda melakukan commit perubahan versi, Anda hanya melakukan commit ke repositori lokal, jadi kecepatan commit sangat cepat, dan Anda tidak memerlukan koneksi jaringan, yang dapat sangat menghemat waktu pengembangan.
* Karena setiap orang memiliki salinan repositori yang lengkap, ini berarti bahwa saat menggunakan kontrol versi Git, tidak ada yang namanya "kontrol izin." Setiap anggota dapat meng-clone repositori dan dapat melakukan commit perubahan secara lokal tanpa batasan izin apa pun. Saat menggunakan Git, satu-satunya izin yang dapat diatur adalah apakah Anda memiliki izin untuk mengakses repositori upstream atau repositori remote.
* Jika Anda perlu bertukar versi yang diubah dengan orang lain, Anda dapat melakukannya melalui "merging" kapan saja. Git memiliki kemampuan penelusuran merge yang sangat kuat.
* Untuk menggabungkan versi dari banyak orang, Anda hanya perlu memiliki izin atau akses ke repositori bersama.
  **Contohnya: Di server yang sama, Anda dapat berbagi melalui izin folder, atau mengakses repositori Git server lain dari jarak jauh melalui SSH, atau berbagi repositori Git melalui server web, dan lain-lain.**
