# Day 17: マージの基本概念と使い方

Day 08（ブランチの基本概念と使い方）で述べたように、私たちは「ブランチ」について学びました。次は「マージ」の実行方法について説明します。Git は分散型バージョン管理システム（DVCS）であるため、意図的なマージ（`git merge`）であれ、意図しないマージ（`git pull`）であれ、ブランチとマージの操作を絶えず行うことになります。要するに、「ブランチ」と「マージ」の操作は、Git を使ってバージョン管理を行う際に確かに頻繁に発生します。本記事では、「マージ」操作の基本概念と使い方を説明します。

## マージの概念を理解する

Git ワーキングディレクトリでブランチを作成すると、異なるニーズに応じて、互いに影響し合うことなく個別にシステムを開発できます。たとえば、もともと安定していたシステムを `master` ブランチに保持して開発し、エラーを修正する必要がある場合は、追加で `bugfix` ブランチを作成してソフトウェアエラーを修正できます。バグが修正された後、「マージ」を通じて `bugfix` ブランチの変更を `master` に再適用できます。これが主な使用シナリオの 1 つです。

一般的に、誰もがメインまたはデフォルトのブランチ（`master`）で開発し、ニーズに応じてブランチを作成し（`bugfix`）、最後に 2 つのブランチを 1 つにマージします。実際、「マージ」操作を行う際は、別のブランチを現在のブランチにマージし、その後、他のブランチを手動で削除します。これは「2 つのブランチを 1 つにマージする」という概念と一致します。

実務では、3 つ、4 つ、あるいはそれ以上のブランチを、そのうちの 1 つにマージする機会がよくあります。たとえば、メインブランチ（`master`）に加えて、デバッグ用のブランチ（`bugfix`）と機能追加用のブランチ（`feature`）を作成することもできます。ある程度開発が進んだら、これら両方のブランチをメインブランチ（`master`）にまとめてマージするかどうかを決めることができます。

Git でマージを使う際には、重要な概念があります。それは、**マージアクションは同じリポジトリ内で発生しなければならない**ということです。思い出してください。いかなる Git リポジトリにも Initial Commit オブジェクト（初期バージョン）が存在しなければならず、他のすべてのバージョンはこのバージョンに関連します。この関係を「ブランチの先端で追跡されるオブジェクト」と呼びます。そのため、あるリポジトリの特定のブランチを、まったく無関係な別のリポジトリのブランチにマージすることはできません。

マージの際、2 つのブランチが同じファイルを変更していても、変更した行が異なる限り、Git は自動的にこの 2 つの変更を適用／マージしてくれます。しかし、たまたま両方のブランチで「同じファイル」の「同じ行」を変更していた場合、マージ中に競合イベントが発生します。マージ競合が発生すると、Git は何も判断せず、「競合の解決」という作業を「あなた」に委ねます。そして、これらの競合ファイルはすべて `unmerged` ステータスでマークされます。マージ競合の後は、`git status` コマンドを使ってこれらのステータスを確認できます。

## マージの種類

Git には主に 2 種類のマージがあります。

1. **Fast-forward マージ**：ターゲットブランチがソースブランチから分岐していない場合に使われます
2. **Three-way マージ**：両方のブランチに新しいコミットがある場合に使われます

## Fast-forward マージ

Fast-forward マージは、現在のブランチがマージされるブランチから分岐していない場合に発生します。Git は単にブランチポインタを前方に移動させます。

```
# On master branch
git merge feature-branch
```

`feature-branch` が作成されて以来 `master` に新しいコミットがなければ、Git は Fast-forward マージを実行します。

## Three-way マージ

両方のブランチに新しいコミットがある場合、Git は Three-way マージを実行し、両方のブランチの変更を組み合わせた新しいマージコミットを作成します。

```
# On master branch
git merge feature-branch
```

これにより、2 つの親コミットを持つ新しいコミットが作成されます。

## Fast-forward を防ぐ

Fast-forward が可能な場合でも、ブランチ履歴を保持したいことがあります。

```
git merge --no-ff feature-branch
```

これにより、Fast-forward マージの場合でも、常にマージコミットが作成されます。

## マージ競合

競合は、マージされる 2 つのブランチで同じファイルの同じ行が異なる方法で変更された場合に発生します。この場合、以下のようになります。

1. Git はマージを一時停止します
2. 競合しているファイルをマークします
3. ファイルに競合マーカーを追加します
4. あなたが競合を解決するのを待ちます

## 競合しているファイルを表示する

どのファイルに競合があるかを確認するには、以下を使います。

```
git status
```

競合のあるファイルは「both modified」として一覧表示されます。

## 競合マーカー

Git は競合しているファイルにマーカーを追加します。

```
<<<<<<< HEAD
Your changes
=======
Their changes
>>>>>>> branch-name
```

* `<<<<<<< HEAD`：自分の変更の開始をマークします
* `=======`：2 つのバージョンを区切ります
* `>>>>>>> branch-name`：取り込まれる変更の終了をマークします

## 競合を解決する

競合を解決するには、以下の手順を行います。

1. 競合しているファイルを開きます
2. 競合マーカーを探します
3. ファイルを編集して競合を解決します
4. 競合マーカーを削除します
5. 解決したファイルをステージします：`git add <file>`
6. マージを完了します：`git commit`

## マージを中止する

進行中のマージを取り消したい場合は、以下を使います。

```
git merge --abort
```

これにより、リポジトリはマージ開始前の状態に戻ります。

## マージ履歴を表示する

履歴内のマージコミットを見るには、以下を使います。

```
git log --oneline --graph --all
```

これにより、ブランチとマージの履歴が視覚的に表示されます。

## マージ戦略

Git はさまざまなマージ戦略をサポートしています。

* **recursive**（デフォルト）：デフォルトの Three-way マージ戦略
* **ours**：競合の際は常に自分のバージョンを優先します
* **theirs**：競合の際は常に相手のバージョンを優先します

```
git merge -X ours branch-name
git merge -X theirs branch-name
```

## ベストプラクティス

1. マージの前に**作業をコミットする**
2. マージの前にリモートから**最新の変更を取得する**
3. 共有ブランチにプッシュする前に**マージをテストする**
4. マージについてチームと**コミュニケーションを取る**
5. 可能な場合は**マージを小さく保つ**

## 本日のまとめ

マージは基本的な Git 操作であり、異なるブランチの作業を組み合わせることができます。マージの仕組み、特に競合の扱い方を理解することは、効果的なコラボレーションに不可欠です。定期的にマージを練習して、このプロセスに慣れましょう。

本日学んだ Git コマンドとパラメータを整理しておきます。

* git merge
* git merge --no-ff
* git merge --abort
* git merge -X ours
* git merge -X theirs
* git log --graph
* git status
