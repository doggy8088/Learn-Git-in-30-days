# Day 27: 同じリモートリポジトリでブランチを使ってバージョン管理する

チームによって、ブランチ戦略は異なります。本記事では、一般的なブランチモデルと、それぞれをいつ使うべきかを探ります。

## ブランチ戦略が重要な理由

明確な戦略がないと、以下の問題が生じます。
* コードの競合が増えます
* リリースが混乱します
* バグが本番環境に紛れ込みます
* チームの調整がうまくいきません

## GitHub Flow

**適している対象**：Web アプリケーション、継続的デプロイ

### 戦略

* main ブランチは 1 つだけ：`main`
* すべての変更に機能ブランチを使います
* `main` からデプロイします

### ワークフロー

```
1. Create branch from main
   git checkout -b feature-name

2. Work and commit
   git commit -am "Add feature"

3. Push and create PR
   git push origin feature-name

4. Review and discuss

5. Deploy from branch (staging)

6. Merge to main
   # On GitHub: Merge PR

7. Deploy from main (production)
```

### 長所
* シンプルで分かりやすいです
* 開発のペースが速くなります
* main は常にデプロイ可能です
* 継続的デプロイに最適です

### 短所
* 長期的なリリースサポートがありません
* 優れた CI/CD が必要です
* 複数のバージョンには不向きです

## Git Flow

**適している対象**：リリースのあるソフトウェア、複数のバージョン

### ブランチの種類

* **main**：本番環境に対応できるコード
* **develop**：統合ブランチ
* **feature/**：新機能
* **release/**：リリース準備
* **hotfix/**：緊急修正

### ワークフロー

```
# Start new feature
git checkout -b feature/login develop

# Work on feature
git commit -am "Implement login"

# Finish feature
git checkout develop
git merge --no-ff feature/login
git branch -d feature/login

# Start release
git checkout -b release/1.0 develop

# Prepare release (bug fixes only)
git commit -am "Bump version to 1.0"

# Finish release
git checkout main
git merge --no-ff release/1.0
git tag -a 1.0

git checkout develop
git merge --no-ff release/1.0
git branch -d release/1.0

# Hotfix
git checkout -b hotfix/1.0.1 main
git commit -am "Fix critical bug"

git checkout main
git merge --no-ff hotfix/1.0.1
git tag -a 1.0.1

git checkout develop
git merge --no-ff hotfix/1.0.1
git branch -d hotfix/1.0.1
```

### 長所
* 関心事が明確に分離されます
* 複数のバージョンをサポートします
* 構造化されたリリースプロセスです

### 短所
* より複雑です
* 開発サイクルが遅くなります
* シンプルなプロジェクトには過剰です

## GitLab Flow

**適している対象**：ステージング環境と本番環境を持つ組織

### 戦略

* 環境ブランチ：`main`、`staging`、`production`
* 機能ブランチは `main` にマージします
* 環境を通じて昇格させます

### ワークフロー

```
# Feature development
git checkout -b feature-name main
# Work and commit
git push origin feature-name
# Create MR to main

# After merge to main
# Deploy to staging
git checkout staging
git merge main
git push origin staging

# After testing in staging
# Deploy to production
git checkout production
git merge staging
git push origin production
```

### 長所
* 環境ベースのデプロイです
* 昇格のパスが明確です
* 規制の厳しい業界に適しています

### 短所
* 管理するブランチが増えます
* 自動化が必要です
* 遅くなる場合があります

## トランクベース開発

**適している対象**：高パフォーマンスなチーム、継続的デプロイ

### 戦略

* 単一のトランク：`main`
* 非常に短命な機能ブランチ（1 日未満）
* 未完成の機能にはフィーチャーフラグを使います

### ワークフロー

```
# Create short-lived branch
git checkout -b quick-fix main

# Make small change
git commit -am "Fix button color"

# Merge same day
git checkout main
git merge quick-fix
git push origin main

# Or commit directly to main
# (with CI and feature flags)
```

### 長所
* 最速の統合です
* マージ競合が減ります
* CI/CD を促進します
* コード品質が高くなります

### 短所
* 規律が必要です
* 優れた CI/CD が必要です
* フィーチャーフラグの複雑さがあります

## Release Flow（Microsoft）

**適している対象**：エンタープライズソフトウェア、計画的なリリース

### 戦略

* `main`：常にリリース可能な状態
* `release/*`：安定化ブランチ
* トピックブランチ：短命な機能ブランチ

### ワークフロー

```
# Create topic branch
git checkout -b users/name/feature main

# Work and create PR
git push origin users/name/feature

# Create release branch
git checkout -b release/v2.0 main

# Cherry-pick into release
git cherry-pick <commit-hash>

# Release
git checkout main
git merge release/v2.0
git tag v2.0
```

### 長所
* リリーススケジュールが柔軟です
* 開発と安定化を並行して進められます
* エンタープライズに適しています

### 短所
* 複雑になる場合があります
* cherry-pick が必要です
* メンテナンスの負担が増えます

## 戦略の選び方

### GitHub Flow が適する場合：
* 継続的デプロイ
* Web アプリケーション
* 小規模なチーム
* 速いイテレーション

### Git Flow が適する場合：
* 定期的なリリース
* デスクトップ／モバイルアプリ
* 複数のバージョンをサポートする必要がある
* 従来型のソフトウェアライフサイクル

### GitLab Flow が適する場合：
* 複数の環境
* 段階的なデプロイ
* 規制要件

### トランクベースが適する場合：
* 経験豊富なチーム
* 優れた CI/CD
* 継続的デプロイ
* 高いリリース頻度

## ブランチの命名規則

### 機能ブランチ
```
feature/user-authentication
feature/dark-mode
feat/issue-123
```

### バグ修正ブランチ
```
fix/login-error
bugfix/issue-456
hotfix/critical-security-patch
```

### リリースブランチ
```
release/1.0
release/2.0.0
release/v1.5
```

### その他のブランチ
```
docs/update-readme
test/integration-tests
refactor/database-layer
chore/update-dependencies
```

## ブランチ管理コマンド

### ブランチを一覧表示する
```
# Local branches
git branch

# All branches (including remote)
git branch -a

# With last commit
git branch -v

# Merged branches
git branch --merged

# Unmerged branches
git branch --no-merged
```

### ブランチを削除する
```
# Delete local branch
git branch -d feature-name

# Force delete
git branch -D feature-name

# Delete remote branch
git push origin --delete feature-name
```

### ブランチ名を変更する
```
# Rename current branch
git branch -m new-name

# Rename other branch
git branch -m old-name new-name
```

## 本日のまとめ

適切なブランチ戦略の選択は、チーム、プロジェクト、デプロイモデルによって異なります。万能な解決策はありません。GitHub Flow のようなシンプルな戦略から始めて、必要に応じて進化させましょう。重要なのは一貫性とコミュニケーションです。

本日学んだ Git コマンドとパラメータを整理しておきます。

* git checkout -b branch-name
* git merge --no-ff
* git cherry-pick
* git branch -m
* git branch --merged
* git branch --no-merged
* git push origin --delete
