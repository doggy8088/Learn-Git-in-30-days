# Day 22: コミット済み履歴の修正 Part 4（rebase）

これまでに、バージョンを修正する 3 つの異なる方法について説明してきました。厳密に言えば、`git revert` と `git cherry-pick` は実際には「バージョン履歴の記録を修正する」ものではありません。これらは、コミット済みのバージョンを「再適用」したり「逆方向に適用」したりするものです。本記事では、コミット記録を変更するために実際に使われる Git の Rebase の仕組みを説明します。これは重要で強力な機能です。

## git rebase を理解する

Rebase は、Git の最も強力な機能の 1 つですが、潜在的に危険な機能でもあります。コミット履歴を書き換えて、よりクリーンで線形な履歴にできます。

Rebase とは、一連のコミットを新しいベースコミットへ移動したり結合したりする処理です。完全な履歴を保持するマージとは異なり、Rebase は履歴を書き換えて線形な進行を作り出します。

## 基本的な Rebase

基本的な Rebase の操作は以下のとおりです。

```
# On feature branch
git checkout feature-branch

# Rebase onto main
git rebase main
```

これにより、`feature-branch` のすべてのコミットが `main` の上に再生されます。

## Rebase の仕組み

Rebase を実行すると、以下の処理が行われます。

1. Git が自分のブランチと対象ブランチの共通の祖先を見つけます
2. その祖先以降の自分のブランチのすべてのコミットを保存します
3. 自分のブランチを対象ブランチの位置にリセットします
4. 保存したコミットを 1 つずつ再適用します

## Rebase と Merge の比較

**Merge**：
* 完全な履歴を保持します
* ブランチがいつ分岐しマージされたかを示します
* 共有ブランチに対して安全です
* マージコミットを作成します

**Rebase**：
* 線形な履歴を作成します
* よりクリーンで分かりやすくなります
* 履歴を書き換えます（共有ブランチに対しては危険です）
* マージコミットは作成されません

視覚的な比較は以下のとおりです。

```
# Before rebase
     C---D feature
    /
A---B---E---F main

# After git rebase main (on feature)
             C'---D' feature
            /
A---B---E---F main

# After git merge feature (on main)
     C---D 
    /     A---B---E---F---G main
```

## Rebase 中の競合を処理する

競合が発生した場合は、以下のようにします。

```
# Git pauses the rebase
# Resolve conflicts in the files
# Stage the resolved files
git add <resolved-files>

# Continue the rebase
git rebase --continue
```

Rebase を中止するには、以下を使います。

```
git rebase --abort
```

現在のコミットをスキップするには、以下を使います。

```
git rebase --skip
```

## インタラクティブ Rebase

インタラクティブ Rebase を使うと、コミットを完全に制御できます。

```
git rebase -i HEAD~3
```

これによりエディタが開き、以下の操作ができます。

* **pick**：コミットをそのまま保持します
* **reword**：コミットメッセージを変更します
* **edit**：コミットを修正するために停止します
* **squash**：前のコミットと結合し、両方のメッセージを保持します
* **fixup**：前のコミットと結合し、このメッセージは破棄します
* **drop**：コミットを完全に削除します

インタラクティブ Rebase のエディタの例は以下のとおりです。

```
pick abc123 Add feature A
reword def456 Add feature B
squash ghi789 Fix typo in feature B
drop jkl012 Experimental change
```

## よくあるインタラクティブ Rebase の作業

### コミットをスカッシュする

複数のコミットを 1 つに結合します。

```
git rebase -i HEAD~3

# In the editor, change:
pick abc123 First commit
pick def456 Second commit
pick ghi789 Third commit

# To:
pick abc123 First commit
squash def456 Second commit
squash ghi789 Third commit
```

### コミットを並べ替える

インタラクティブ Rebase のエディタで行の順序を入れ替えるだけです。

### コミットを編集する

```
git rebase -i HEAD~3

# Change "pick" to "edit" for the commit you want to modify
# Git will stop at that commit
# Make your changes
git add .
git commit --amend
git rebase --continue
```

## 別のブランチへの Rebase

```
git rebase --onto new-base old-base feature-branch
```

これにより、`old-base` より後にある `feature-branch` のコミットが `new-base` の上に移動します。

## Autosquash

fixup コミットを自動的にスカッシュします。

```
# Create a fixup commit
git commit --fixup <commit-to-fix>

# Later, rebase with autosquash
git rebase -i --autosquash main
```

## Rebase の黄金律

**共有リポジトリにプッシュされたコミットは、決して Rebase してはいけません！**

Rebase は履歴を書き換えるため、それらのコミットをベースに作業している他の人に大きな問題を引き起こす可能性があります。

安全な場合：
* まだプッシュしていないローカルコミット
* 自分が所有する機能ブランチ
* プルリクエストを作成する前の整理

危険な場合：
* Main／master ブランチ
* 共有している機能ブランチ
* 他の人がベースにしている可能性のあるすべてのコミット

## Rebase のミスから復旧する

Rebase がうまくいかなかった場合は、以下のようにします。

```
# Find the commit before the rebase
git reflog

# Reset to that commit
git reset --hard HEAD@{2}
```

## ベストプラクティス

1. **プッシュする前に Rebase する**：共有する前にローカルコミットを整理します
2. **公開履歴を Rebase しない**：Rebase するのはローカルコミットだけにします
3. **大規模な Rebase の前にバックアップする**：まずブランチを作成します
4. **コミュニケーションを取る**：共有コードを Rebase しなければならない場合はチームに知らせます
5. **練習する**：まず使い捨てのブランチで Rebase を試してみます

## 本日のまとめ

Rebase は、クリーンで線形なコミット履歴を作成するための強力なツールです。ローカル作業やマージに向けたブランチの準備には優れていますが、共有履歴を書き換えないよう慎重に使う必要があります。Rebase をいつ、どのように使うかを理解することは、高度な Git ワークフローに不可欠です。

本日学んだ Git コマンドとパラメータを整理しておきます。

* git rebase
* git rebase main
* git rebase -i
* git rebase --continue
* git rebase --abort
* git rebase --skip
* git rebase --onto
* git rebase --autosquash
* git commit --fixup
