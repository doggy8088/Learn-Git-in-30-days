# Day 18: コミット済み履歴の修正 Part 1（reset と amend）

Git を使ってバージョン管理を行う際、私たちは `git commit` を使って多くのバージョンを作成します。Git は分散型バージョン管理システムであるため、Subversion や TFVC のような集中型バージョン管理システムと比べて、Git はバージョン管理における権限設計が少なくなっています。Git は「バージョン記録を変更する」ための仕組みをより多く提供しており、バージョンを他の人と「共有」する前に事前に整理することができます。

## バージョン管理の基本原則

Git、Subversion、TFVC のいずれを使う場合でも、バージョン管理を行う際、良好なバージョン記録を維持することで、各バージョンの更新履歴を追跡するのに役立ちます（必要な場合に）。私自身の経験では、プロジェクトにおいてソフトウェア開発プロセスを追跡する機会や意欲はめったにありません。私たちのプロジェクトの多くは数千ものバージョン記録を蓄積しています。その履歴を調べる時間など誰にあるでしょうか。

しかし実際には、ソフトウェアのバグが発生した際、そのバグの本当の原因を突き止めるために、特定のバグの履歴記録を追跡する必要があります。このときにこそ、バージョン管理が最大の価値をもたらします。

したがって、良好な「バージョン記録」をどのように維持するかも非常に重要です。いくつかの管理原則を共有します。

* 小さな機能変更ごとにバージョンを作成し、変更を追跡しやすくする
* 多くの変更を蓄積してから「大きなバージョン」を作成することは決してしない
* 機能を論理的かつ順序立てて修正し、関連するバージョン修正が順番にコミットされるようにして、追跡しやすくする

しかし、人間は間違いを犯すものです。チームの全員が常に上記の原則に従ってバージョン管理を行えると、誰が保証できるでしょうか。誰もが「思いついたら変更する」のではないでしょうか。このような要求は非現実的になってしまいます。したがって、バージョンがリモートサーバーに提出される際にはすでに完璧な状態になっているよう、「バージョンを変更する」仕組みが必要です。

## コミット履歴を修正する理由

これまでのところ、「リモートリポジトリ」の詳細には触れていないため、ほとんどの Git 操作は依然としてローカル操作、すなわちワーキングディレクトリでのバージョン管理に焦点を当てており、このリポジトリはあなたの `.git/` ディレクトリにあります。しかし、まもなく「リモートリポジトリ」の応用について説明します。その際は複数人がリポジトリを持つことになり、より多くの詳細に注意が必要になります。

誰もが自由にコミット履歴を変更できるというのは、Subversion や TFVC に慣れた人には奇妙に聞こえるかもしれません。なぜなら、誰もが集中型リポジトリを使って、バージョン管理サーバーに集中的に接続することに慣れていたからです。誰かが履歴記録を自由に改ざんできるとしたら、それでもバージョン管理と呼べるでしょうか。

実際、Git のバージョン管理でも概念は同じです。同じリポジトリを複数人で共有する限り、誰かが自由にバージョンを改ざんすれば、Git のバージョン管理も正常に機能しなくなります。

では、どのような使用シナリオでバージョン記録の変更が必要になるのでしょうか。以下のポイントを参照してください。

現在、3 つのバージョン [A] -> [B] -> [C] があると仮定します。

* バージョン [C] が誤ってコミットされており、このバージョンのすべての変更を削除しなければならないことが分かる場合があります
* [C] をコミットした後、このバージョンにはテストコードしか含まれていないことに気づき、削除したい場合があります
* 一部のバージョン記録メッセージにタイプミスがあり、ファイル変更履歴に影響を与えずにメッセージテキストを変更したい場合があります
* バージョンの進化をより論理的にするため、これらのバージョンのコミット順序を [A] -> [C] -> [B] に調整したい場合があります
* バージョン [B] のコミット前に重要なファイルを含め忘れたことに気づき、後からこの変更を是正したい場合があります
* ブランチを「共有」しようとした際にコードの欠陥を発見し、共有前に修正できる場合があります

## コミット履歴を修正する際の重要な注意点

Git が「バージョン履歴記録を変更する」仕組みを保持しているのは、主に、あなたが「自己管理するバージョン」がある程度整った後、バージョン記録内のさまざまな情報を自分で整理できるようにし、バージョンを「公開」した後に、他の人がこれらのバージョンに対してあなたがどのような変更を加えたかをより明確に理解できるようにするためです。

したがって、バージョン履歴記録を変更する際には、いくつか特に注意すべきことがあります。

* リポジトリには多くのブランチを持つことができます（デフォルトのブランチ名は `master` です）
* Git ソースコードを共有する最小単位は「ブランチ」です
* ブランチ上のバージョンは、他の人と「共有」していない限り、自由に変更できます
* **特定のブランチを他の人と「共有」したら、その「共有された」バージョン履歴記録はもう変更しないでください！**

## git commit --amend を理解する

`--amend` オプションを使うと、最新のコミットを変更できます。これは以下の場合に便利です。

* コミットメッセージを変更したい場合
* 一部のファイルを含め忘れた場合
* 最新のコミットの小さなミスを修正する必要がある場合

### 最新のコミットメッセージを変更する

```
git commit --amend -m "New commit message"
```

### 最新のコミットにファイルを追加する

```
# Make changes or add forgotten files
git add forgotten-file.txt

# Amend the commit
git commit --amend --no-edit
```

`--no-edit` フラグは既存のコミットメッセージを保持します。

### 対話式の amend

エディタでコミットメッセージを編集するには、以下を使います。

```
git commit --amend
```

これにより、設定済みのエディタが開き、コミットメッセージを変更できます。

## git reset を理解する

`git reset` は強力なコマンドであり、以下のことができます。

* 現在のブランチポインタを移動する
* ステージングエリア（インデックス）を変更する
* ワーキングディレクトリを変更する

reset には 3 つのモードがあります。

1. **--soft**：HEAD を移動し、ステージングエリアとワーキングディレクトリは変更しません
2. **--mixed**（デフォルト）：HEAD を移動し、ステージングエリアをリセットし、ワーキングディレクトリは変更しません
3. **--hard**：HEAD を移動し、ステージングエリアとワーキングディレクトリをリセットします

## Soft リセット

ブランチポインタを移動しますが、変更はステージされたまま保持されます。

```
git reset --soft HEAD~1
```

これにより、最新のコミットが取り消されますが、変更はステージングエリアに残り、再コミットの準備ができた状態になります。

## Mixed リセット

ブランチポインタを移動し、変更のステージを取り消します。

```
git reset HEAD~1
# or
git reset --mixed HEAD~1
```

これにより、最新のコミットが取り消され、変更のステージも取り消されますが、変更はワーキングディレクトリに残ります。

## Hard リセット

コミットとすべての変更を完全に破棄します。

```
git reset --hard HEAD~1
```

**警告**：これは変更を永久に破棄します。慎重に使ってください！

## 特定のコミットへのリセット

任意のコミットにリセットできます。

```
# Using commit hash
git reset --hard a1b2c3d

# Using relative reference
git reset --soft HEAD~3
```

## ファイルのステージを取り消す

変更を失うことなくファイルのステージを取り消すには、以下を使います。

```
git reset HEAD file.txt
# or
git restore --staged file.txt
```

## リセットから復旧する

誤ってリセットした場合は、通常 reflog を使って復旧できます。

```
git reflog
git reset --hard HEAD@{2}
```

## reset と revert の違い

重要な区別は以下のとおりです。

* **reset**：履歴を書き換えます（ローカルの、プッシュされていないコミットに使います）
* **revert**：変更を取り消す新しいコミットを作成します（共有履歴に対して安全です）

## よくあるユースケース

### 最新のコミットを取り消し、変更を保持する

```
git reset HEAD~1
```

### 最新のコミットを取り消し、変更を破棄する

```
git reset --hard HEAD~1
```

### 1 つのコミットを複数に分割する

```
git reset HEAD~1
git add file1.txt
git commit -m "First part"
git add file2.txt
git commit -m "Second part"
```

### 最新のいくつかのコミットを変更する

```
git reset --soft HEAD~3
# Make changes
git commit -m "Combined commit"
```

## 警告とベストプラクティス

1. **公開履歴は決してリセットしない**：共有リポジトリにプッシュされたコミットはリセットしないでください
2. **--amend は慎重に使う**：プッシュされていないコミットのみを amend してください
3. **代替手段を検討する**：共有履歴については、代わりに `git revert` を使ってください
4. **二重に確認する**：特に `--hard` を使う前には確認してください
5. **reflog を把握しておく**：ミスからあなたを救ってくれます

## 本日のまとめ

`git commit --amend` と `git reset` は、ローカルのコミット履歴を修正するための強力なツールです。`--amend` は最新のコミットの素早い修正に最適であり、`reset` は複数のコミットに対するより細かな制御を可能にします。ただし、どちらも慎重に使うべきであり、特に他の人と共有されたコミットについては注意が必要です。

本日学んだ Git コマンドとパラメータを整理しておきます。

* git commit --amend
* git commit --amend --no-edit
* git reset --soft
* git reset --mixed
* git reset --hard
* git reset HEAD~n
* git reflog
