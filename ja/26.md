# Day 26: 同じリモートリポジトリで複数人が作業する

複数人が同じリポジトリで作業する場合、調整と Git ワークフローの理解が極めて重要になります。本記事では、チームコラボレーションのベストプラクティスとよくあるシナリオを探ります。

## チームコラボレーションにおける一般的な課題

1. **マージ競合**：複数人が同じファイルを編集すること
2. **ブランチの分岐**：ローカルとリモートの同期がずれること
3. **コミットの消失**：他の人の作業を誤って上書きすること
4. **コミュニケーションのギャップ**：他の人が何に取り組んでいるか分からないこと

## 基本的なチームワークフロー

### 日常のワークフロー

```
# Morning: Get latest changes
git pull origin main

# Create feature branch
git checkout -b feature-name

# Work and commit frequently
git add .
git commit -m "Progress on feature"

# Before finishing: update with latest main
git checkout main
git pull origin main
git checkout feature-name
git merge main

# Resolve any conflicts

# Push your branch
git push origin feature-name

# Create pull request for review
```

### 最新の状態を保つ

変更を定期的にフェッチします。

```
# Check what's changed
git fetch origin

# View remote changes
git log main..origin/main

# Merge if appropriate
git merge origin/main
```

## 同時作業を処理する

### シナリオ 1：同じファイル、異なる行

通常は自動的にマージされます。

```
git pull origin main
# If auto-merge succeeds, you're done!
```

### シナリオ 2：同じファイル、同じ行

手動での解決が必要です。

```
git pull origin main
# Conflict!

# Edit conflicting files
# Remove markers: <<<<<<<, =======, >>>>>>>
# Keep the correct changes

# Stage resolved files
git add resolved-file.txt

# Complete the merge
git commit
```

### シナリオ 3：誰かが Rebase した

ブランチが共有されている場合、大きな問題を引き起こす可能性があります。

```
# If someone rebased a shared branch
git fetch origin

# You need to rebase your work
git rebase origin/feature-branch

# Or start fresh
git reset --hard origin/feature-branch
```

## コードレビューのプロセス

### 良いプルリクエストを作成する

1. **分かりやすいタイトル**：「Add user authentication feature」
2. **詳細な説明**：
   * この PR は何をするものですか？
   * なぜこの変更が必要ですか？
   * どのようにテストしましたか？
3. **小さく保つ**：レビューしやすくなります
4. **1 つの PR につき 1 つの関心事**：機能と修正を混ぜないでください
5. **main で更新する**：クリーンにマージできることを確認します

### プルリクエストをレビューする

1. コードのロジックとスタイルを**確認する**
2. 可能であれば**ローカルでテストする**
3. **建設的なフィードバックを残す**
4. **承認する、または変更を要求する**
5. **準備ができたらマージする**

## チームの競合を解決する

### まずコミュニケーション

* **チームと話す**：多くの問題を未然に防げます
* **PR のコメントを使う**：質問したり、アプローチを議論したりします
* **決定を文書化する**：PR の説明やコメントを更新します

### 技術的な解決策

#### 競合を解決する

```
# Update your branch
git fetch origin
git merge origin/main

# Resolve conflicts in files
# Stage changes
git add .

# Complete merge
git commit
```

#### 中止してやり直す

```
# If resolution is too complex
git merge --abort

# Talk to the other developer
# Coordinate who makes what changes
```

## ブランチ保護ルール

GitHub では、重要なブランチを保護します。

1. **プルリクエストのレビューを必須にする**
2. **ステータスチェックを必須にする**（CI/CD）
3. **線形な履歴を強制する**
4. **管理者も対象に含める**

設定場所：Settings > Branches > Branch protection rules

## 継続的インテグレーション

CI を使って問題を早期に発見します。

```yaml
# Example .github/workflows/test.yml
name: Tests
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v2
      - run: npm install
      - run: npm test
```

## コミュニケーションツール

### コミットメッセージ

規約に従います。

```
<type>(<scope>): <subject>

<body>

<footer>
```

例：

```
feat(auth): add user login functionality

Implement JWT-based authentication with email and password.
Includes password hashing with bcrypt and token refresh.

Closes #123
```

### プルリクエストテンプレート

`.github/pull_request_template.md` を作成します。

```markdown
## Description
<!-- Describe your changes -->

## Type of Change
- [ ] Bug fix
- [ ] New feature
- [ ] Breaking change

## Testing
<!-- How was this tested? -->

## Checklist
- [ ] Tests pass
- [ ] Documentation updated
- [ ] No merge conflicts
```

## 大規模チームへの対応

### フィーチャーフラグ

まだ準備ができていないコードをデプロイします。

```javascript
if (featureFlags.newUI) {
  return <NewUI />;
} else {
  return <OldUI />;
}
```

### リリースブランチ

開発とリリースを分離します。

```
main (production)
├── release/v2.0
├── release/v1.9
└── develop (integration)
    ├── feature/login
    ├── feature/dashboard
    └── feature/reports
```

## ベストプラクティスのまとめ

1. **プッシュする前にプルする**：常に最新の変更を先に取得します
2. **頻繁にコミットする**：小さく論理的なコミットにします
3. **定期的にプッシュする**：作業を共有し、フィードバックを得ます
4. **ブランチを使う**：main を安定させます
5. **テストを書く**：他の人に影響する前に問題を発見します
6. **コードをレビューする**：互いに学び合います
7. **コミュニケーションを取る**：必要であれば過剰なくらいに
8. **文書化する**：README、Wiki、コメント
9. **忍耐強く**：競合は起こるものです。一緒に解決しましょう
10. **他の人を助ける**：チームの成功は自分の成功です

## 本日のまとめ

Git によるチームコラボレーションを成功させるには、技術的なスキルと良いコミュニケーションの両方が必要です。一般的なワークフローを理解し、競合に適切に対処し、プルリクエストや CI/CD などのツールを使うことで、チームがスムーズに協力できるようになります。

本日学んだ Git コマンドとパラメータを整理しておきます。

* git pull origin main
* git fetch origin
* git merge origin/main
* git rebase origin/branch
* git push origin branch
* git log main..origin/main
