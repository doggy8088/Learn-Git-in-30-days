# Day 01: Git バージョン管理を理解する

私は Subversion（SVN）をほぼ 10 年間使ってきましたが、他のバージョン管理プラットフォームに切り替える必要性を感じたことは一度もありませんでした。数年前、クラウド化の流れに対応して TFS のバージョン管理（TFS Service）を徐々に導入し始めたのが転機でした。SVN と TFS はバージョン管理の概念が似ており、どちらも集中型バージョン管理システムであるため、移行はスムーズでした。集中型バージョン管理システムはシンプルで直感的であり、権限管理も容易です。正直なところ、ほとんどの開発シナリオでは Subversion や TFS で十分です。では、どのような機会や要件が私たちを Git バージョン管理への移行へと駆り立てたのでしょうか。人それぞれ Git を採用する理由は異なると思います。面白いから、新鮮だから、強力だから。いずれにせよ、その理由が馴染みのない技術を積極的に学ぶ原動力になるなら、それは良いことです。本記事では、Git のバージョン管理の仕組みを紹介するだけでなく、私が Git に切り替えたいと思った理由も共有します。

## 本記事の目的

ソフトウェア開発の分野において、ソースコードのバージョン管理は非常に重要です。Subversion や TFVC（Team Foundation Version Control）のような集中型バージョン管理システムとは異なり、Git は分散型バージョン管理システム（DVCS; Distributed Version Control System）であり、バージョン管理に多くの利点をもたらし、ローカル操作のサポート、バックアップの容易さ、強力で柔軟なブランチとマージなど、従来の集中型バージョン管理の欠点を解決しています。しかし、Git のバージョン管理は、バージョン管理の概念とツールの使い方の両面で従来の集中型バージョン管理ツールと大きく異なるため、学習のハードルが高くなっています。

本記事のテーマは「30 日で Git をマスターする」ですが、正直なところ、これは少し大げさです。Git は奥が深く、探求すべき細部が数多くあります。実際に仕事で活用するには、何日学べば本当にマスターできるのでしょうか。30 日間連続で毎日少しずつ学ぶというのは、妥当な数字に思えます（あるいは多すぎるでしょうか？）。誰もが使わなければならず、すぐにマスターしなければならないツールがあるとして、30 日学んでも柔軟に使いこなせないようでは、学習のハードルが高すぎます。したがって、このシリーズの主眼は「30 日以内に Git バージョン管理を学び、実際の開発業務で熟練して活用できるようになること」だと考えています。これこそが本シリーズの真の目的です。退屈な細部を特に強調することはしませんが、見逃せない重要な概念や細部は常にあるものです。各トピックでいくつか触れ、機会があれば深く掘り下げていきます。実践しながら学び、Git バージョン管理の強力な魅力を深く体感していただければ幸いです。

## 移行のきっかけ

ここ数か月、当社では 12 名以上の開発者が参加する大規模なプロジェクトがありました。全員で話し合った結果、このプロジェクトのバージョン管理の仕組みとして Git を採用することに決めました。Git のバージョン管理を採用したというより、採用の本当の理由は「バージョン管理プラットフォームとして GitHub を使うことを選んだ」からです。GitHub プラットフォームは実によく統合されており、完全な Git バージョン管理のサポート、課題の追跡と管理、オンライン Wiki によるドキュメント管理、使いやすいソースコードレビューのインターフェースを備えています。これらの機能は、複数人での共同開発におけるチームのコミュニケーション問題を効果的に軽減してくれます。

Git の入門はかなり大変でした。Git のバージョン管理の概念は Subversion と大きく異なり、その違いを直感的に理解するのが難しいのです。GUI のグラフィカルツールのインターフェースを与えられても、必ずしも使い方が分かるとは限りません。強力で便利なツールを手にしているとき、「正しく使えないこと」は「使い方を知らないこと」よりも恐ろしいのです！簡単に言えば、まず考え方を確立し、Git の動作原理を理解してから、Git 関連のツール（コマンドラインツールでもグラフィカルインターフェースツールでも）を使い始めるべきです。これが正しいやり方です！

## 学習方法

Git を学び始めた当初、私はいくつかの書籍を読み（実際には要点を拾い読みしました）、多くのオンライン記事やプレゼンテーションを読み、チュートリアル動画もいくつか視聴しました。見て学ぶことで、確かに Git ツールの使い方は身につきましたし、それほど難しいとは思いませんでした。しかし、Git にはコマンドやパラメータが非常に多く、とても頭で記憶できる範囲を超えています。毎日使っているのでなければ、どうして一日中バージョン管理のコマンドを打ち続けられるでしょうか。Git コマンドを使いたいときに毎回本を調べなければならないのでは、効率が悪すぎます。そのとき私は直感的に、Git の学習は最終的に便利な GUI ツールに戻るべきだと考えました。さもなければ、チームに普及させるのは容易ではないかもしれません。

さらに、Git は「分散型バージョン管理」の仕組みであるため、開発者の数が増え始め、一人ひとりが自分のリポジトリのコピーを持つようになると、最初の複数人でのブランチとマージの過程では誰もが苦労し、それがかなりの期間続きます。社内で技術共有は行われましたが、全員が初めて学ぶ立場だったため、Git の抽象的な概念を深く心に刻むことはできませんでした。ツールの使い方、よく使うコマンド、特殊な状況で使うべきコマンドなど、Git の使用方法に基づいた共有しかできませんでした。過程で複雑な原理が説明されても、全員の Git に対する理解がまだ曖昧だったため、Git のバージョン管理方法に対する理解は人によって異なり、吸収した知識や概念も必ずしも一致しませんでした。そのため、講習が終わった後も、全員が数日間かけて継続的に適応し、互いに議論し、共に問題を解決する必要がありました。自分一人だけが Git を使っている場合、Git がもたらすメリットを実感するのは本当に難しく、継続できないかもしれません。

したがって、Git バージョン管理をしっかり学ぶには、まず以下のポイントを知っておくと学びやすいのではないかと思います。

* 第一に、Git の基本概念を持つこと。コマンドを通じて学ぶのが最も速い方法です。この部分を飛ばさないでください。
* より多くの人と一緒に Git バージョン管理を学びましょう。できれば実際の開発業務で直接使うのが望ましいです。
* チームの中に、Git の概念をより深く学び、他の人と共有したり、誰かが行き詰まったときに及時に支援したりできる先遣隊が数名いるのが理想です。
* Git は「分散型バージョン管理」であり、全員が完全なリポジトリを持っていることを理解し、頻繁にファイルをマージしなければなりません。
* Git を使う際、ブランチとマージは日常茶飯事ですが、マージがあるところには必ずコンフリクト（競合）があります。コンフリクトの解決方法を学びましょう。

## Git バージョン管理を理解する

Git は、Linux の父である Linus Torvalds が Linux カーネルを開発していたときに生まれました。初期のバージョン管理方法は非常に非効率で集中型だったため、Linux カーネルのような複雑で大規模なプロジェクトのバージョン管理を扱う際に多くの問題が生じました。最初期の Linux カーネルは BitKeeper でバージョン管理を行っていましたが、その後 Linus Torvalds は BitKeeper と Monotone の経験をもとに、より優れた Git バージョン管理システムを設計しました。もともと Git は、他のバージョン管理システム（SCM）の操作ツールとして使われる低レベルのバージョン管理ツールとしてのみ設計されていましたが、後に徐々に完全なバージョン管理システムへと進化しました。

興味深いことに、Linus Torvalds が最初にバージョン管理を Git に切り替えたとき、Git はあまりに複雑で、多くのバージョン管理の概念も従来と大きく異なっていたため、世界中のオープンソースコミュニティから反対に遭いました。しかし、長年の努力と発展を経て、Git を操作するツールはますます成熟し、反対の声は徐々に収まっていきました。2013 年の市場調査によると、世界のオープンソースプロジェクトの 30% がバージョン管理を Git に切り替えています。これは驚くべき市場シェアであり、Git には間違いなく驚異的な特徴があり、しっかり研究する価値があることを意味します！

Git のアーキテクチャについて言えば、それは完全に Linus Torvalds が Linux カーネルのような大規模プロジェクトを保守してきた経験と、ファイルシステム最適化に関する豊富な経験に基づいています。そのため、Git には以下の重要な設計が含まれています。

* 非線形開発モデル（分散開発モデル）への強力なサポート
  * Git には高速なブランチとマージの仕組みがあり、バージョン変更の履歴パスを表示するグラフィカルツールも含まれます。
  * Git はブランチとマージを非常に重視しているため、バージョン管理の過程では絶えずブランチとマージの操作を行うことになります。
  * Git のブランチの仕組みは非常に軽量で負担がありません。各ブランチは、あるコミットへの参照ポインタにすぎません。
* 分散開発モデル
  * Git 開発に参加する全員が、完全な開発履歴を持ちます。
  * 開発者が初めて Git リポジトリをクローンするとき、それはその Git リポジトリの「完全なバックアップ」と完全に等価です。
  * リポジトリ全体の変更されたファイルと履歴記録はすべて、ローカルリポジトリに保存されます。
* 既存のオペレーティングシステムとの互換性
  * Git リポジトリは実際には、各種の関連設定ファイルと各種の blob オブジェクトファイルが入ったフォルダにすぎません。
  * Git リポジトリはあらゆる方法で公開できるため、HTTP、FTP、rsync、SSH、さらには Git プロトコルを、Git リポジトリにアクセスする媒体として使用でき、互換性が非常に高いです。
* 大規模プロジェクトの効率的な処理
  * 完全なリポジトリがローカルマシンにクローンされ、そのリポジトリには完全なファイルとバージョン変更記録が含まれているため、バージョン管理における各種ファイル操作の速度は、リモートに直接アクセスするよりも数百倍速くなります。
  * これは、プロジェクトが大きくなりファイルが増えても、Git のバージョン管理が遅くならないことも意味します。
* 履歴記録の保護
  * Git のバージョン管理の過程では、各コミットがハッシュ ID 番号を生成し、変更過程の各バージョンはこのハッシュ ID を参照します。ハッシュ ID が一致しない限り、Git は動作しません。そのため、プロジェクトが大きくなり、リポジトリのコピーがより多くクローンされるほど、ファイルの内容やバージョン記録を改ざんすることはほとんど不可能になります。
  * **覚えておいてください：全員が完全なリポジトリを持っています。元のリポジトリを変更してしまうと、全員のリポジトリを元のリポジトリにマージして戻すことができなくなるため、バージョン記録を勝手に改ざんすることはほぼ不可能です。**
* ツールキットベースの設計
  * Git は一連のツールソフトウェア（コマンドラインツール）として設計されています。異なるツールの使用を簡単に組み合わせることができ、柔軟性に優れています。
* プラグイン可能なマージ戦略
  * Git にはよく設計された「不完全なマージ」の仕組みと、マージを完了できる複数のアルゴリズムがあり、最終的に、自動マージが完了できない理由をユーザーに知らせるか、手動マージが必要であることを通知します。
* パッシブなガベージコレクションの仕組み
  * Git を使用しているとき、現在の操作を中断したり、前の操作を復元したりしたい場合は、それが可能です。間違ったコマンドを使ってしまったり、コマンドが実行途中でクラッシュしたりする心配はありません。
  * Git のガベージコレクションの仕組みは、実際にはファイルシステムに残された不要なファイルのことです。このガベージコレクションの仕組みは、それらの不要なオブジェクトがある期間蓄積した後にのみ自動的に実行されますが、自分でコマンドを発行してクリアすることもできます。例：git gc --prune
* オブジェクトの定期的なパッキング
  * Git で言う「オブジェクト」とは、実際にはリポジトリ内のファイルを表します。バージョン変更の過程では、プロジェクト内のコードやその他のファイルが更新されます。更新されるたびに、ファイルの内容が異なる限り、新しい「オブジェクト」が作成され、内容の異なるこれらのファイルはすべて保持されます。
  * プロジェクトが大きくなりバージョンが増えるにつれて、オブジェクトがますます増えていくことが想像できるでしょう。各ファイルを個別に圧縮して小さくすることはできますが、ファイルが多すぎるとファイルへのアクセス効率はどんどん低下します。そのため、Git の設計には、古い「オブジェクト」のグループを自動的に packfile にパッキングして、ファイルアクセスの効率を向上させる仕組みがあります。
  * 新しく追加されたファイルは依然として単一のファイルとして存在します。つまり、Git リポジトリ内の「ファイル」は Git の「オブジェクト」ですが、時々再パッキングする必要があります。
  * おそらく Git は再パッキングなどのアクションを自動的に実行しますが、自分でコマンドを発行して実行することもできます。例：git gc
  * Git が保守するファイルシステムが完全かどうかを確認したい場合は、次のコマンドを実行できます：git fsck

Git の分散型バージョン管理システムについて、いくつか繰り返し述べておきます。

* 全員がリポジトリの完全なコピーを持っているため、Git はサーバー側のサポートなしに完全にバージョン管理を操作できます。
* 全員がリポジトリの完全なコピーを持っているため、バージョン変更をコミットするたびにローカルリポジトリにのみコミットするので、コミット速度が非常に速く、ネットワーク接続も不要で、開発時間を大幅に節約できます。
* 全員がリポジトリの完全なコピーを持っているため、Git のバージョン管理を使う際に「権限管理」というものは存在しません。全メンバーがリポジトリをクローンでき、権限の制限なくローカルで変更をコミットできます。Git を使う際に設定できる唯一の権限は、上流リポジトリやリモートリポジトリへのアクセス権限があるかどうかです。
* 変更したバージョンを他の人と交換したい場合は、いつでも「マージ」を通じて行えます。Git には非常に強力なマージ追跡機能があります。
* 複数人のバージョンをマージするには、共有リポジトリへの権限またはアクセス権があればよいのです。
  **例：同じサーバー上ではフォルダの権限を通じて共有したり、SSH を通じて別のサーバーの Git リポジトリにリモートアクセスしたり、Web サーバーを通じて Git リポジトリを共有したりできます。**
