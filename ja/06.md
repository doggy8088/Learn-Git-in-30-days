# Day 06: Git のデータ構造を解析する - オブジェクト構造

Git のデータ構造において、「オブジェクト」は「不変の（immutable）」ファイルタイプです。「オブジェクトストレージ」に保存されたすべてのファイルは、通常は入るだけで出ることはなく、その内容が変更されることもありません。その理由は、ファイルの内容を改ざんすると、新しい内容から計算される SHA1 ハッシュ値が元のオブジェクトのファイル名と異なってしまい、Git が実行を継続できなくなるためです。また、相対的に Git リポジトリにある程度の保護を提供します。本記事では Git のオブジェクト構造をより詳しく紹介し、最後には動画を通じてオブジェクトが生成されるプロセスとロジックも詳しく説明します。

## オブジェクトデータベースについて

前回の記事で述べたように、blob オブジェクトであれ tree オブジェクトであれ、これらはすべてオブジェクトであり、これらのオブジェクトは「オブジェクトストレージ」（object storage）と呼ばれる場所に保存されます。この「オブジェクトストレージ」は、デフォルトでは「リポジトリ」の objects ディレクトリにあります。以下の図のとおりです。

![画像](figures/06/01.png)

ただし、Git リポジトリ内の各「オブジェクト」は、「ファイルの内容」に対して SHA1 ハッシュ演算を実行してハッシュ値を計算し、このハッシュ値をオブジェクトの名前（ファイル名）として使用します。8a6b275638f3cf164395e65066a1132bb36b7896 を例にとると、Git はまず最初の 2 文字（8a）をディレクトリとして取り、次に残りのハッシュ値をファイル名（6b275638f3cf164395e65066a1132bb36b7896）として使用します。これらのオブジェクトの物理ディレクトリとファイルも .git\objects ディレクトリに配置されます。以下の図のとおりです。

## オブジェクトの種類

この「オブジェクトデータベース」には、4 種類のオブジェクトがあります。

1. **blob オブジェクト**： これはワーキングディレクトリ内のファイルの「内容」であり、内容のみです。git add コマンドを実行すると、これらの新しいファイルの内容は直ちに blob オブジェクトとして書き込まれます。ファイル名はオブジェクトの内容のハッシュ結果であり、その他の情報は含まれません。ファイルの時刻、元のファイル名、その他のファイル情報といった情報は、他の種類のオブジェクト（つまり tree オブジェクト）に保存されます。

2. **tree オブジェクト**： この種類のオブジェクトは、特定のディレクトリ配下のすべての情報を保存します。そのディレクトリ配下のファイル名、対応する blob オブジェクト名、シンボリックリンク、または他の tree オブジェクトを含みます。tree オブジェクトは他の tree オブジェクトを含むことができるため、tree オブジェクトを閲覧することは、実際にはファイルシステムにおける「フォルダ」と同じです。簡単に言えば、tree オブジェクトは特定のバージョンにおけるフォルダのスナップショットです。

3. **commit オブジェクト**： バージョンにどの tree オブジェクトが含まれているかを記録するために使われます。commit オブジェクトは Git のコミットを表し、特定のコミットバージョンにどの tree オブジェクトがあるか、バージョンをコミットした時刻、コミットメッセージなどを記録します。通常、前の commit オブジェクトの名前も記録します（最初のコミットバージョンだけが、前の commit オブジェクトの名前を持ちません）。

4. **tag オブジェクト**： これはコンテナであり、通常は特定の commit オブジェクトに関連付けるために使われ（特定の blob オブジェクトや tree オブジェクトに関連付けることもできます）、タグ名などの追加の参照情報（メタデータ）を保存します。tag オブジェクトの最も一般的な用途は、特定のバージョンの commit オブジェクトに理解しやすい名前で印を付けることであり、それは特定のリリースバージョンや特別な意味を持つバージョンを表すことがあります。

Git は各バージョンの各ファイルに対して、対応する blob オブジェクトを作成します。同様に、blob オブジェクトのファイル名は上記の方法で計算されます。これらの blob ファイルからは、バージョンとの関係はまったく見えません。tree オブジェクト（フォルダのスナップショット）と commit オブジェクト（各バージョンのスナップショット）を使って、これらの blob とバージョンの関係を関連付けなければなりません。

すべてのオブジェクトは zlib アルゴリズムで圧縮されており、ファイルアクセスの効率を効果的に向上できるだけでなく、将来パッキングする際にデルタ圧縮アルゴリズムを使って容量を節約することもできます。類似した blob を自動的に見つけ、blob 間の差分を自動的に計算し、それらの差分を *packfile* と呼ばれるファイルに保存することで、ディスク容量を大幅に節約できます。通常、*packfiles* は .git\objects\pack ディレクトリに配置されます。以下の図のとおりです。

## オブジェクト構造の利点

Git の「オブジェクト」の設計がいかに美しいかを、徐々に理解してきているはずです。最初の記事で、Git の重要な設計をいくつか挙げました。ここで「オブジェクト」の特性に関連する設計をいくつか再掲します。

* 大規模プロジェクトの効率的な処理
* 完全なリポジトリがローカルマシンにクローンされるだけでなく、すべての blob オブジェクトは「内容」を通じてコンテンツアドレス可能であるため、異なるバージョン間で同じ内容を見つけることが非常に効率的です。
* 履歴記録の保護
* Git のバージョン管理の過程では、各コミットが commit オブジェクトを生成し、この commit オブジェクトの名前は commit オブジェクトの内容を通じて生成されます。さらに、commit オブジェクトは tree オブジェクトに関連付けられ、tree オブジェクトの名前は tree オブジェクトの内容を通じて生成されます。tree オブジェクトは blob オブジェクトと tree オブジェクトに関連付けられ、これらのオブジェクトの名前も内容を通じて生成されます。このように階層ごとに関連付けられているため、今日あるバージョンの履歴を本当に改ざんしようとすると、その難易度はかなり高いです！
* Git リポジトリは頻繁にクローンやフォークが行われるため、リポジトリがクローンされさえすれば、ソースリポジトリ内のいずれかのオブジェクトが変更されると、それらのクローンされたリポジトリを元にマージして戻すことが難しくなるため、バージョン記録を勝手に改ざんすることはほぼ不可能です。
* オブジェクトの定期的なパッキング
* Git で言う「オブジェクト」とは、実際にはリポジトリ内のファイルを表します。バージョン変更の過程では、プロジェクト内のコードやその他のファイルが更新されます。更新されるたびに、ファイルの内容が異なる限り、新しい「オブジェクト」が作成され、内容の異なるこれらのファイルはすべて保持されます。
* プロジェクトが大きくなりバージョンが増えるにつれて、オブジェクトがますます増えていくことが想像できるでしょう。各ファイルを個別に圧縮して小さくすることはできますが、ファイルが多すぎるとファイルへのアクセス効率はどんどん低下します。そのため、Git の設計には、古い「オブジェクト」のグループを自動的に packfile にパッキングして、ファイルアクセスの効率を向上させる仕組みがあります。
* 新しく追加されたファイルは依然として単一のファイルとして存在します。つまり、Git リポジトリ内の「ファイル」は Git の「オブジェクト」ですが、時々再パッキングする必要があります。
* おそらく Git は再パッキングなどのアクションを自動的に実行しますが、自分でコマンドを発行して実行することもできます。例：git gc
* Git が保守するファイルシステムが完全かどうかを確認したい場合は、次のコマンドを実行できます：git fsck

## 本日のまとめ

Git における「オブジェクト」は非常に重要であり、その特性も非常に重要です。通常、Git コマンドを操作する過程でこれらのファイルに直接触れる必要はありませんが、これらのオブジェクトの存在を理解することは、Git の動作モードと Git 独自の設計概念をよりよく理解する助けとなります。
