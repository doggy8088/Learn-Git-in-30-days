# Hari 06: Menghurai Struktur Data Git - Struktur Objek

Dalam struktur data Git, "objek" ialah jenis fail yang "tidak boleh berubah" (immutable). Semua fail yang disimpan dalam "storan objek" biasanya hanya masuk dan tidak keluar, dan kandungannya tidak akan diubah suai. Sebabnya ialah jika anda mengusik kandungan fail, nilai hash SHA1 yang dikira daripada kandungan baharu akan berbeza daripada nama fail objek asal, yang akan menyebabkan Git gagal untuk terus melaksanakan, dan secara relatifnya juga memberikan tahap perlindungan tertentu untuk repositori Git. Artikel ini akan memperkenalkan struktur objek Git dengan lebih terperinci, dan akhirnya juga akan menerangkan dengan terperinci proses dan logik cara objek dijana melalui video.

## Tentang Pangkalan Data Objek

Seperti yang disebutkan dalam artikel sebelumnya, tanpa mengira objek blob atau objek tree, ini semua adalah objek, dan objek ini akan disimpan dalam apa yang dipanggil "storan objek" (object storage), dan "storan objek" ini secara lalai berada dalam direktori objects bagi "repositori", seperti yang ditunjukkan dalam rajah berikut:

![imej](figures/06/01.png)

Walau bagaimanapun, setiap "objek" dalam repositori Git melakukan operasi hash SHA1 pada "kandungan fail" untuk mengira nilai hash, dan menggunakan nilai hash ini sebagai nama objek (nama fail). Mengambil 8a6b275638f3cf164395e65066a1132bb36b7896 sebagai contoh, Git akan terlebih dahulu mengambil dua aksara pertama (8a) sebagai direktori, dan kemudian menggunakan nilai hash yang selebihnya sebagai nama fail (6b275638f3cf164395e65066a1132bb36b7896). Direktori fizikal dan fail objek ini juga akan diletakkan dalam direktori .git\objects, seperti yang ditunjukkan dalam rajah berikut:

![imej](figures/06/02.png)

## Jenis Objek

Dalam "pangkalan data objek" ini, terdapat 4 jenis objek:

1. **blob object**: Ini ialah "kandungan" fail dalam direktori kerja, dan kandungan sahaja. Apabila anda melaksanakan perintah git add, kandungan fail baharu ini akan segera ditulis sebagai objek blob. Nama fail ialah hasil hash kandungan objek, tanpa sebarang maklumat lain. Maklumat seperti masa fail, nama fail asal, atau maklumat fail lain akan disimpan dalam jenis objek lain (iaitu, objek tree).

2. **tree object**: Jenis objek ini menyimpan semua maklumat di bawah direktori tertentu, termasuk nama fail di bawah direktori itu, nama objek blob yang sepadan, pautan simbolik, atau objek tree lain. Oleh kerana objek tree boleh mengandungi objek tree lain, menyemak imbas objek tree sebenarnya sama dengan "folder" dalam sistem fail. Secara ringkasnya, objek tree ialah snapshot folder di bawah versi tertentu.

3. **commit object**: Digunakan untuk merekodkan objek tree mana yang disertakan dalam versi. Objek commit mewakili commit Git, merekodkan objek tree mana yang berada dalam versi commit tertentu, serta masa commit versi, mesej commit, dsb. Biasanya, ia juga merekodkan nama objek commit sebelumnya (hanya versi commit pertama tidak mempunyai nama objek commit sebelumnya).

4. **tag object**: Ini ialah bekas, biasanya digunakan untuk mengaitkan dengan objek commit tertentu (juga boleh dikaitkan dengan objek blob dan tree tertentu), dan menyimpan beberapa maklumat rujukan tambahan (metadata), seperti nama tag. Penggunaan objek tag yang paling lazim ialah untuk menandakan objek commit versi tertentu dengan nama yang mudah difahami, yang mungkin mewakili versi keluaran tertentu atau versi yang mempunyai kepentingan khas.

Git akan mencipta objek blob yang sepadan untuk setiap fail dalam setiap versi. Begitu juga, nama fail objek blob dikira dengan cara di atas. Daripada fail blob ini, anda tidak dapat melihat sebarang hubungan dengan versi. Anda mesti menggunakan objek tree (snapshot folder) dan objek commit (snapshot setiap versi) untuk mengaitkan hubungan antara blob dan versi ini.

Semua objek dimampatkan menggunakan algoritma zlib, yang bukan sahaja boleh meningkatkan kecekapan akses fail dengan berkesan tetapi juga menggunakan algoritma pemampatan delta untuk menjimatkan ruang apabila membungkus pada masa hadapan. Ia akan mencari blob yang serupa secara automatik, mengira perbezaan antara blob secara automatik, dan menyimpan perbezaan ini dalam fail yang dipanggil *packfile*, yang boleh menjimatkan ruang cakera dengan banyak. Biasanya, *packfile* diletakkan dalam direktori .git\objects\pack, seperti yang ditunjukkan dalam rajah berikut:

## Kelebihan Struktur Objek

Anda sepatutnya secara beransur-ansur memahami betapa indahnya reka bentuk "objek" Git. Dalam artikel pertama, kami menyebutkan beberapa reka bentuk penting Git. Mari kita senaraikan semula beberapa reka bentuk yang berkaitan dengan ciri "objek":

* Pengendalian projek besar yang cekap
* Bukan sahaja repositori lengkap akan diklon ke mesin setempat, tetapi oleh kerana semua objek blob boleh dialamatkan kandungan melalui "kandungan", mencari kandungan yang sama antara versi yang berbeza adalah sangat cekap.
* Perlindungan rekod sejarah
* Dalam proses kawalan versi Git, setiap commit menjana objek commit, dan nama objek commit ini dijana melalui kandungan objek commit. Tambahan pula, objek commit dikaitkan dengan objek tree, dan nama objek tree dijana melalui kandungan objek tree. Objek tree dikaitkan dengan objek blob dan tree, dan nama objek ini juga dijana melalui kandungan. Pengaitan lapis demi lapis seperti ini, jika anda benar-benar ingin mengusik sejarah versi tertentu hari ini, kesukarannya agak tinggi!
* Oleh kerana repositori Git sering diklon atau di-fork, selagi repositori diklon, jika mana-mana objek dalam repositori sumber diubah suai, repositori yang diklon ini akan sukar untuk dicantumkan kembali, jadi anda hampir tidak boleh mengusik rekod versi sewenang-wenangnya.
* Pembungkusan objek secara berkala
* "Objek" yang kami sebutkan dalam Git sebenarnya mewakili fail dalam repositori. Dalam proses perubahan versi, kod atau fail lain dalam projek akan dikemas kini. Setiap kali ia dikemas kini, selagi kandungan fail berbeza, "objek" baharu akan dicipta, dan semua fail dengan kandungan berbeza ini akan dikekalkan.
* Anda boleh bayangkan bahawa apabila projek menjadi lebih besar dan mempunyai lebih banyak versi, akan ada semakin banyak objek. Walaupun setiap fail boleh dimampatkan secara individu untuk menjadikan fail lebih kecil, terlalu banyak fail masih akan menjadikan akses fail semakin tidak cekap. Oleh itu, reka bentuk Git mempunyai mekanisme yang boleh membungkus sekumpulan "objek" lama secara automatik ke dalam packfile untuk meningkatkan kecekapan akses fail.
* Fail yang baru ditambah itu masih akan wujud sebagai fail tunggal, yang juga bermakna "fail" dalam repositori Git ialah "objek" Git, tetapi ia perlu dibungkus semula sekali-sekala.
* Agaknya, Git akan melaksanakan tindakan seperti pembungkusan semula secara automatik, tetapi anda masih boleh mengeluarkan perintah untuk melaksanakannya sendiri. Contohnya: git gc
* Jika anda ingin menyemak sama ada sistem fail yang diselenggara oleh Git adalah lengkap, anda boleh melaksanakan perintah berikut: git fsck

## Ringkasan Hari Ini

"Objek" dalam Git sangat penting, dan ciri-cirinya juga sangat penting. Walaupun kita biasanya tidak perlu menyentuh fail ini secara langsung semasa proses mengendalikan perintah Git, memahami kewujudan objek ini memang membantu anda lebih memahami mod operasi Git dan konsep reka bentuk unik Git.
