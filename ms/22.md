# Hari 22: Membetulkan Sejarah Versi yang Telah Di-commit Bahagian 4 (rebase)

Kami telah membincangkan tiga kaedah berbeza untuk membetulkan versi. Secara tegasnya, `git revert` dan `git cherry-pick` tidak benar-benar "membetulkan rekod sejarah versi" - ia menggunakan versi yang telah di-commit sebelum ini, sama ada "menggunakannya semula" atau "menggunakannya secara songsang." Artikel ini akan menerangkan mekanisme Rebase Git, yang benar-benar digunakan untuk mengubah suai rekod commit. Ciri ini penting dan berkuasa.

## Memahami git rebase

Rebase ialah salah satu ciri Git yang paling berkuasa tetapi berpotensi berbahaya. Ia membolehkan anda menulis semula sejarah commit, menjadikannya lebih bersih dan lebih linear.

Rebase ialah proses memindahkan atau menggabungkan urutan commit ke commit asas baharu. Tidak seperti cantuman, yang mengekalkan sejarah lengkap, rebase menulis semula sejarah untuk mencipta kemajuan yang linear.

## Rebase Asas

Operasi rebase asas:

```
# On feature branch
git checkout feature-branch

# Rebase onto main
git rebase main
```

Ini memainkan semula semua commit daripada `feature-branch` di atas `main`.

## Cara Rebase Berfungsi

Apabila anda membuat rebase:

1. Git mencari leluhur sepunya bagi cabang anda dan cabang sasaran
2. Ia menyimpan semua commit daripada cabang anda sejak leluhur tersebut
3. Ia me-reset cabang anda kepada cabang sasaran
4. Ia menggunakan semula commit yang disimpan satu demi satu

## Rebase vs Cantuman

**Cantuman (Merge)**:
* Mengekalkan sejarah yang lengkap
* Menunjukkan bila cabang mencapah dan dicantumkan
* Selamat untuk cabang yang dikongsi
* Mencipta commit cantuman

**Rebase**:
* Mencipta sejarah linear
* Lebih bersih, lebih mudah difahami
* Menulis semula sejarah (berbahaya untuk cabang yang dikongsi)
* Tiada commit cantuman

Perbandingan visual:

```
# Before rebase
     C---D feature
    /
A---B---E---F main

# After git rebase main (on feature)
             C'---D' feature
            /
A---B---E---F main

# After git merge feature (on main)
     C---D 
    /     A---B---E---F---G main
```

## Mengendalikan Konflik Semasa Rebase

Jika konflik berlaku:

```
# Git pauses the rebase
# Resolve conflicts in the files
# Stage the resolved files
git add <resolved-files>

# Continue the rebase
git rebase --continue
```

Untuk membatalkan rebase:

```
git rebase --abort
```

Untuk melangkau commit semasa:

```
git rebase --skip
```

## Rebase Interaktif

Rebase interaktif memberikan anda kawalan penuh ke atas commit:

```
git rebase -i HEAD~3
```

Ini membuka editor di mana anda boleh:

* **pick**: Kekalkan commit seperti sedia ada
* **reword**: Tukar mesej commit
* **edit**: Berhenti untuk meminda commit
* **squash**: Gabungkan dengan commit sebelumnya, kekalkan kedua-dua mesej
* **fixup**: Gabungkan dengan commit sebelumnya, buang mesej ini
* **drop**: Keluarkan commit sepenuhnya

Contoh editor rebase interaktif:

```
pick abc123 Add feature A
reword def456 Add feature B
squash ghi789 Fix typo in feature B
drop jkl012 Experimental change
```

## Tugas Rebase Interaktif yang Lazim

### Menggabungkan Commit (Squashing)

Gabungkan berbilang commit menjadi satu:

```
git rebase -i HEAD~3

# In the editor, change:
pick abc123 First commit
pick def456 Second commit
pick ghi789 Third commit

# To:
pick abc123 First commit
squash def456 Second commit
squash ghi789 Third commit
```

### Menyusun Semula Commit

Hanya susun semula baris dalam editor rebase interaktif.

### Menyunting Commit

```
git rebase -i HEAD~3

# Change "pick" to "edit" for the commit you want to modify
# Git will stop at that commit
# Make your changes
git add .
git commit --amend
git rebase --continue
```

## Rebase ke Cabang yang Berbeza

```
git rebase --onto new-base old-base feature-branch
```

Ini memindahkan commit daripada `feature-branch` yang datang selepas `old-base` ke `new-base`.

## Autosquash

Gabungkan commit fixup secara automatik:

```
# Create a fixup commit
git commit --fixup <commit-to-fix>

# Later, rebase with autosquash
git rebase -i --autosquash main
```

## Peraturan Emas Rebase

**Jangan sekali-kali rebase commit yang telah di-push ke repositori yang dikongsi!**

Rebase menulis semula sejarah, yang boleh menyebabkan masalah besar kepada orang lain yang telah mendasarkan kerja pada commit tersebut.

Selamat untuk:
* Commit setempat yang belum di-push
* Cabang ciri yang anda miliki
* Membersihkan sebelum mencipta pull request

Berbahaya untuk:
* Cabang main/master
* Cabang ciri yang dikongsi
* Sebarang commit yang mungkin telah dijadikan asas kerja oleh orang lain

## Memulihkan daripada Kesilapan Rebase

Jika rebase menjadi salah:

```
# Find the commit before the rebase
git reflog

# Reset to that commit
git reset --hard HEAD@{2}
```

## Amalan Terbaik

1. **Rebase sebelum push**: Bersihkan commit setempat anda sebelum berkongsi
2. **Jangan rebase sejarah awam**: Hanya rebase commit setempat
3. **Buat sandaran sebelum rebase besar**: Cipta cabang terlebih dahulu
4. **Berkomunikasi**: Beritahu pasukan anda jika anda mesti rebase kod yang dikongsi
5. **Berlatih**: Cuba rebase pada cabang buangan terlebih dahulu

## Ringkasan Hari Ini

Rebase ialah alat yang berkuasa untuk mencipta sejarah commit yang bersih dan linear. Walaupun ia sangat baik untuk kerja setempat dan menyediakan cabang untuk dicantumkan, ia mesti digunakan dengan berhati-hati untuk mengelakkan penulisan semula sejarah yang dikongsi. Memahami bila dan cara menggunakan rebase adalah penting untuk aliran kerja Git lanjutan.

Izinkan saya menyusun semula perintah dan parameter Git yang dipelajari hari ini:

* git rebase
* git rebase main
* git rebase -i
* git rebase --continue
* git rebase --abort
* git rebase --skip
* git rebase --onto
* git rebase --autosquash
* git commit --fixup
