# Hari 05: Memahami Hubungan antara Repositori, Direktori Kerja, Objek, dan Indeks

Dalam proses menggunakan kawalan versi Git, beberapa konsep yang sangat asas mesti dibina supaya anda boleh belajar dengan lebih cekap dan bermakna. Dengan sokongan konsep yang jelas dan betul, ia bukan sahaja akan membantu anda mempelajari operasi perintah Git, tetapi yang lebih penting, mempelajari pengetahuan berkaitan Git akan menjadi lebih mudah.

## Memahami Repositori

Apabila kita menggunakan Git untuk kawalan versi, secara semula jadi, kita memerlukan "repositori" untuk menyimpan maklumat versi ini. Perkataan Inggeris Repository bermaksud ini. Saya biasa menterjemahkan perkataan Inggeris ini sebagai "repositori storan", mewakili ruang atau folder dan sekumpulan fail yang digunakan untuk menyimpan semua versi.

Jika anda mempunyai pengalaman menggunakan Git, anda sepatutnya tahu dengan baik bahawa terdapat banyak cara untuk mencipta repositori. Jika anda ingin mencipta repositori Git dalam mana-mana folder, hanya masukkan perintah berikut untuk melengkapkan penciptaan:

    git init

Melalui rajah proses mencipta repositori Git berikut, kita boleh tahu dengan jelas bahawa apabila kita melaksanakan git init dalam direktori G:\git-demo, Git akan membantu kita mencipta apa yang dipanggil repositori Git secara automatik dalam direktori .git bagi direktori itu. Jangan ragu-ragu, folder .git ini ialah repositori Git yang lengkap. Pada masa hadapan, semua perubahan versi akan disimpan secara automatik dalam folder ini.

## Memahami Direktori Kerja

Dalam contoh di atas, direktori G:\git-demo akan menjadi "direktori kerja" kita secara automatik. Maksud "direktori kerja" ialah kita sedang bersedia untuk membangunkan fail projek, dan semua kerja masa hadapan akan diedit dalam direktori ini, sama ada menambah fail, mengubah suai fail, memadam fail, menamakan semula fail, ... dan semua operasi berkaitan Git yang lain akan diselesaikan dalam direktori ini, jadi ia dipanggil "direktori kerja".

Apabila kita mengendalikan parameter perintah berkaitan Git, kita biasanya melaksanakannya dalam "direktori kerja".

Oleh kerana akan terdapat banyak situasi cabang apabila menggunakan kawalan versi Git, direktori kerja mungkin bertukar antara cabang yang berbeza. Sesetengah perintah git akan mengemas kini fail dalam direktori kerja apabila ia dilaksanakan. Contohnya, apabila anda menggunakan git checkout untuk beralih ke cabang yang berbeza, kerana struktur direktori cabang semasa tidak begitu sama dengan cabang yang anda ingin beralih kepadanya, ia sangat berkemungkinan akan mengemas kini fail dalam direktori kerja semasa anda supaya direktori dan fail di bawah direktori kerja semasa ini sama dengan direktori dan fail di bawah cabang lain yang hendak dialih kepadanya.

Oleh itu, memastikan direktori kerja bersih pada masa yang sesuai ialah prinsip asas dalam proses kawalan versi, terutamanya apabila melakukan cantuman pada masa hadapan. Ini amat penting. Saya akan menerangkan lebih lanjut pengetahuan berkaitan dalam artikel akan datang.

## Memahami Struktur Data Git

Terdapat dua struktur data penting dalam Git, iaitu "objek" dan "indeks".

"Objek" digunakan untuk menyimpan semua fail dan rekod versi dalam repositori, manakala "indeks" digunakan untuk menyimpan keadaan direktori sebelum memasuki repositori.

## Tentang Objek

Apa yang dipanggil "objek" ialah "fail khas". Proses penjanaan fail ini sangat menarik. Ia mengambil kandungan fail, menjana nilai hash SHA1 melalui kandungan itu, dan kemudian menamakan fail mengikut nilai hash SHA1 ini.

Dalam proses menggunakan Git untuk kawalan versi, semua direktori dan fail yang hendak dikawal akan terlebih dahulu membezakan antara "maklumat direktori" dan "kandungan fail", yang kita panggil objek tree dan objek blob.

Antaranya, objek blob menggunakan "kandungan fail" asal sebagai kandungan fail blob (nota: objek blob sebenarnya ialah fail fizikal), dan kemudian melakukan operasi hash SHA1 pada kandungannya untuk menjana id hash, dan kemudian menggunakan id hash ini sebagai nama fail bagi fail blob. Daripada ini, kita boleh tahu bahawa objek blob ialah fail dengan "kandungan sahaja". Nama failnya dijana daripada kandungan, jadi mana-mana fail blob tunggal biasanya tiada bantuan untuk kawalan versi.

Satu lagi objek tree digunakan untuk menyimpan fail mana yang disertakan dalam folder tertentu dan apakah nama fail objek blob yang sepadan dengan fail ini. Dalam objek tree, selain mengandungi nama fail dan maklumat berkaitan objek blob, ia juga boleh mengandungi objek tree lain. Jadi objek tree sebenarnya sinonim dengan "folder".

Tanpa mengira objek blob dan objek tree, ini semua adalah objek, dan objek ini akan disimpan dalam apa yang dipanggil "storan objek" (object storage), dan "storan objek" ini secara lalai berada dalam direktori objects bagi "repositori", seperti yang ditunjukkan dalam rajah berikut:

## Tentang Indeks

Apa yang dipanggil "indeks" ialah fail sementara yang kerap berubah, yang biasanya terletak dalam fail bernama index dalam direktori .git. Secara ringkasnya, tujuan "indeks" terutamanya adalah untuk merekodkan "fail mana yang akan diserahkan kepada versi commit seterusnya". Dengan kata lain, jika anda ingin menyerahkan versi ke repositori Git, maka anda mesti terlebih dahulu mengemas kini status indeks, dan perubahan akan diserahkan.

Fail indeks ini biasanya menyimpan keadaan versi tertentu dalam repositori Git. Keadaan ini boleh diwakili oleh mana-mana objek commit dan objek tree.

Kita biasanya tidak mengedit fail binari .git\index secara langsung, tetapi mengendalikan fail indeks ini melalui perintah git standard. Perintah untuk mengendalikan fail indeks adalah lebih kurang seperti berikut:

* git add
* git mv
* git rm
* git status
* git commit
* git ls-files

"Indeks" Git ialah medium antara "storan objek" (object storage) dan "direktori kerja" (working directory).

Anda mungkin sudah meneka bahawa hubungan antara konsep ini yang ingin dihuraikan oleh artikel ini boleh diterangkan dengan 5 langkah berikut:

* Untuk menggunakan kawalan versi Git, anda mesti terlebih dahulu mencipta "direktori kerja" dan "repositori". (mkdir, git init)
* Anda mesti terlebih dahulu membangun dalam "direktori kerja", anda mungkin mencipta direktori, mencipta fail, mengubah suai fail, memadam fail, ... dan operasi lain.
* Kemudian apabila anda ingin menyerahkan versi baharu ke "repositori" Git, anda mesti terlebih dahulu mengemas kini status "indeks". (git add, git mv, ...)
* Kemudian Git akan memutuskan fail mana yang hendak diserahkan ke "repositori" Git berdasarkan keadaan semasa "indeks". (git status)
* Akhir sekali, apabila menyerahkan perubahan (git commit), maklumat versi akan ditulis ke "storan objek" (pada masa ini, objek commit akan ditulis).

## Ringkasan Hari Ini

Perkara yang paling penting tentang seni bina Git yang dibincangkan hari ini ialah hubungan antara "objek" dan "indeks", kerana tanpa maklumat "indeks", Git tidak boleh mencipta versi.

Berdasarkan perbezaan antara "objek" dan "indeks", anda sepatutnya dapat mendapati bahawa "objek" ialah jenis fail yang "tidak boleh berubah" (immutable). Pada prinsipnya, sebarang objek yang ditulis ke "storan objek" tidak akan berubah lagi, kerana semua objek dijana daripada kandungan fail asal. Kita juga boleh mengatakan ini ialah "pangkalan data objek" (object database), dan pangkalan data ini biasanya hanya menambah kandungan, dan terdapat lebih sedikit kes "memadam kandungan" atau "mengubah kandungan". Data hanya dipadam apabila melaksanakan git gc untuk membersihkan data sampah. "Indeks" ialah fail indeks yang "boleh berubah" (mutable) yang digunakan untuk merekodkan kandungan yang direktori kerja semasa bersedia untuk commit.

Apabila anda selangkah demi selangkah menghampiri teras Git, perlahan-lahan mengubah konsep abstrak yang kabur dan tidak jelas menjadi pengetahuan konsep yang konkrit, anda tidak akan lagi berasa tidak senang tentang Git. Sila terus berusaha untuk belajar, kejayaan ada di hadapan.
