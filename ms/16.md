# Hari 16: Menggunakan git reflog untuk Menjejak Sejarah Perubahan

Mempelajari perintah kawalan versi Git tidak sukar, tetapi memahami apa yang sebenarnya dilakukan oleh Git terhadap repositori anda boleh menjadi agak mencabar. Apabila anda secara beransur-ansur memahami konsep teras dan prinsip operasi Git, anda boleh mengawal perubahan versi dalam repositori Git anda dengan berkesan. Artikel ini menerangkan cara Git merekodkan sejarah perubahan untuk setiap versi.

## Memahami git reflog

`git reflog` (log rujukan) ialah mekanisme yang merekodkan bila hujung cabang dan rujukan lain dikemas kini dalam repositori setempat. Sebelum anda memahami sepenuhnya prinsip asas dan struktur objek Git, anda tidak boleh benar-benar memahami proses perekodan versi. Apabila anda tidak memahami proses perekodan versi, anda secara semula jadi bimbang "ke mana perginya versi saya?" Anda mungkin pernah mendengar seseorang berkata "Kami menggunakan kawalan versi, jadi semua versi terpelihara, sila ubah suai kod dengan bebas." Mengetahui perkara ini adalah satu hal, mengetahui cara melakukannya adalah hal lain, dan sama ada anda benar-benar boleh melakukannya adalah hal yang lain pula.

Nasib baik, Git mempunyai mekanisme pengelogan yang ketat, dan mekanisme ini sangat terbuka - fail log semuanya dalam format teks dan agak mudah difahami. Mari kita terangkan proses perekodan versi ini.

Reflog amat berguna untuk:

* Mencari commit yang tidak lagi boleh dicapai daripada mana-mana cabang
* Memulih daripada reset atau rebase yang tersilap
* Memahami apa yang anda lakukan dalam repositori anda
* Membuat asal perubahan yang tidak disengajakan

## Direktori logs

Jika anda memasuki folder `.git/` mana-mana direktori kerja Git, anda boleh melihat direktori `logs`. Folder `logs` ini mengandungi fail `HEAD` yang merekodkan sejarah perubahan versi "cabang semasa."

Kandungan fail kelihatan seperti ini (ID objek disingkatkan untuk kebolehbacaan):

```
0000000 f5685e0 Will <xxxx@gmail.com> 1381718394 +0800	commit (initial): Initial commit
f5685e0 38d924f Will <xxxx@gmail.com> 1381718395 +0800	commit: a.txt: set 1 as content
38d924f efa1e0c Will <xxxx@gmail.com> 1381734238 +0800	commit: test
efa1e0c af493e5 Will <xxxx@gmail.com> 1381837967 +0800	commit: Add c.txt
```

## Penggunaan Asas

Untuk melihat reflog:

```
git reflog
```

Ini menunjukkan senarai tindakan terkini dalam tertib kronologi terbalik. Daripada fail teks, anda boleh melihat "versi pertama" di bahagian atas, tetapi melalui `git reflog`, "versi terkini" dipaparkan dahulu, dan "versi pertama" terakhir.

Setiap entri menunjukkan:
* Hash commit
* Rujukan (biasanya HEAD)
* Tindakan yang dilakukan
* Mesej commit

## Format Reflog

Output kelihatan seperti:

```
a1b2c3d HEAD@{0}: commit: Add new feature
e4f5g6h HEAD@{1}: checkout: moving from master to feature-branch
i7j8k9l HEAD@{2}: reset: moving to HEAD~1
```

Tatatanda `HEAD@{n}` merujuk kepada nilai HEAD ke-n sebelumnya. Di sini, setiap versi dalam log sejarah mempunyai nombor yang mewakili kedudukan versi ini dalam fail log. `HEAD@{0}` sentiasa mewakili "versi terkini" cabang semasa, dalam erti kata lain, operasi Git paling terkini yang anda lakukan pada "cabang" ini. Sebarang perubahan versi yang anda buat pada Git akan direkodkan sepenuhnya.

## Memulih daripada Perubahan yang Tidak Disengajakan

Apabila pemula mula-mula menggunakan Git, mereka mungkin secara tidak sengaja melaksanakan perintah yang salah, seperti konflik berlaku semasa `git merge`, atau kesilapan berlaku semasa melaksanakan `git pull` untuk mendapatkan versi terkini daripada repositori jauh. Dalam situasi sedemikian, anda boleh menggunakan "nama rujukan" khas `HEAD@{n}` untuk "mencari" versi ini dan memulihkan versi repositori Git semasa kepada versi sebelumnya.

Contohnya, jika kami ingin "membatalkan" rekod versi paling terkini, kami boleh menggunakan `git reset HEAD@{1} --hard` untuk memulihkan perubahan. Ini bermakna perubahan yang asalnya pada `HEAD@{0}` akan dipadam. Walau bagaimanapun, dalam Git, semua perubahan direkodkan, termasuk tindakan anda melaksanakan `git reset "HEAD@{1}" --hard`.

Apakah maksudnya? Ia bermakna apabila melaksanakan sebarang perintah Git, anda tidak lagi perlu bimbang bahawa mana-mana data anda akan hilang. Tidak kira betapa salahnya perintah yang anda masukkan, semua fail yang sudah berada dalam repositori akan terpelihara, dengan sama sekali tiada peluang untuk hilang. Jadi, jika anda ingin membuat asal tindakan `git reset "HEAD@{1}" --hard` yang baru anda laksanakan, hanya laksanakan `git reset "HEAD@{1}" --hard` sekali lagi. Bukankah itu hebat!

## Melihat Reflog Terperinci

Untuk maklumat yang lebih terperinci:

```
git reflog show --all
```

Untuk melihat reflog bagi cabang tertentu:

```
git reflog show branch-name
```

## Menggunakan Reflog untuk Memulihkan Commit

Jika anda secara tidak sengaja me-reset atau kehilangan commit, anda boleh memulihkannya menggunakan reflog:

```
# Find the commit you want to recover
git reflog

# Reset to that commit
git reset --hard HEAD@{2}
```

Atau gunakan hash commit secara langsung:

```
git reset --hard a1b2c3d
```

## Memulihkan Cabang yang Dipadam

Jika anda memadam cabang secara tersilap:

```
# Find the commit where the branch was deleted
git reflog

# Recreate the branch
git branch branch-name HEAD@{3}
# or
git branch branch-name <commit-hash>
```

## Tamat Tempoh Reflog

Secara lalai, entri reflog tamat tempoh selepas 90 hari untuk commit yang boleh dicapai dan 30 hari untuk commit yang tidak boleh dicapai. Anda boleh mengkonfigurasi ini:

```
git config gc.reflogExpire "90 days"
git config gc.reflogExpireUnreachable "30 days"
```

## Membersihkan Reflog

Untuk membersihkan entri reflog secara manual:

```
# Remove old reflog entries
git reflog expire --expire=now --all

# Run garbage collection
git gc --prune=now
```

## Had Reflog

Perkara penting untuk diingat:

* Reflog hanya setempat - ia tidak dikongsi dengan orang lain
* Reflog menjejak perubahan pada repositori anda, bukan fail
* Ia boleh membantu anda memulihkan commit, tetapi bukan perubahan yang belum di-commit

## Contoh Praktikal

### Contoh 1: Membuat Asal Hard Reset

```
# You accidentally reset
git reset --hard HEAD~3

# Find the old position
git reflog

# Restore to the old position
git reset --hard HEAD@{1}
```

### Contoh 2: Memulih Selepas Rebase yang Tersilap

```
# After a problematic rebase
git reflog

# Find the commit before the rebase (usually labeled "rebase finished")
git reset --hard HEAD@{5}
```

## Ringkasan Hari Ini

`git reflog` ialah ciri keselamatan yang berkuasa yang boleh menyelamatkan anda daripada banyak kesilapan Git. Ia amat berharga apabila anda perlu memulih daripada operasi seperti reset, rebase, atau pemadaman cabang. Walaupun ia bukan pengganti sandaran biasa, ia ialah alat yang tidak ternilai untuk pemulihan setempat.

Izinkan saya menyusun semula perintah dan parameter Git yang dipelajari hari ini:

* git reflog
* git reflog show
* git reflog show --all
* git reset --hard HEAD@{n}
* git branch branch-name HEAD@{n}
* git reflog expire
* git gc
