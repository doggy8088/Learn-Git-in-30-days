# Hari 01: Memahami Kawalan Versi Git

Saya telah menggunakan Subversion (SVN) selama hampir 10 tahun dan tidak pernah berasa perlu beralih kepada platform kawalan versi lain sehinggalah beberapa tahun yang lalu, apabila saya secara beransur-ansur memperkenalkan kawalan versi TFS (TFS Service) sebagai tindak balas kepada perubahan berasaskan awan. Peralihan itu berjalan lancar kerana SVN dan TFS mempunyai konsep kawalan versi yang serupa, kedua-duanya merupakan sistem kawalan versi berpusat. Sistem kawalan versi berpusat ini mudah, intuitif, dan senang untuk mengurus kebenaran. Sejujurnya, dalam kebanyakan senario pembangunan, Subversion atau TFS sudah lebih daripada mencukupi. Jadi, apakah peluang atau keperluan yang memaksa kami beralih kepada kawalan versi Git? Saya percaya orang yang berbeza mempunyai alasan mereka sendiri untuk menggunakan Git - ada yang menganggapnya menyeronokkan, ada yang menganggapnya segar, dan ada yang menganggapnya berkuasa. Walau apa pun, selagi alasan itu menyokong anda untuk mempelajari teknologi yang tidak dikenali secara aktif, ia adalah baik. Artikel ini bukan sahaja akan memperkenalkan mekanisme kawalan versi Git kepada anda tetapi juga berkongsi alasan saya ingin beralih kepada Git.

## Tujuan Artikel

Dalam bidang pembangunan perisian, kawalan versi kod sumber adalah sangat penting. Berbeza daripada sistem kawalan versi berpusat seperti Subversion atau TFVC (Team Foundation Version Control), Git ialah sistem kawalan versi teragih (DVCS; Distributed Version Control System) yang membawa banyak kelebihan kepada kawalan versi dan mengatasi kekurangan kawalan versi berpusat tradisional, seperti sokongan untuk operasi setempat, sandaran yang mudah, pencabangan dan cantuman yang berkuasa dan fleksibel, dan banyak lagi. Walau bagaimanapun, kerana kawalan versi Git amat berbeza daripada alat kawalan versi berpusat tradisional dari segi konsep kawalan versi mahupun penggunaan alat, ia mewujudkan keluk pembelajaran yang ketara.

Walaupun tema artikel ini ialah "Mahir Git dalam 30 Hari," sejujurnya, ini agak keterlaluan kerana Git sangat luas dan mendalam dengan banyak butiran untuk diterokai. Jika anda benar-benar ingin mengaplikasikannya dalam kerja, berapa hari pembelajaran yang diperlukan untuk benar-benar menguasainya? Belajar sedikit setiap hari selama 30 hari berturut-turut nampaknya angka yang munasabah (atau terlalu banyak?). Jika ada alat yang semua orang perlu gunakan dan perlu kuasai dengan segera, dan jika anda masih tidak tahu cara menggunakannya dengan fleksibel selepas 30 hari belajar, maka keluk pembelajarannya terlalu tinggi. Oleh itu, saya berpendapat fokus utama siri artikel ini ialah "cara mempelajari kawalan versi Git dalam masa 30 hari dan mesti boleh mengaplikasikannya dengan mahir dalam kerja pembangunan praktikal." Inilah tujuan sebenar siri ini. Saya tidak akan menekankan secara khusus butiran yang membosankan itu, tetapi sentiasa ada beberapa konsep dan butiran penting yang tidak boleh dilepaskan. Saya akan cuba menyebut sebahagiannya dalam setiap topik dan menerokainya dengan mendalam apabila ada peluang. Saya berharap semua orang dapat belajar sambil membuat dan merasai sendiri daya tarikan kawalan versi Git yang berkuasa.

## Peluang Peralihan

Dalam beberapa bulan yang lalu, syarikat kami mempunyai projek besar dengan lebih daripada 12 orang pembangun yang mengambil bahagian. Semua orang akhirnya memutuskan untuk menggunakan Git sebagai mekanisme kawalan versi untuk projek ini. Sebenarnya, berbanding dikatakan kami menggunakan kawalan versi Git, alasan sebenar penggunaannya ialah "kami memilih untuk menggunakan GitHub sebagai platform kawalan versi kami" kerana platform GitHub benar-benar disepadukan dengan baik, dengan sokongan kawalan versi Git yang lengkap, penjejakan dan pengurusan isu, pengurusan dokumen Wiki dalam talian, dan antara muka semakan kod sumber yang mesra. Ciri-ciri ini dapat membantu kami mengurangkan masalah komunikasi pasukan dengan berkesan semasa pembangunan kolaboratif berbilang orang.

Bermula dengan Git agak sukar kerana konsep kawalan versi Git sangat berbeza daripada Subversion sehingga sukar untuk memahami perbezaannya secara intuitif. Walaupun anda diberikan antara muka alat grafik GUI, anda mungkin belum tentu tahu cara menggunakannya. Anda tahu, apabila anda mempunyai alat yang berkuasa dan berguna di tangan anda, "menggunakannya dengan salah" adalah lebih teruk daripada "tidak tahu cara menggunakannya"! Secara ringkasnya, anda mesti terlebih dahulu membina mindset, memahami prinsip kerja Git, dan kemudian mula menggunakan alat berkaitan Git (sama ada alat baris perintah atau alat antara muka grafik). Inilah cara yang betul!

## Kaedah Pembelajaran

Apabila saya mula-mula mempelajari Git, saya membaca beberapa buah buku (sebenarnya memilih perkara utama), juga membaca banyak artikel dan pembentangan dalam talian, dan juga menonton beberapa video tutorial. Dengan menonton dan belajar, saya sememangnya dapat mempelajari cara menggunakan alat Git, dan saya tidak berasa ia terlalu sukar. Walau bagaimanapun, Git mempunyai banyak perintah dan parameter, jauh melebihi julat ingatan otak. Melainkan anda menggunakannya setiap hari, bagaimana mungkin anda boleh menaip perintah untuk kawalan versi sepanjang hari? Jika anda perlu merujuk buku setiap kali anda ingin menggunakan perintah Git, itu terlalu tidak cekap. Pada masa itu, saya secara intuitif berpendapat bahawa mempelajari Git pada akhirnya harus kembali kepada alat GUI yang berguna; jika tidak, perkara ini mungkin tidak mudah untuk dipromosikan dalam pasukan.

Tambahan pula, kerana Git ialah mekanisme "kawalan versi teragih", apabila bilangan pembangun mula meningkat dan setiap orang mula mempunyai salinan repositori mereka sendiri, semua orang menderita semasa proses pencabangan dan cantuman berbilang orang yang pertama, dan ia berlarutan untuk tempoh yang agak lama. Walaupun terdapat perkongsian teknikal dalam syarikat, oleh kerana semua orang belajar buat kali pertama, konsep abstrak Git itu tidak dapat berakar umbi dalam hati orang ramai. Mereka hanya boleh berkongsi berdasarkan kaedah penggunaan Git, seperti cara menggunakan alat, apakah perintah yang lazim digunakan, perintah apa yang harus digunakan dalam situasi khas, dan sebagainya. Walaupun prinsip yang kompleks dijelaskan semasa proses itu, oleh kerana pemahaman semua orang tentang Git masih kabur, pemahaman orang yang berbeza tentang kaedah kawalan versi Git tidak sama, dan pengetahuan serta konsep yang diserap tidak semestinya konsisten. Jadi walaupun selepas kursus itu, semua orang masih memerlukan beberapa hari untuk terus menyesuaikan diri, berbincang antara satu sama lain, dan menyelesaikan masalah bersama-sama. Jika anda seorang sahaja yang menggunakan Git, sangat sukar untuk merasai manfaat yang dibawa oleh Git, dan anda mungkin tidak dapat bertahan.

Oleh itu, saya berpendapat bahawa untuk mempelajari kawalan versi Git dengan baik, ia mungkin lebih mudah dipelajari jika anda mengetahui perkara berikut terlebih dahulu:

* Pertama, miliki konsep asas Git. Belajar melalui perintah ialah cara terpantas. Jangan langkau bahagian ini.
* Cari lebih ramai orang untuk mempelajari kawalan versi Git bersama anda, sebaik-baiknya menggunakannya secara langsung dalam kerja pembangunan praktikal.
* Adalah lebih baik untuk mempunyai beberapa pasukan perintis dalam pasukan yang boleh mempelajari lebih banyak konsep Git untuk dikongsi dengan orang lain atau memberikan bantuan tepat pada masanya apabila seseorang tersekat.
* Fahami bahawa Git ialah "kawalan versi teragih," dan semua orang mempunyai repositori yang lengkap, jadi anda mesti kerap mencantumkan fail.
* Apabila menggunakan Git, pencabangan dan cantuman adalah perkara biasa, tetapi setiap kali ada cantuman, akan ada konflik. Pelajari cara menyelesaikan konflik.

## Memahami Kawalan Versi Git

Git berasal daripada Linus Torvalds, bapa Linux, semasa beliau membangunkan kernel Linux. Oleh kerana kaedah kawalan versi awal sangat tidak cekap dan berpusat, banyak masalah timbul apabila mengurus kawalan versi untuk projek yang kompleks dan besar seperti kernel Linux. Kernel Linux terawal menggunakan BitKeeper untuk kawalan versi, tetapi kemudiannya Linus Torvalds mereka bentuk sistem kawalan versi Git yang lebih baik berdasarkan pengalamannya dengan BitKeeper dan Monotone. Pada asalnya, Git direka hanya sebagai alat kawalan versi peringkat rendah untuk digunakan sebagai alat operasi bagi sistem kawalan versi lain (SCM), dan kemudiannya secara beransur-ansur berkembang menjadi sistem kawalan versi yang lengkap.

Menariknya, apabila Linus Torvalds mula-mula beralih kepada Git untuk kawalan versi, Git terlalu kompleks, dan banyak konsep kawalan versi terlalu berbeza daripada sebelumnya, yang juga mendapat tentangan daripada komuniti sumber terbuka di seluruh dunia. Walau bagaimanapun, selepas bertahun-tahun usaha dan pembangunan, alat untuk mengendalikan Git menjadi semakin matang, secara beransur-ansur meredakan tentangan itu. Menurut penyelidikan pasaran pada tahun 2013, 30% projek sumber terbuka di seluruh dunia telah beralih kepada Git untuk kawalan versi. Ini ialah bahagian pasaran yang menakjubkan, bermakna Git sememangnya mempunyai ciri-ciri yang memukau, dan ia perlu dikaji dengan baik!

Bercakap tentang seni bina Git, ia sepenuhnya berdasarkan pengalaman Linus Torvalds dalam menyelenggara projek besar seperti kernel Linux dan pengalamannya yang kaya dalam pengoptimuman sistem fail. Disebabkan ini, Git merangkumi reka bentuk penting berikut:

* Sokongan kuat untuk model pembangunan bukan linear (model pembangunan teragih)
  * Git mempunyai mekanisme pencabangan dan cantuman yang pantas, termasuk alat grafik untuk memaparkan laluan sejarah perubahan versi.
  * Git sangat menekankan pencabangan dan cantuman, jadi dalam proses kawalan versi, anda akan sentiasa melakukan operasi pencabangan dan cantuman.
  * Mekanisme pencabangan Git sangat ringan, tanpa beban. Setiap cabang hanyalah penunjuk rujukan kepada commit tertentu.
* Model pembangunan teragih
  * Semua orang yang mengambil bahagian dalam pembangunan Git akan mempunyai sejarah pembangunan yang lengkap.
  * Apabila pembangun mula-mula mengklon repositori Git, ia sepenuhnya bersamaan dengan "sandaran lengkap" repositori Git ini.
  * Semua fail yang diubah dan rekod sejarah dalam keseluruhan repositori disimpan dalam repositori setempat.
* Serasi dengan sistem pengendalian sedia ada
  * Repositori Git sebenarnya hanyalah folder dengan pelbagai fail konfigurasi berkaitan dan pelbagai fail objek blob.
  * Repositori Git boleh diterbitkan dalam apa jua cara, jadi anda boleh menggunakan HTTP, FTP, rsync, SSH, atau protokol Git itu sendiri sebagai medium untuk mengakses repositori Git, dengan keserasian yang sangat tinggi.
* Pengendalian projek besar yang cekap
  * Oleh kerana repositori yang lengkap akan diklon ke mesin setempat, dan repositori itu mengandungi fail lengkap serta rekod perubahan versi, kelajuan pelbagai operasi fail dalam kawalan versi akan menjadi ratusan kali lebih pantas daripada akses jauh secara langsung.
  * Ini juga bermakna kawalan versi Git tidak akan menjadi perlahan apabila projek menjadi lebih besar dan fail menjadi lebih banyak.
* Perlindungan rekod sejarah
  * Dalam proses kawalan versi Git, setiap commit menjana nombor id hash, dan setiap versi dalam proses perubahan merujuk kepada id hash ini. Selagi id hash tidak dapat dipadankan, Git tidak akan berfungsi. Jadi apabila projek menjadi lebih besar dan lebih banyak salinan repositori diklon, anda hampir tidak boleh mengusik kandungan fail atau rekod versi.
  * **Ingat: Semua orang mempunyai repositori yang lengkap. Jika anda mengubah yang asal, repositori semua orang tidak lagi boleh dicantumkan kembali ke repositori asal, jadi anda hampir tidak boleh mengusik rekod versi sewenang-wenangnya.**
* Reka bentuk berasaskan kit alat
  * Git direka sebagai satu siri perisian alat (alat baris perintah). Anda boleh menggabungkan penggunaan alat yang berbeza dengan mudah dan dengan fleksibiliti yang tinggi.
* Strategi cantuman boleh palam
  * Git mempunyai mekanisme "cantuman tidak lengkap" yang direka dengan baik dan berbilang algoritma yang boleh melengkapkan cantuman, dan akhirnya memaklumkan pengguna mengapa cantuman automatik tidak dapat dilengkapkan atau memberitahu anda bahawa cantuman manual diperlukan.
* Mekanisme pengumpulan sampah pasif
  * Apabila menggunakan Git, jika anda ingin mengganggu operasi semasa atau memulihkan operasi sebelumnya, ia boleh dilakukan. Anda tidak perlu bimbang tentang kemungkinan menggunakan perintah yang salah atau perintah terhenti di tengah jalan semasa pelaksanaan.
  * Mekanisme pengumpulan sampah Git sebenarnya ialah fail tidak berguna yang tertinggal dalam sistem fail. Mekanisme pengumpulan sampah ini hanya akan dilaksanakan secara automatik selepas objek tidak berguna ini terkumpul untuk satu tempoh masa, atau anda juga boleh mengeluarkan perintah untuk membersihkannya sendiri. Contohnya: git gc --prune
* Pembungkusan objek secara berkala
  * "Objek" yang kami sebutkan dalam Git sebenarnya mewakili fail dalam repositori. Dalam proses perubahan versi, kod atau fail lain dalam projek akan dikemas kini. Setiap kali ia dikemas kini, selagi kandungan fail berbeza, "objek" baharu akan dicipta, dan semua fail dengan kandungan berbeza ini akan dikekalkan.
  * Anda boleh bayangkan bahawa apabila projek menjadi lebih besar dan mempunyai lebih banyak versi, akan ada semakin banyak objek. Walaupun setiap fail boleh dimampatkan secara individu untuk menjadikan fail lebih kecil, terlalu banyak fail masih akan menjadikan akses fail semakin tidak cekap. Oleh itu, reka bentuk Git mempunyai mekanisme yang boleh membungkus sekumpulan "objek" lama secara automatik ke dalam packfile untuk meningkatkan kecekapan akses fail.
  * Fail yang baru ditambah itu masih akan wujud sebagai fail tunggal, yang juga bermakna "fail" dalam repositori Git ialah "objek" Git, tetapi ia perlu dibungkus semula sekali-sekala.
  * Agaknya, Git akan melaksanakan tindakan seperti pembungkusan semula secara automatik, tetapi anda masih boleh mengeluarkan perintah untuk melaksanakannya sendiri. Contohnya: git gc
  * Jika anda ingin menyemak sama ada sistem fail yang diselenggara oleh Git adalah lengkap, anda boleh melaksanakan perintah berikut: git fsck

Berkenaan sistem kawalan versi teragih Git, izinkan saya mengulangi beberapa perkara:

* Git boleh mengendalikan kawalan versi sepenuhnya tanpa sokongan bahagian pelayan kerana semua orang mempunyai salinan lengkap repositori.
* Oleh kerana semua orang mempunyai salinan lengkap repositori, setiap kali anda commit perubahan versi, anda hanya commit ke repositori setempat, jadi kelajuan commit sangat pantas, dan anda tidak memerlukan sambungan rangkaian, yang boleh menjimatkan masa pembangunan dengan banyak.
* Oleh kerana semua orang mempunyai salinan lengkap repositori, ini bermakna apabila menggunakan kawalan versi Git, tidak ada perkara seperti "kawalan kebenaran." Setiap ahli boleh mengklon repositori dan boleh commit perubahan secara setempat tanpa sebarang sekatan kebenaran. Apabila menggunakan Git, satu-satunya kebenaran yang boleh ditetapkan ialah sama ada anda mempunyai kebenaran untuk mengakses repositori huluan atau repositori jauh.
* Jika anda perlu bertukar versi yang diubah dengan orang lain, anda boleh berbuat demikian melalui "cantuman" pada bila-bila masa. Git mempunyai keupayaan penjejakan cantuman yang sangat berkuasa.
* Untuk mencantumkan versi berbilang orang, anda hanya perlu mempunyai kebenaran atau akses kepada repositori yang dikongsi.
  **Contohnya: Pada pelayan yang sama, anda boleh berkongsi melalui kebenaran folder, atau mengakses repositori Git pelayan lain dari jauh melalui SSH, atau berkongsi repositori Git melalui pelayan web, dsb.**
