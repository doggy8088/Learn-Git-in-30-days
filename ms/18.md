# Hari 18: Membetulkan Sejarah Versi yang Telah Di-commit Bahagian 1 (reset & amend)

Apabila menggunakan Git untuk kawalan versi, kami menggunakan `git commit` untuk mencipta banyak versi. Oleh kerana Git ialah sistem kawalan versi teragih, berbanding sistem kawalan versi berpusat seperti Subversion atau TFVC, Git mempunyai kurang reka bentuk kebenaran untuk kawalan versi. Git menyediakan lebih banyak mekanisme untuk "mengubah suai rekod versi," membolehkan anda menyusun perkara terlebih dahulu sebelum "berkongsi" versi dengan orang lain.

## Prinsip Asas Kawalan Versi

Apabila melakukan kawalan versi, sama ada menggunakan Git, Subversion, atau TFVC, mengekalkan rekod versi yang baik membantu kami menjejak sejarah kemas kini setiap versi (apabila kami perlu melakukan ini). Dalam pengalaman peribadi saya, kami jarang mempunyai peluang atau keinginan untuk menjejak proses pembangunan perisian dalam projek. Banyak projek kami telah mengumpul beribu-ribu rekod versi - siapa yang mempunyai masa untuk menyiasat sejarah itu?

Walau bagaimanapun, dalam praktiknya, apabila pepijat perisian berlaku, kami perlu menjejak rekod sejarah pepijat tertentu untuk mengetahui punca sebenar pepijat itu. Pada masa inilah kawalan versi membawa nilai terbesar.

Oleh itu, cara mengekalkan "rekod versi" yang baik juga sangat penting. Berikut ialah beberapa prinsip kawalan untuk dikongsi:

* Buat versi untuk setiap pengubahsuaian ciri kecil, memudahkan penjejakan perubahan
* Jangan sekali-kali mengumpul banyak pengubahsuaian sebelum mencipta "versi besar"
* Betulkan ciri secara logik dan mengikut tertib, memastikan pembetulan versi yang berkaitan di-commit mengikut turutan untuk penjejakan yang lebih mudah

Walau bagaimanapun, manusia membuat kesilapan - siapa yang boleh memastikan bahawa semua orang dalam pasukan sentiasa boleh mengikuti prinsip di atas untuk kawalan versi? Siapa yang tidak hanya "mengubah suai mengikut fikiran"? Keperluan sedemikian menjadi tidak praktikal. Oleh itu, kami memerlukan mekanisme untuk "mengubah suai versi" supaya apabila versi diserahkan kepada pelayan jauh, ia sudah berada dalam keadaan sempurna.

## Sebab Membetulkan Sejarah Commit

Setakat ini, kami belum menyebutkan butiran "repositori jauh," jadi kebanyakan operasi Git masih menumpukan pada operasi setempat, iaitu kawalan versi dalam direktori kerja, dengan repositori ini terletak dalam direktori `.git/` anda. Walau bagaimanapun, kami akan membincangkan aplikasi "repositori jauh" tidak lama lagi, apabila lebih daripada seorang akan mempunyai repositori, dan lebih banyak butiran perlu diberi perhatian.

Membenarkan semua orang mengubah suai sejarah commit secara sewenang-wenangnya mungkin kedengaran pelik kepada orang yang biasa dengan Subversion atau TFVC, kerana semua orang biasa menyambung secara berpusat ke pelayan kawalan versi, menggunakan repositori berpusat. Jika seseorang boleh mengusik rekod sejarah secara sewenang-wenangnya, bolehkah ia masih dipanggil kawalan versi?

Sebenarnya, dalam kawalan versi Git, konsepnya adalah sama. Selagi repositori yang sama dikongsi oleh berbilang orang, jika seseorang mengusik versi secara sewenang-wenangnya, kawalan versi Git juga akan gagal berfungsi dengan betul.

Jadi, senario penggunaan apakah yang memerlukan pengubahsuaian rekod versi? Anda boleh merujuk perkara berikut.

Andaikan kami kini mempunyai tiga versi [A] -> [B] -> [C]:

* Anda mungkin mendapati bahawa versi [C] telah di-commit secara salah dan mesti memadam semua perubahan dalam versi ini
* Anda mungkin mendapati selepas membuat commit [C] bahawa versi ini hanya mempunyai kod ujian, dan anda ingin memadamnya
* Sesetengah mesej rekod versi mempunyai kesilapan taip, dan anda ingin mengubah suai teks mesej tanpa menjejaskan sejarah perubahan fail
* Anda mungkin ingin melaraskan tertib commit versi ini kepada [A] -> [C] -> [B] untuk menjadikan evolusi versi lebih logik
* Anda mendapati bahawa versi [B] terlupa memasukkan fail penting sebelum membuat commit, dan anda ingin memulihkan perubahan ini selepas itu
* Apabila anda merancang untuk "berkongsi" cabang, anda mendapati kecacatan kod dan boleh membetulkannya sebelum berkongsi

## Nota Penting untuk Membetulkan Sejarah Commit

Git mengekalkan mekanisme untuk "mengubah suai rekod sejarah versi," terutamanya berharap bahawa selepas anda telah "mengurus sendiri versi" hingga tahap tertentu, anda boleh menyusun pelbagai maklumat dalam rekod versi sendiri, supaya selepas anda "menerbitkan" versi, orang lain boleh memahami dengan lebih jelas pengubahsuaian apa yang anda buat pada versi ini.

Oleh itu, apabila mengubah suai rekod sejarah versi, beberapa perkara mesti diberi perhatian khas:

* Repositori boleh mempunyai banyak cabang (nama cabang lalai ialah `master`)
* Unit minimum untuk berkongsi kod sumber Git ialah mengikut "cabang"
* Anda boleh mengubah suai versi pada cabang secara sewenang-wenangnya, selagi anda belum "berkongsi"nya dengan orang lain
* **Sebaik sahaja anda "berkongsi" cabang tertentu dengan orang lain, jangan ubah suai rekod sejarah versi yang "dikongsi" itu lagi!**

## Memahami git commit --amend

Pilihan `--amend` membolehkan anda mengubah suai commit paling terkini. Ini berguna apabila anda:

* Ingin menukar mesej commit
* Terlupa memasukkan beberapa fail
* Perlu membetulkan kesilapan kecil dalam commit terakhir

### Menukar Mesej Commit Terakhir

```
git commit --amend -m "New commit message"
```

### Menambah Fail ke Commit Terakhir

```
# Make changes or add forgotten files
git add forgotten-file.txt

# Amend the commit
git commit --amend --no-edit
```

Bendera `--no-edit` mengekalkan mesej commit sedia ada.

### Amend Interaktif

Untuk menyunting mesej commit dalam editor anda:

```
git commit --amend
```

Ini membuka editor yang anda konfigurasikan di mana anda boleh mengubah suai mesej commit.

## Memahami git reset

`git reset` ialah perintah berkuasa yang boleh:

* Menggerakkan penunjuk cabang semasa
* Mengubah suai indeks (kawasan pementasan)
* Mengubah suai direktori kerja

Terdapat tiga mod reset:

1. **--soft**: Menggerakkan HEAD, mengekalkan indeks dan direktori kerja tidak berubah
2. **--mixed** (lalai): Menggerakkan HEAD, me-reset indeks, mengekalkan direktori kerja tidak berubah
3. **--hard**: Menggerakkan HEAD, me-reset indeks dan direktori kerja

## Reset Lembut (Soft Reset)

Menggerakkan penunjuk cabang tetapi mengekalkan perubahan anda dipentaskan:

```
git reset --soft HEAD~1
```

Ini membuat asal commit terakhir tetapi meninggalkan perubahan anda dalam indeks, bersedia untuk di-commit semula.

## Reset Campuran (Mixed Reset)

Menggerakkan penunjuk cabang dan menyahpentaskan perubahan:

```
git reset HEAD~1
# or
git reset --mixed HEAD~1
```

Ini membuat asal commit terakhir dan menyahpentaskan perubahan, tetapi perubahan kekal dalam direktori kerja anda.

## Reset Keras (Hard Reset)

Membuang commit dan semua perubahan sepenuhnya:

```
git reset --hard HEAD~1
```

**Amaran**: Ini membuang perubahan secara kekal. Gunakan dengan berhati-hati!

## Me-reset ke Commit Tertentu

Anda boleh me-reset ke mana-mana commit:

```
# Using commit hash
git reset --hard a1b2c3d

# Using relative reference
git reset --soft HEAD~3
```

## Menyahpentaskan Fail

Untuk menyahpentaskan fail tanpa kehilangan perubahan:

```
git reset HEAD file.txt
# or
git restore --staged file.txt
```

## Memulih daripada Reset

Jika anda me-reset secara tersilap, anda biasanya boleh memulih menggunakan reflog:

```
git reflog
git reset --hard HEAD@{2}
```

## Reset vs Revert

Perbezaan penting:

* **reset**: Menulis semula sejarah (gunakan untuk commit setempat yang belum di-push)
* **revert**: Mencipta commit baharu yang membuat asal perubahan (selamat untuk sejarah yang dikongsi)

## Kes Penggunaan Lazim

### Buat Asal Commit Terakhir, Kekalkan Perubahan

```
git reset HEAD~1
```

### Buat Asal Commit Terakhir, Buang Perubahan

```
git reset --hard HEAD~1
```

### Pisahkan Satu Commit kepada Berbilang

```
git reset HEAD~1
git add file1.txt
git commit -m "First part"
git add file2.txt
git commit -m "Second part"
```

### Tukar Beberapa Commit Terakhir

```
git reset --soft HEAD~3
# Make changes
git commit -m "Combined commit"
```

## Amaran dan Amalan Terbaik

1. **Jangan sekali-kali me-reset sejarah awam**: Jangan reset commit yang telah di-push ke repositori yang dikongsi
2. **Gunakan --amend dengan berhati-hati**: Hanya amend commit yang belum di-push
3. **Pertimbangkan alternatif**: Untuk sejarah yang dikongsi, gunakan `git revert` sebagai gantinya
4. **Semak dua kali**: Terutamanya sebelum menggunakan `--hard`
5. **Ketahui reflog anda**: Ia boleh menyelamatkan anda daripada kesilapan

## Ringkasan Hari Ini

`git commit --amend` dan `git reset` ialah alat berkuasa untuk membetulkan sejarah commit setempat. `--amend` sesuai untuk pembetulan pantas pada commit terakhir, manakala `reset` memberi anda lebih kawalan ke atas berbilang commit. Walau bagaimanapun, kedua-duanya harus digunakan dengan berhati-hati, terutamanya untuk commit yang telah dikongsi dengan orang lain.

Izinkan saya menyusun semula perintah dan parameter Git yang dipelajari hari ini:

* git commit --amend
* git commit --amend --no-edit
* git reset --soft
* git reset --mixed
* git reset --hard
* git reset HEAD~n
* git reflog
