# Day 26: 같은 원격 리포지토리에서 여러 사람이 작업하기

여러 사람이 같은 리포지토리에서 작업할 때는 조율과 Git 워크플로에 대한 이해가 매우 중요해집니다. 이 글에서는 팀 협업을 위한 모범 사례와 흔한 시나리오를 살펴보겠습니다.

## 팀 협업의 흔한 어려움

1. **병합 충돌**: 여러 사람이 같은 파일을 편집하는 경우
2. **브랜치 분기**: 로컬과 원격이 동기화되지 않는 경우
3. **커밋 유실**: 실수로 다른 사람의 작업을 덮어쓰는 경우
4. **소통의 공백**: 다른 사람이 무엇을 작업 중인지 모르는 경우

## 기본 팀 워크플로

### 일상 워크플로

```
# Morning: Get latest changes
git pull origin main

# Create feature branch
git checkout -b feature-name

# Work and commit frequently
git add .
git commit -m "Progress on feature"

# Before finishing: update with latest main
git checkout main
git pull origin main
git checkout feature-name
git merge main

# Resolve any conflicts

# Push your branch
git push origin feature-name

# Create pull request for review
```

### 최신 상태 유지하기

변경 사항을 정기적으로 fetch합니다.

```
# Check what's changed
git fetch origin

# View remote changes
git log main..origin/main

# Merge if appropriate
git merge origin/main
```

## 동시 작업 처리하기

### 시나리오 1: 같은 파일, 다른 줄

보통 자동으로 병합됩니다.

```
git pull origin main
# If auto-merge succeeds, you're done!
```

### 시나리오 2: 같은 파일, 같은 줄

수동으로 해결해야 합니다.

```
git pull origin main
# Conflict!

# Edit conflicting files
# Remove markers: <<<<<<<, =======, >>>>>>>
# Keep the correct changes

# Stage resolved files
git add resolved-file.txt

# Complete the merge
git commit
```

### 시나리오 3: 누군가가 Rebase한 경우

브랜치가 공유되고 있으면 큰 문제가 될 수 있습니다.

```
# If someone rebased a shared branch
git fetch origin

# You need to rebase your work
git rebase origin/feature-branch

# Or start fresh
git reset --hard origin/feature-branch
```

## 코드 리뷰 과정

### 좋은 풀 리퀘스트 만들기

1. **설명적인 제목**: "Add user authentication feature"
2. **자세한 설명**:
   * 이 PR은 무엇을 하나요?
   * 왜 이 변경이 필요한가요?
   * 어떻게 테스트했나요?
3. **작게 유지하기**: 리뷰하기 쉽습니다
4. **PR 하나에 관심사 하나**: 기능과 수정을 섞지 마세요
5. **main으로 업데이트**: 깔끔하게 병합되도록 하세요

### 풀 리퀘스트 리뷰하기

1. **코드를 확인하세요**: 로직과 스타일을 봅니다
2. **가능하면 로컬에서 테스트하세요**
3. **건설적인 피드백을 남기세요**
4. **승인하거나 변경을 요청하세요**
5. **준비되면 병합하세요**

## 팀 충돌 해결하기

### 소통이 먼저입니다

* **팀과 대화하세요**: 많은 문제를 예방할 수 있습니다
* **PR 댓글을 사용하세요**: 질문하고 접근 방식을 논의하세요
* **결정을 문서화하세요**: PR 설명이나 댓글을 업데이트하세요

### 기술적 해결책

#### 충돌 해결하기

```
# Update your branch
git fetch origin
git merge origin/main

# Resolve conflicts in files
# Stage changes
git add .

# Complete merge
git commit
```

#### 중단하고 처음부터 다시 하기

```
# If resolution is too complex
git merge --abort

# Talk to the other developer
# Coordinate who makes what changes
```

## 브랜치 보호 규칙

GitHub에서 중요한 브랜치를 보호합니다.

1. **풀 리퀘스트 리뷰 필수**
2. **상태 검사 필수**(CI/CD)
3. **선형 이력 강제**
4. **관리자도 포함**

설정 위치: Settings > Branches > Branch protection rules

## 지속적 통합

CI를 사용해 문제를 조기에 발견합니다.

```yaml
# Example .github/workflows/test.yml
name: Tests
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v2
      - run: npm install
      - run: npm test
```

## 소통 도구

### 커밋 메시지

규약을 따릅니다.

```
<type>(<scope>): <subject>

<body>

<footer>
```

예시는 다음과 같습니다.

```
feat(auth): add user login functionality

Implement JWT-based authentication with email and password.
Includes password hashing with bcrypt and token refresh.

Closes #123
```

### 풀 리퀘스트 템플릿

`.github/pull_request_template.md`를 만듭니다.

```markdown
## Description
<!-- Describe your changes -->

## Type of Change
- [ ] Bug fix
- [ ] New feature
- [ ] Breaking change

## Testing
<!-- How was this tested? -->

## Checklist
- [ ] Tests pass
- [ ] Documentation updated
- [ ] No merge conflicts
```

## 대규모 팀 다루기

### 기능 플래그

아직 준비되지 않은 코드를 배포합니다.

```javascript
if (featureFlags.newUI) {
  return <NewUI />;
} else {
  return <OldUI />;
}
```

### 릴리스 브랜치

개발과 릴리스를 분리합니다.

```
main (production)
├── release/v2.0
├── release/v1.9
└── develop (integration)
    ├── feature/login
    ├── feature/dashboard
    └── feature/reports
```

## 모범 사례 요약

1. **push하기 전에 pull**: 항상 최신 변경 사항을 먼저 가져오세요
2. **자주 커밋**: 작고 논리적인 커밋을 만드세요
3. **정기적으로 push**: 작업을 공유하고 피드백을 받으세요
4. **브랜치 사용**: main을 안정적으로 유지하세요
5. **테스트 작성**: 다른 사람이 발견하기 전에 문제를 잡으세요
6. **코드 리뷰**: 서로에게 배우세요
7. **소통**: 필요하다면 과할 정도로 소통하세요
8. **문서화**: README, 위키, 댓글을 활용하세요
9. **인내심**: 충돌은 일어나는 법입니다. 차근차근 해결하세요
10. **다른 사람을 돕기**: 팀의 성공이 곧 여러분의 성공입니다

## 오늘의 요약

Git을 활용한 성공적인 팀 협업에는 기술적 역량과 좋은 소통이 모두 필요합니다. 흔한 워크플로를 이해하고, 충돌을 우아하게 처리하며, 풀 리퀘스트와 CI/CD 같은 도구를 사용하면 팀이 원활하게 함께 일할 수 있습니다.

오늘 배운 Git 명령어와 매개변수를 다시 정리하겠습니다.

* git pull origin main
* git fetch origin
* git merge origin/main
* git rebase origin/branch
* git push origin branch
* git log main..origin/main
