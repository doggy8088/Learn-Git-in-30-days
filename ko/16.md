# Day 16: git reflog로 변경 이력 추적하기

Git 버전 관리 명령어를 배우는 것은 어렵지 않지만, Git이 실제로 리포지토리에 무엇을 하는지 이해하는 것은 상당히 어려울 수 있습니다. Git의 핵심 개념과 작동 원리를 점차 이해하게 되면, Git 리포지토리의 버전 변경을 효과적으로 제어할 수 있습니다. 이 글에서는 Git이 모든 버전의 변경 이력을 어떻게 기록하는지 설명합니다.

## git reflog 이해하기

`git reflog`(참조 로그, reference log)는 로컬 리포지토리에서 브랜치의 팁과 기타 참조가 언제 업데이트되었는지를 기록하는 메커니즘입니다. Git의 기본 원리와 개체 구조를 완전히 이해하기 전에는 버전 기록 과정을 진정으로 이해할 수 없습니다. 버전 기록 과정을 이해하지 못하면 당연히 "내 버전이 어디로 갔지?"라고 걱정하게 됩니다. "버전 관리를 사용하니 모든 버전이 보존되므로, 마음껏 코드를 수정하세요"라는 말을 들어 본 적이 있을 것입니다. 이것을 아는 것과, 하는 방법을 아는 것은 별개이며, 실제로 해낼 수 있는지는 또 다른 문제입니다.

다행히 Git에는 엄격한 로깅 메커니즘이 있으며, 이 메커니즘은 매우 개방적입니다. 로그 파일은 모두 텍스트 형식이라 이해하기가 꽤 쉽습니다. 이 버전 기록 과정을 설명해 보겠습니다.

reflog는 특히 다음에 유용합니다.

* 어떤 브랜치에서도 더 이상 도달할 수 없는 커밋 찾기
* 잘못된 reset이나 rebase로부터 복구하기
* 리포지토리에서 자신이 한 작업 이해하기
* 실수로 한 변경 되돌리기

## logs 디렉터리

어떤 Git 작업 디렉터리의 `.git/` 폴더에 들어가면 `logs` 디렉터리를 볼 수 있습니다. 이 `logs` 폴더에는 "현재 브랜치"의 버전 변경 이력을 기록하는 `HEAD` 파일이 들어 있습니다.

파일 내용은 다음과 같습니다(개체 ID는 가독성을 위해 축약했습니다).

```
0000000 f5685e0 Will <xxxx@gmail.com> 1381718394 +0800	commit (initial): Initial commit
f5685e0 38d924f Will <xxxx@gmail.com> 1381718395 +0800	commit: a.txt: set 1 as content
38d924f efa1e0c Will <xxxx@gmail.com> 1381734238 +0800	commit: test
efa1e0c af493e5 Will <xxxx@gmail.com> 1381837967 +0800	commit: Add c.txt
```

## 기본 사용법

reflog를 보려면 다음을 사용합니다.

```
git reflog
```

이렇게 하면 최근 작업의 목록이 역연대순으로 표시됩니다. 텍스트 파일에서는 맨 위에 "첫 번째 버전"이 보이지만, `git reflog`를 통하면 "최신 버전"이 먼저 표시되고 "첫 번째 버전"이 마지막에 표시됩니다.

각 항목은 다음을 표시합니다.
* 커밋 해시
* 참조(보통 HEAD)
* 수행된 작업
* 커밋 메시지

## Reflog 형식

출력은 다음과 같습니다.

```
a1b2c3d HEAD@{0}: commit: Add new feature
e4f5g6h HEAD@{1}: checkout: moving from master to feature-branch
i7j8k9l HEAD@{2}: reset: moving to HEAD~1
```

`HEAD@{n}` 표기는 HEAD의 n번째 이전 값을 가리킵니다. 여기서 이력 로그의 각 버전에는 로그 파일에서 이 버전의 위치를 나타내는 번호가 있습니다. `HEAD@{0}`는 항상 현재 브랜치의 "최신 버전", 즉 이 "브랜치"에서 수행한 가장 최근의 Git 작업을 나타냅니다. Git에 가하는 모든 버전 변경은 완전히 기록됩니다.

## 실수로 한 변경으로부터 복구하기

초보자가 Git을 처음 사용할 때는 잘못된 명령어를 실수로 실행할 수 있는데, 예를 들어 `git merge` 중 충돌이 발생하거나, 원격 리포지토리에서 최신 버전을 가져오기 위해 `git pull`을 실행하다가 실수가 생기는 경우가 있습니다. 이러한 상황에서는 특수한 "참조 이름"인 `HEAD@{n}`을 사용해 이 버전을 "찾아내고", 현재 Git 리포지토리 버전을 이전 버전으로 복원할 수 있습니다.

예를 들어 가장 최근의 버전 기록을 "취소"하고 싶다면, `git reset HEAD@{1} --hard`를 사용해 변경을 복원할 수 있습니다. 이는 원래 `HEAD@{0}`에 있던 변경이 삭제된다는 의미입니다. 그러나 Git에서는 모든 변경이 기록되며, `git reset "HEAD@{1}" --hard`를 실행한 여러분의 작업도 포함됩니다.

이것은 무엇을 의미할까요? 어떤 Git 명령어를 실행할 때도 더 이상 데이터가 손실될까 걱정할 필요가 없다는 의미입니다. 입력한 명령어가 아무리 잘못되어도, 이미 리포지토리에 들어 있는 모든 파일은 보존되며 손실될 가능성이 전혀 없습니다. 따라서 방금 실행한 `git reset "HEAD@{1}" --hard` 작업을 되돌리고 싶다면, `git reset "HEAD@{1}" --hard`를 다시 실행하기만 하면 됩니다. 정말 멋지지 않나요!

## 자세한 Reflog 보기

더 자세한 정보를 보려면 다음을 사용합니다.

```
git reflog show --all
```

특정 브랜치의 reflog를 보려면 다음을 사용합니다.

```
git reflog show branch-name
```

## Reflog를 사용해 커밋 복구하기

실수로 reset하거나 커밋을 잃어버린 경우, reflog를 사용해 복구할 수 있습니다.

```
# Find the commit you want to recover
git reflog

# Reset to that commit
git reset --hard HEAD@{2}
```

또는 커밋 해시를 직접 사용합니다.

```
git reset --hard a1b2c3d
```

## 삭제된 브랜치 복구하기

실수로 브랜치를 삭제한 경우:

```
# Find the commit where the branch was deleted
git reflog

# Recreate the branch
git branch branch-name HEAD@{3}
# or
git branch branch-name <commit-hash>
```

## Reflog 만료

기본적으로 reflog 항목은 도달 가능한 커밋의 경우 90일, 도달할 수 없는 커밋의 경우 30일 후에 만료됩니다. 이를 구성할 수 있습니다.

```
git config gc.reflogExpire "90 days"
git config gc.reflogExpireUnreachable "30 days"
```

## Reflog 정리하기

reflog 항목을 수동으로 정리하려면 다음을 사용합니다.

```
# Remove old reflog entries
git reflog expire --expire=now --all

# Run garbage collection
git gc --prune=now
```

## Reflog의 한계

기억해야 할 중요한 사항:

* Reflog는 로컬 전용으로, 다른 사람과 공유되지 않습니다
* Reflog는 파일이 아니라 리포지토리의 변경 사항을 추적합니다
* 커밋을 복구하는 데 도움이 되지만, 커밋되지 않은 변경은 복구할 수 없습니다

## 실용적인 예시

### 예시 1: Hard Reset 되돌리기

```
# You accidentally reset
git reset --hard HEAD~3

# Find the old position
git reflog

# Restore to the old position
git reset --hard HEAD@{1}
```

### 예시 2: 잘못된 Rebase 후 복구하기

```
# After a problematic rebase
git reflog

# Find the commit before the rebase (usually labeled "rebase finished")
git reset --hard HEAD@{5}
```

## 오늘의 요약

`git reflog`는 많은 Git 실수로부터 여러분을 구해 줄 수 있는 강력한 안전 기능입니다. reset, rebase, 브랜치 삭제와 같은 작업으로부터 복구해야 할 때 특히 가치가 있습니다. 정기적인 백업을 대체할 수는 없지만, 로컬 복구를 위한 귀중한 도구입니다.

오늘 배운 Git 명령어와 매개변수를 다시 정리하겠습니다.

* git reflog
* git reflog show
* git reflog show --all
* git reset --hard HEAD@{n}
* git branch branch-name HEAD@{n}
* git reflog expire
* git gc
