# Day 22: 커밋된 버전 이력 수정하기 Part 4 (rebase)

지금까지 버전을 수정하는 세 가지 방법을 살펴보았습니다. 엄밀히 말하면 `git revert`와 `git cherry-pick`은 진정한 의미의 "버전 이력 기록 수정"은 아닙니다. 이미 커밋된 버전을 "다시 적용"하거나 "역방향으로 적용"하는 것이기 때문입니다. 이 글에서는 커밋 기록을 실제로 수정하는 데 사용되는 Git의 Rebase 메커니즘을 설명하겠습니다. 중요하면서도 강력한 기능입니다.

## git rebase 이해하기

Rebase는 Git에서 가장 강력하지만 잠재적으로 위험할 수 있는 기능 중 하나입니다. 커밋 이력을 다시 써서 더 깔끔하고 선형적으로 만들 수 있습니다.

Rebase란 일련의 커밋을 새로운 베이스 커밋으로 옮기거나 결합하는 과정입니다. 전체 이력을 보존하는 병합과 달리, rebase는 이력을 다시 써서 선형적인 진행을 만듭니다.

## 기본 Rebase

기본적인 rebase 작업은 다음과 같습니다.

```
# On feature branch
git checkout feature-branch

# Rebase onto main
git rebase main
```

이렇게 하면 `feature-branch`의 모든 커밋이 `main` 위에 재생됩니다.

## Rebase의 동작 방식

rebase를 실행하면 다음이 수행됩니다.

1. Git이 현재 브랜치와 대상 브랜치의 공통 조상을 찾습니다
2. 그 조상 이후의 현재 브랜치 커밋을 모두 저장합니다
3. 현재 브랜치를 대상 브랜치로 reset합니다
4. 저장해 둔 커밋을 하나씩 다시 적용합니다

## Rebase vs Merge

**Merge**:
* 전체 이력을 보존합니다
* 브랜치가 분기되고 병합된 시점을 보여 줍니다
* 공유 브랜치에서도 안전합니다
* 병합 커밋을 만듭니다

**Rebase**:
* 선형 이력을 만듭니다
* 더 깔끔하고 이해하기 쉽습니다
* 이력을 다시 씁니다(공유 브랜치에서는 위험합니다)
* 병합 커밋이 없습니다

시각적 비교는 다음과 같습니다.

```
# Before rebase
     C---D feature
    /
A---B---E---F main

# After git rebase main (on feature)
             C'---D' feature
            /
A---B---E---F main

# After git merge feature (on main)
     C---D 
    /     A---B---E---F---G main
```

## Rebase 중 충돌 처리하기

충돌이 발생하면 다음을 수행합니다.

```
# Git pauses the rebase
# Resolve conflicts in the files
# Stage the resolved files
git add <resolved-files>

# Continue the rebase
git rebase --continue
```

rebase를 중단하려면 다음을 사용합니다.

```
git rebase --abort
```

현재 커밋을 건너뛰려면 다음을 사용합니다.

```
git rebase --skip
```

## 대화형 Rebase

대화형 rebase를 사용하면 커밋을 완전히 제어할 수 있습니다.

```
git rebase -i HEAD~3
```

이렇게 하면 편집기가 열리고 다음 작업을 할 수 있습니다.

* **pick**: 커밋을 그대로 유지합니다
* **reword**: 커밋 메시지를 변경합니다
* **edit**: 커밋을 수정하기 위해 멈춥니다
* **squash**: 이전 커밋과 결합하고 두 메시지를 모두 유지합니다
* **fixup**: 이전 커밋과 결합하고 이 메시지는 버립니다
* **drop**: 커밋을 완전히 제거합니다

대화형 rebase 편집기의 예시는 다음과 같습니다.

```
pick abc123 Add feature A
reword def456 Add feature B
squash ghi789 Fix typo in feature B
drop jkl012 Experimental change
```

## 흔한 대화형 Rebase 작업

### 커밋 합치기(Squash)

여러 커밋을 하나로 결합합니다.

```
git rebase -i HEAD~3

# In the editor, change:
pick abc123 First commit
pick def456 Second commit
pick ghi789 Third commit

# To:
pick abc123 First commit
squash def456 Second commit
squash ghi789 Third commit
```

### 커밋 순서 바꾸기

대화형 rebase 편집기에서 줄 순서를 바꾸기만 하면 됩니다.

### 커밋 편집하기

```
git rebase -i HEAD~3

# Change "pick" to "edit" for the commit you want to modify
# Git will stop at that commit
# Make your changes
git add .
git commit --amend
git rebase --continue
```

## 다른 브랜치 위로 Rebase하기

```
git rebase --onto new-base old-base feature-branch
```

이렇게 하면 `feature-branch`에서 `old-base` 이후의 커밋이 `new-base` 위로 이동합니다.

## Autosquash

fixup 커밋을 자동으로 합칩니다.

```
# Create a fixup commit
git commit --fixup <commit-to-fix>

# Later, rebase with autosquash
git rebase -i --autosquash main
```

## Rebase의 황금률

**공유 리포지토리에 push된 커밋은 절대로 rebase하지 마세요!**

Rebase는 이력을 다시 쓰므로, 그 커밋을 기반으로 작업한 다른 사람들에게 큰 문제를 일으킬 수 있습니다.

안전한 경우:
* 아직 push하지 않은 로컬 커밋
* 본인이 소유한 기능 브랜치
* 풀 리퀘스트를 만들기 전에 정리하는 경우

위험한 경우:
* Main/master 브랜치
* 공유 기능 브랜치
* 다른 사람이 기반으로 작업했을 수 있는 모든 커밋

## Rebase 실수에서 복구하기

rebase가 잘못되면 다음을 수행합니다.

```
# Find the commit before the rebase
git reflog

# Reset to that commit
git reset --hard HEAD@{2}
```

## 모범 사례

1. **push하기 전에 rebase하세요**: 로컬 커밋을 공유하기 전에 정리하세요
2. **공개 이력을 rebase하지 마세요**: 로컬 커밋만 rebase하세요
3. **대규모 rebase 전에 백업하세요**: 먼저 브랜치를 만드세요
4. **소통하세요**: 공유 코드를 rebase해야 한다면 팀에게 알리세요
5. **연습하세요**: 먼저 일회용 브랜치에서 rebase를 연습해 보세요

## 오늘의 요약

Rebase는 깔끔하고 선형적인 커밋 이력을 만들기 위한 강력한 도구입니다. 로컬 작업과 병합을 위한 브랜치 준비에는 훌륭하지만, 공유 이력을 다시 쓰는 일이 없도록 주의해서 사용해야 합니다. rebase를 언제 어떻게 사용할지 이해하는 것은 고급 Git 워크플로에 필수적입니다.

오늘 배운 Git 명령어와 매개변수를 다시 정리하겠습니다.

* git rebase
* git rebase main
* git rebase -i
* git rebase --continue
* git rebase --abort
* git rebase --skip
* git rebase --onto
* git rebase --autosquash
* git commit --fixup
