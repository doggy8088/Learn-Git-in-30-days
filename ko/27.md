# Day 27: 같은 원격 리포지토리에서 브랜치로 버전 관리하기

팀마다 서로 다른 브랜치 전략을 사용합니다. 이 글에서는 흔한 브랜치 모델과 각각을 언제 사용할지 살펴보겠습니다.

## 브랜치 전략이 중요한 이유

명확한 전략이 없으면 다음 문제가 생깁니다.
* 코드 충돌이 늘어납니다
* 릴리스가 혼란스러워집니다
* 버그가 프로덕션에 유입됩니다
* 팀 조율이 어려워집니다

## GitHub Flow

**적합한 경우**: 웹 애플리케이션, 지속적 배포

### 전략

* 하나의 main 브랜치: `main`
* 모든 변경에 기능 브랜치 사용
* `main`에서 배포

### 워크플로

```
1. Create branch from main
   git checkout -b feature-name

2. Work and commit
   git commit -am "Add feature"

3. Push and create PR
   git push origin feature-name

4. Review and discuss

5. Deploy from branch (staging)

6. Merge to main
   # On GitHub: Merge PR

7. Deploy from main (production)
```

### 장점
* 단순하고 직관적입니다
* 빠른 속도의 개발이 가능합니다
* main이 항상 배포 가능한 상태입니다
* 지속적 배포에 좋습니다

### 단점
* 장기적인 릴리스 지원이 없습니다
* 좋은 CI/CD가 필요합니다
* 여러 버전을 다루기에는 적합하지 않습니다

## Git Flow

**적합한 경우**: 릴리스가 있는 소프트웨어, 여러 버전

### 브랜치 종류

* **main**: 프로덕션 준비가 된 코드
* **develop**: 통합 브랜치
* **feature/**: 새 기능
* **release/**: 릴리스 준비
* **hotfix/**: 긴급 수정

### 워크플로

```
# Start new feature
git checkout -b feature/login develop

# Work on feature
git commit -am "Implement login"

# Finish feature
git checkout develop
git merge --no-ff feature/login
git branch -d feature/login

# Start release
git checkout -b release/1.0 develop

# Prepare release (bug fixes only)
git commit -am "Bump version to 1.0"

# Finish release
git checkout main
git merge --no-ff release/1.0
git tag -a 1.0

git checkout develop
git merge --no-ff release/1.0
git branch -d release/1.0

# Hotfix
git checkout -b hotfix/1.0.1 main
git commit -am "Fix critical bug"

git checkout main
git merge --no-ff hotfix/1.0.1
git tag -a 1.0.1

git checkout develop
git merge --no-ff hotfix/1.0.1
git branch -d hotfix/1.0.1
```

### 장점
* 관심사가 명확히 분리됩니다
* 여러 버전을 지원합니다
* 구조화된 릴리스 과정이 있습니다

### 단점
* 더 복잡합니다
* 개발 주기가 느려집니다
* 단순한 프로젝트에는 과도합니다

## GitLab Flow

**적합한 경우**: 스테이징과 프로덕션 환경이 있는 조직

### 전략

* 환경 브랜치: `main`, `staging`, `production`
* 기능 브랜치는 `main`에 병합됩니다
* 환경을 거치며 승격됩니다

### 워크플로

```
# Feature development
git checkout -b feature-name main
# Work and commit
git push origin feature-name
# Create MR to main

# After merge to main
# Deploy to staging
git checkout staging
git merge main
git push origin staging

# After testing in staging
# Deploy to production
git checkout production
git merge staging
git push origin production
```

### 장점
* 환경 기반 배포가 가능합니다
* 승격 경로가 명확합니다
* 규제 산업에 좋습니다

### 단점
* 관리할 브랜치가 더 많습니다
* 자동화가 필요합니다
* 느려질 수 있습니다

## 트렁크 기반 개발

**적합한 경우**: 높은 성과를 내는 팀, 지속적 배포

### 전략

* 단일 트렁크: `main`
* 매우 수명이 짧은 기능 브랜치(1일 미만)
* 미완성 기능에는 기능 플래그 사용

### 워크플로

```
# Create short-lived branch
git checkout -b quick-fix main

# Make small change
git commit -am "Fix button color"

# Merge same day
git checkout main
git merge quick-fix
git push origin main

# Or commit directly to main
# (with CI and feature flags)
```

### 장점
* 가장 빠른 통합이 가능합니다
* 병합 충돌이 줄어듭니다
* CI/CD를 장려합니다
* 코드 품질이 높아집니다

### 단점
* 규율이 필요합니다
* 좋은 CI/CD가 필요합니다
* 기능 플래그가 복잡해질 수 있습니다

## Release Flow(Microsoft)

**적합한 경우**: 엔터프라이즈 소프트웨어, 계획된 릴리스

### 전략

* `main`: 항상 릴리스 준비 상태
* `release/*`: 안정화 브랜치
* 토픽 브랜치: 수명이 짧은 기능

### 워크플로

```
# Create topic branch
git checkout -b users/name/feature main

# Work and create PR
git push origin users/name/feature

# Create release branch
git checkout -b release/v2.0 main

# Cherry-pick into release
git cherry-pick <commit-hash>

# Release
git checkout main
git merge release/v2.0
git tag v2.0
```

### 장점
* 유연한 릴리스 일정이 가능합니다
* 개발과 안정화를 병행할 수 있습니다
* 엔터프라이즈에 좋습니다

### 단점
* 복잡해질 수 있습니다
* cherry-pick이 필요합니다
* 유지 관리가 더 필요합니다

## 전략 선택하기

### GitHub Flow를 선택할 때:
* 지속적 배포
* 웹 애플리케이션
* 작은 팀
* 빠른 반복

### Git Flow를 선택할 때:
* 예정된 릴리스
* 데스크톱/모바일 앱
* 여러 버전을 지원해야 할 때
* 전통적인 소프트웨어 생명 주기

### GitLab Flow를 선택할 때:
* 여러 환경
* 단계적 배포
* 규제 요구 사항

### 트렁크 기반을 선택할 때:
* 경험 많은 팀
* 뛰어난 CI/CD
* 지속적 배포
* 높은 릴리스 빈도

## 브랜치 이름 규약

### 기능 브랜치
```
feature/user-authentication
feature/dark-mode
feat/issue-123
```

### 버그 수정 브랜치
```
fix/login-error
bugfix/issue-456
hotfix/critical-security-patch
```

### 릴리스 브랜치
```
release/1.0
release/2.0.0
release/v1.5
```

### 기타 브랜치
```
docs/update-readme
test/integration-tests
refactor/database-layer
chore/update-dependencies
```

## 브랜치 관리 명령어

### 브랜치 목록 보기
```
# Local branches
git branch

# All branches (including remote)
git branch -a

# With last commit
git branch -v

# Merged branches
git branch --merged

# Unmerged branches
git branch --no-merged
```

### 브랜치 삭제하기
```
# Delete local branch
git branch -d feature-name

# Force delete
git branch -D feature-name

# Delete remote branch
git push origin --delete feature-name
```

### 브랜치 이름 바꾸기
```
# Rename current branch
git branch -m new-name

# Rename other branch
git branch -m old-name new-name
```

## 오늘의 요약

올바른 브랜치 전략을 선택하는 것은 팀, 프로젝트, 배포 모델에 따라 달라집니다. 모두에게 맞는 하나의 해법은 없습니다. GitHub Flow 같은 단순한 전략으로 시작해 필요에 따라 발전시켜 나가세요. 핵심은 일관성과 소통입니다.

오늘 배운 Git 명령어와 매개변수를 다시 정리하겠습니다.

* git checkout -b branch-name
* git merge --no-ff
* git cherry-pick
* git branch -m
* git branch --merged
* git branch --no-merged
* git push origin --delete
