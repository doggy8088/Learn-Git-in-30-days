# Day 25: GitHub 원격 리포지토리 사용하기 - 개념

Day 24의 기초를 바탕으로, 이 글에서는 GitHub 원격 리포지토리로 작업할 때의 중요한 개념과 워크플로를 살펴보겠습니다.

## 원격 추적 브랜치 이해하기

원격 추적 브랜치는 원격 브랜치의 상태에 대한 참조입니다. `<remote>/<branch>`라는 이름 패턴을 따릅니다.

```
# List all branches including remote tracking branches
git branch -a

# Example output:
# * main
#   feature
#   remotes/origin/main
#   remotes/origin/feature
```

## Fetch vs Pull

### Fetch

다른 리포지토리에서 개체와 참조를 다운로드하지만 병합하지는 않습니다.

```
git fetch origin
```

이렇게 하면 원격 추적 브랜치는 업데이트되지만 작업 디렉터리는 변경되지 않습니다.

### Pull

Fetch와 Merge를 하나의 명령어로 수행합니다.

```
git pull origin main
# Equivalent to:
git fetch origin
git merge origin/main
```

또는 rebase와 함께 사용합니다.

```
git pull --rebase origin main
```

## 업스트림 브랜치

push/pull을 단순화하기 위해 업스트림 추적을 설정합니다.

```
# Set upstream when pushing
git push -u origin feature-branch

# Now you can just use:
git push
git pull
```

업스트림 설정을 확인합니다.

```
git branch -vv
```

## 원격 브랜치 추적하기

### 원격에서 로컬 브랜치 만들기

```
# Option 1: Automatic tracking
git checkout feature-branch
# If feature-branch exists on remote, Git auto-creates and tracks it

# Option 2: Explicit tracking
git checkout -b feature-branch origin/feature-branch

# Option 3: Using track flag
git checkout --track origin/feature-branch
```

### 원격 브랜치 추적 해제하기

```
git branch --unset-upstream
```

## 다른 브랜치 이름으로 Push하기

로컬 브랜치를 다른 이름으로 원격에 push합니다.

```
git push origin local-branch:remote-branch
```

## 원격 브랜치 삭제하기

원격 브랜치를 삭제합니다.

```
# Method 1
git push origin --delete branch-name

# Method 2
git push origin :branch-name
```

## 여러 리모트로 작업하기

여러 개의 리모트(예: origin과 upstream)를 가질 수 있습니다.

```
# Add upstream remote
git remote add upstream https://github.com/original/repo.git

# Fetch from upstream
git fetch upstream

# Merge upstream changes
git merge upstream/main

# Push to your origin
git push origin main
```

## git push 동작 이해하기

다양한 push 모드는 다음과 같습니다.

```
# Push current branch to matching branch on remote
git config push.default simple  # Default in Git 2.0+

# Push all matching branches
git config push.default matching

# Push current branch to branch with same name
git config push.default current

# No push without explicit ref spec
git config push.default nothing
```

## 강제 Push와 그 위험성

### 강제 Push가 필요한 경우

* 기능 브랜치를 rebase한 경우
* 그 브랜치에서 작업하는 사람이 본인뿐인 경우
* push된 커밋의 실수를 수정해야 하는 경우

### 강제 Push 방법

```
# Standard force push (dangerous!)
git push -f origin feature-branch

# Safer: force push with lease
git push --force-with-lease origin feature-branch
```

`--force-with-lease`는 마지막으로 fetch한 이후 원격이 변경되지 않았을 때만 성공합니다.

### 강제 Push 모범 사례

1. **main/master에는 절대로 강제 push하지 마세요**
2. 공유 브랜치를 강제 push하기 전에 **소통하세요**
3. -f 대신 **--force-with-lease를 사용하세요**
4. 강제 push하기 전에 **백업 브랜치를 만드세요**
5. **본인의 기능 브랜치만 강제 push하세요**

## 분기된 브랜치 처리하기

로컬과 원격이 서로 분기되었을 때는 다음을 수행합니다.

```
# Check the situation
git status

# Option 1: Merge remote changes
git pull origin main

# Option 2: Rebase on remote changes
git pull --rebase origin main

# Option 3: Force push (if appropriate)
git push --force-with-lease origin feature-branch
```

## 원격 추적 참조 정리하기

오래된 원격 추적 브랜치를 제거합니다.

```
# See stale branches
git remote prune origin --dry-run

# Remove stale branches
git remote prune origin

# Or during fetch
git fetch --prune
```

## Bare 리포지토리 vs Non-Bare 리포지토리

### Non-Bare(작업 리포지토리)

* 작업 디렉터리가 있습니다
* 개발에 사용됩니다
* 일반적으로 clone하는 형태입니다

### Bare 리포지토리

* 작업 디렉터리가 없습니다
* Git 데이터만 있습니다
* 서버에서 사용됩니다

```
# Create bare repository
git clone --bare project project.git

# Or init as bare
git init --bare project.git
```

## Git 워크플로 패턴

### 중앙 집중식 워크플로

모든 사람이 main 브랜치에서 작업합니다.

```
git pull origin main
# Make changes
git add .
git commit -m "Changes"
git push origin main
```

### 기능 브랜치 워크플로

각 기능마다 전용 브랜치를 둡니다.

```
git checkout -b feature-x
# Work on feature
git push origin feature-x
# Create pull request
# After merge, delete branch
git branch -d feature-x
git push origin --delete feature-x
```

### Gitflow 워크플로

여러 개의 장기 브랜치를 사용합니다.

* **main**: 프로덕션 준비가 된 코드
* **develop**: 통합 브랜치
* **feature/**: 기능 개발
* **release/**: 릴리스 준비
* **hotfix/**: 긴급 수정

## 풀 리퀘스트 워크플로

1. 리포지토리를 **Fork**합니다(오픈 소스의 경우)
2. 포크를 **Clone**합니다
3. **기능 브랜치를 만듭니다**
   ```
   git checkout -b feature-name
   ```
4. **변경 사항을 만들고 커밋합니다**
5. **포크에 push합니다**
   ```
   git push origin feature-name
   ```
6. GitHub에서 **풀 리퀘스트를 만듭니다**
7. 코드를 **논의하고 리뷰합니다**
8. **요청된 변경 사항을 반영합니다**
9. **승인되면 병합합니다**

## Fork를 최신 상태로 유지하기

```
# Add upstream remote (once)
git remote add upstream https://github.com/original/repo.git

# Fetch upstream changes
git fetch upstream

# Merge upstream/main into your main
git checkout main
git merge upstream/main

# Push to your fork
git push origin main
```

## 풀 리퀘스트의 충돌 해결하기

```
# Update your branch with target branch
git fetch origin
git checkout feature-branch
git merge origin/main

# Resolve conflicts
# ... edit files ...
git add .
git commit -m "Resolve conflicts"

# Push updated branch
git push origin feature-branch
```

## 오늘의 요약

원격 리포지토리 개념을 이해하는 것은 효과적인 협업에 매우 중요합니다. 팀에서 작업하든 오픈 소스에 기여하든, 리모트를 관리하고 브랜치를 추적하며 충돌을 처리하는 방법을 알면 더 효과적인 Git 사용자가 될 수 있습니다.

오늘 배운 Git 명령어와 매개변수를 다시 정리하겠습니다.

* git fetch origin
* git pull origin main
* git pull --rebase
* git push -u origin branch
* git push origin --delete branch
* git push --force-with-lease
* git branch -vv
* git branch --unset-upstream
* git remote prune origin
* git fetch --prune
* git clone --bare
