# Day 17: 병합의 기본 개념과 사용법

Day 08(브랜치의 기본 개념과 사용법)에서 언급했듯이, 우리는 "브랜치"에 대해 배웠습니다. 이제 "병합"을 수행하는 방법을 논의하겠습니다. Git은 분산 버전 관리 시스템(DVCS)이므로, 의도적인 병합(`git merge`)이든 의도하지 않은 병합(`git pull`)이든 끊임없이 브랜치와 병합 작업을 수행하게 됩니다. 요컨대 "브랜치"와 "병합" 작업은 Git을 사용해 버전 관리를 할 때 실제로 자주 발생합니다. 이 글에서는 "병합" 작업의 기본 개념과 사용법을 설명하겠습니다.

## 병합 개념 이해하기

Git 작업 디렉터리에서 브랜치를 만들면, 서로 영향을 주지 않으면서 서로 다른 요구에 따라 시스템을 따로 개발할 수 있습니다. 예를 들어 원래 안정적인 시스템은 `master` 브랜치에 유지하여 개발하고, 오류를 수정해야 할 때는 추가로 `bugfix` 브랜치를 만들어 소프트웨어 오류를 수정할 수 있습니다. 버그가 수정된 후에는 "병합"을 통해 `bugfix` 브랜치의 변경 사항을 `master`에 다시 적용할 수 있습니다. 이것이 주요 사용 시나리오 중 하나입니다.

일반적으로 모든 사람은 메인 또는 기본 브랜치(`master`)에서 개발한 다음, 요구에 따라 브랜치를 만들고(`bugfix`), 마지막으로 두 브랜치를 하나로 병합합니다. 실제로 "병합" 작업을 수행할 때는 다른 브랜치를 현재 브랜치로 병합한 다음, 다른 브랜치를 수동으로 제거합니다. 이는 "두 브랜치를 하나로 병합한다"는 개념과 일치합니다.

실제로는 세 개, 네 개 또는 그 이상의 브랜치를 그중 하나로 병합할 기회가 종종 있습니다. 예를 들어 메인 브랜치(`master`) 외에도 디버깅을 위한 브랜치(`bugfix`)와 기능 추가를 위한 브랜치(`feature`)를 만듭니다. 어느 정도 개발이 진행된 후에는 이 두 브랜치를 모두 메인 브랜치(`master`)로 함께 병합할지 결정할 수 있습니다.

Git에서 병합을 사용할 때는 중요한 개념이 있습니다. **병합 작업은 반드시 같은 리포지토리 안에서 일어나야 합니다.** 어떤 Git 리포지토리에도 Initial Commit 개체(초기 버전)가 반드시 있어야 하며, 다른 모든 버전은 이 버전과 관련된다는 것을 떠올려 보세요. 우리는 이 관계를 "브랜치 헤드에서 추적되는 개체"라고 부르므로, 한 리포지토리의 특정 브랜치를 완전히 관련 없는 다른 리포지토리의 브랜치로 병합할 수는 없습니다.

병합할 때 두 브랜치가 같은 파일을 수정했더라도, 수정한 행이 다르기만 하면 Git이 이 두 변경 사항을 자동으로 적용/병합해 줍니다. 하지만 두 브랜치 모두에서 "같은 파일"의 "같은 행"을 수정한 경우에는 병합 중 충돌 이벤트가 발생합니다. 병합 충돌이 발생하면 Git은 여러분을 위해 어떤 결정도 내리지 않고, "충돌을 해결하는" 작업을 "여러분"에게 넘기며, 이 충돌하는 파일들은 모두 `unmerged` 상태로 표시됩니다. 병합 충돌 후에는 `git status` 명령어를 사용해 이러한 상태를 확인할 수 있습니다.

## 병합의 유형

Git에는 두 가지 주요 병합 유형이 있습니다.

1. **Fast-forward 병합**: 대상 브랜치가 소스 브랜치에서 분기되지 않았을 때 사용됩니다
2. **3방향 병합(Three-way merge)**: 두 브랜치 모두에 새 커밋이 있을 때 사용됩니다

## Fast-Forward 병합

Fast-forward 병합은 현재 브랜치가 병합되는 브랜치에서 분기되지 않았을 때 발생합니다. Git은 단순히 브랜치 포인터를 앞으로 이동시킵니다.

```
# On master branch
git merge feature-branch
```

`feature-branch`가 만들어진 이후 `master`에 새 커밋이 없었다면, Git은 fast-forward 병합을 수행합니다.

## 3방향 병합

두 브랜치 모두에 새 커밋이 있으면, Git은 3방향 병합을 수행하여 두 브랜치의 변경 사항을 결합한 새 병합 커밋을 만듭니다.

```
# On master branch
git merge feature-branch
```

이렇게 하면 부모 커밋이 두 개인 새 커밋이 만들어집니다.

## Fast-Forward 방지하기

때로는 fast-forward가 가능하더라도 브랜치 기록을 보존하고 싶을 수 있습니다.

```
git merge --no-ff feature-branch
```

이렇게 하면 fast-forward 병합의 경우에도 항상 병합 커밋이 만들어집니다.

## 병합 충돌

충돌은 병합되는 두 브랜치에서 같은 파일의 같은 행이 서로 다르게 변경되었을 때 발생합니다. 이런 일이 발생하면:

1. Git이 병합을 일시 중지합니다
2. 충돌하는 파일을 표시합니다
3. 파일에 충돌 마커를 추가합니다
4. 여러분이 충돌을 해결할 때까지 기다립니다

## 충돌하는 파일 보기

어떤 파일에 충돌이 있는지 보려면 다음을 사용합니다.

```
git status
```

충돌이 있는 파일은 "both modified"로 나열됩니다.

## 충돌 마커

Git은 충돌하는 파일에 마커를 추가합니다.

```
<<<<<<< HEAD
Your changes
=======
Their changes
>>>>>>> branch-name
```

* `<<<<<<< HEAD`: 여러분의 변경 시작을 표시합니다
* `=======`: 두 버전을 구분합니다
* `>>>>>>> branch-name`: 들어오는 변경의 끝을 표시합니다

## 충돌 해결하기

충돌을 해결하려면:

1. 충돌하는 파일을 엽니다
2. 충돌 마커를 찾습니다
3. 충돌을 해결하도록 파일을 편집합니다
4. 충돌 마커를 제거합니다
5. 해결된 파일을 스테이징합니다: `git add <file>`
6. 병합을 완료합니다: `git commit`

## 병합 중단하기

진행 중인 병합을 취소하고 싶다면 다음을 사용합니다.

```
git merge --abort
```

이렇게 하면 리포지토리가 병합이 시작되기 전의 상태로 돌아갑니다.

## 병합 기록 보기

기록에서 병합 커밋을 보려면 다음을 사용합니다.

```
git log --oneline --graph --all
```

이렇게 하면 브랜치와 병합 기록이 시각적으로 표시됩니다.

## 병합 전략

Git은 서로 다른 병합 전략을 지원합니다.

* **recursive**(기본값): 기본 3방향 병합 전략
* **ours**: 충돌 시 항상 우리 버전을 선호합니다
* **theirs**: 충돌 시 항상 상대 버전을 선호합니다

```
git merge -X ours branch-name
git merge -X theirs branch-name
```

## 모범 사례

1. 병합하기 전에 **작업을 커밋하세요**
2. 병합하기 전에 원격에서 **최신 변경 사항을 pull하세요**
3. 공유 브랜치에 push하기 전에 **병합을 테스트하세요**
4. 병합에 대해 팀과 **소통하세요**
5. 가능하면 **병합을 작게 유지하세요**

## 오늘의 요약

병합은 서로 다른 브랜치의 작업을 결합할 수 있게 해 주는 기본적인 Git 작업입니다. 병합이 어떻게 작동하는지, 특히 충돌을 처리하는 방법을 이해하는 것은 효과적인 협업에 필수적입니다. 과정에 익숙해지도록 병합을 정기적으로 연습하세요.

오늘 배운 Git 명령어와 매개변수를 다시 정리하겠습니다.

* git merge
* git merge --no-ff
* git merge --abort
* git merge -X ours
* git merge -X theirs
* git log --graph
* git status
