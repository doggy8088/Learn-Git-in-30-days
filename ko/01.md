# Day 01: Git 버전 관리 이해하기

저는 거의 10년 동안 Subversion(SVN)을 사용해 왔고, 다른 버전 관리 플랫폼으로 바꿀 필요성을 느끼지 못했습니다. 그러다가 몇 년 전부터 클라우드 환경의 변화에 대응하여 TFS 버전 관리(TFS Service)를 점진적으로 도입하게 되었습니다. SVN과 TFS는 버전 관리 개념이 비슷하고 둘 다 중앙 집중식 버전 관리 시스템이기 때문에 전환은 순조로웠습니다. 이러한 중앙 집중식 버전 관리 시스템은 단순하고 직관적이며 권한 관리도 쉽습니다. 솔직히 대부분의 개발 상황에서는 Subversion이나 TFS로도 충분합니다. 그렇다면 어떤 계기나 요구 사항 때문에 Git 버전 관리로 전환하게 되었을까요? 사람마다 Git을 도입하는 이유는 제각각일 것입니다. 재미있어서, 새로워서, 또는 강력해서 선택하기도 합니다. 어떤 이유든, 낯선 기술을 적극적으로 배우려는 동기가 된다면 좋은 이유입니다. 이 글에서는 Git 버전 관리 메커니즘을 소개할 뿐만 아니라, 제가 Git으로 전환하고자 했던 이유도 함께 공유하겠습니다.

## 이 글의 목적

소프트웨어 개발 분야에서 소스 코드의 버전 관리는 매우 중요합니다. Subversion이나 TFVC(Team Foundation Version Control) 같은 중앙 집중식 버전 관리 시스템과 달리, Git은 분산 버전 관리 시스템(DVCS, Distributed Version Control System)으로, 버전 관리에 많은 이점을 제공하며 로컬 작업 지원, 손쉬운 백업, 강력하고 유연한 브랜치와 병합 등 기존 중앙 집중식 버전 관리의 단점을 해결합니다. 그러나 Git 버전 관리는 버전 관리 개념과 도구 사용법 모두에서 기존 중앙 집중식 버전 관리 도구와 크게 다르기 때문에 상당한 학습 곡선이 존재합니다.

이 글의 주제는 "30일 만에 Git 마스터하기"이지만, 솔직히 말하면 이는 다소 과장된 표현입니다. Git은 방대하고 심오하여 탐구할 세부 사항이 많기 때문입니다. 실제로 업무에 적용하려면 며칠을 공부해야 진정으로 마스터할 수 있을까요? 30일 동안 매일 조금씩 배우는 것은 합리적인 기간으로 보입니다(혹은 너무 긴가요?). 모두가 반드시 사용해야 하고 즉시 익혀야 하는 도구가 있다면, 30일을 공부하고도 유연하게 사용하지 못한다면 그 학습 곡선은 너무 높은 것입니다. 따라서 이 시리즈의 핵심은 "30일 안에 Git 버전 관리를 배우고, 실제 개발 업무에 능숙하게 적용할 수 있어야 한다"는 데 있다고 생각합니다. 이것이 이 시리즈의 진정한 목적입니다. 지루한 세부 사항은 특별히 강조하지 않겠지만, 놓쳐서는 안 되는 중요한 개념과 세부 사항은 항상 존재합니다. 각 주제마다 일부를 언급하고, 기회가 있을 때 깊이 탐구하겠습니다. 직접 해 보면서 배우고, Git 버전 관리의 강력한 매력을 깊이 체험하시길 바랍니다.

## 전환의 계기

지난 몇 달 동안 저희 회사에는 12명 이상의 개발자가 참여하는 대규모 프로젝트가 있었습니다. 모두가 최종적으로 이 프로젝트의 버전 관리 메커니즘으로 Git을 채택하기로 결정했습니다. Git 버전 관리를 채택했다고 하기보다는, 도입의 진짜 이유는 "버전 관리 플랫폼으로 GitHub를 사용하기로 선택했기 때문"입니다. GitHub 플랫폼은 정말 잘 통합되어 있어서 완전한 Git 버전 관리 지원, 이슈 추적 및 관리, 온라인 Wiki 문서 관리, 친숙한 소스 코드 리뷰 인터페이스를 제공합니다. 이러한 기능은 다수의 인원이 협업 개발을 할 때 팀 커뮤니케이션 문제를 효과적으로 줄이는 데 도움이 됩니다.

Git을 시작하는 것은 상당히 어려웠습니다. Git 버전 관리의 개념이 Subversion과 너무 달라서 그 차이를 직관적으로 이해하기 힘들었기 때문입니다. GUI 그래픽 도구 인터페이스가 주어지더라도 제대로 사용할 수 없을 수 있습니다. 강력하고 유용한 도구를 손에 쥐고 있을 때, "제대로 사용하지 못하는 것"은 "사용법을 모르는 것"보다 더 끔찍하다는 것을 아실 겁니다! 간단히 말해, 먼저 사고방식을 확립하고 Git의 작동 원리를 이해한 다음, Git 관련 도구(명령줄 도구든 그래픽 인터페이스 도구든)를 사용하기 시작해야 합니다. 이것이 올바른 방법입니다!

## 학습 방법

Git을 처음 배울 때 저는 여러 권의 책을 읽었고(실제로는 핵심 부분만 골라 읽었습니다), 온라인 기사와 프레젠테이션도 많이 읽었으며, 튜토리얼 영상도 여러 편 시청했습니다. 보고 배우는 방식으로 Git 도구의 사용법을 익힐 수 있었고, 그다지 어렵다고 생각하지 않았습니다. 그러나 Git에는 명령어와 매개변수가 너무 많아서 뇌의 기억 범위를 완전히 벗어납니다. 매일 사용하지 않는 한, 하루 종일 버전 관리 명령어를 입력할 수는 없지 않습니까? Git 명령어를 사용할 때마다 책을 찾아봐야 한다면 너무 비효율적입니다. 당시 저는 Git 학습이 결국 유용한 GUI 도구로 귀결되어야 한다고 직관적으로 생각했습니다. 그렇지 않으면 팀에 보급하기 쉽지 않을 수 있기 때문입니다.

게다가 Git은 "분산 버전 관리" 메커니즘이기 때문에, 개발자 수가 늘어나고 각자가 리포지토리의 사본을 갖게 되면, 모두가 처음 다인 브랜치와 병합 과정에서 고통을 겪으며, 그 상태가 상당 기간 지속됩니다. 사내 기술 공유가 있었지만, 모두가 처음 배우는 상황이었기 때문에 Git의 추상적인 개념이 사람들의 마음에 깊이 뿌리내릴 수 없었습니다. 도구 사용법, 자주 사용하는 명령어, 특수한 상황에서 사용해야 할 명령어 등 Git 사용 방법을 기반으로 공유할 수밖에 없었습니다. 과정에서 복잡한 원리를 설명하더라도, Git에 대한 모두의 이해가 아직 모호했기 때문에 Git 버전 관리 방법에 대한 이해가 사람마다 달랐고, 흡수한 지식과 개념도 반드시 일치하지 않았습니다. 그래서 강좌가 끝난 후에도 모두가 며칠 동안 계속 적응하고, 서로 토론하며, 함께 문제를 해결해야 했습니다. 혼자서 Git을 사용한다면 Git이 가져다주는 이점을 느끼기 정말 어렵고, 지속하기도 힘들 수 있습니다.

따라서 Git 버전 관리를 잘 배우려면, 다음 사항을 먼저 알아 두면 배우기가 더 쉬울 수 있다고 생각합니다.

* 첫째, 기본적인 Git 개념을 갖추세요. 명령어를 통해 배우는 것이 가장 빠른 방법입니다. 이 부분을 건너뛰지 마세요.
* 더 많은 사람들과 함께 Git 버전 관리를 배우세요. 실제 개발 업무에 직접 사용하는 것이 가장 좋습니다.
* 팀에 Git 개념을 더 많이 학습하여 다른 사람들과 공유하거나, 누군가 막혔을 때 적시에 도움을 줄 수 있는 선발대가 몇 명 있는 것이 가장 좋습니다.
* Git은 "분산 버전 관리"이며, 모두가 완전한 리포지토리를 가지고 있으므로 파일을 자주 병합해야 한다는 것을 이해하세요.
* Git을 사용할 때 브랜치와 병합은 정상적인 일이지만, 병합이 있을 때마다 충돌이 발생합니다. 충돌 해결 방법을 배우세요.

## Git 버전 관리 이해하기

Git은 Linux의 아버지인 Linus Torvalds가 Linux 커널을 개발하던 중 탄생했습니다. 초기 버전 관리 방식은 매우 비효율적이고 중앙 집중식이었기 때문에, Linux 커널처럼 복잡하고 대규모인 프로젝트의 버전 관리를 관리할 때 많은 문제가 발생했습니다. 초기 Linux 커널은 버전 관리에 BitKeeper를 사용했지만, 나중에 Linus Torvalds는 BitKeeper와 Monotone 사용 경험을 바탕으로 더 나은 Git 버전 관리 시스템을 설계했습니다. 원래 Git은 다른 버전 관리 시스템(SCM)의 운영 도구로 사용되는 저수준 버전 관리 도구로만 설계되었으나, 이후 점차 완전한 버전 관리 시스템으로 발전했습니다.

흥미롭게도, Linus Torvalds가 처음 버전 관리를 위해 Git으로 전환했을 때 Git은 너무 복잡했고, 많은 버전 관리 개념이 이전과 너무 달라서 전 세계 오픈 소스 커뮤니티의 반대에 부딪히기도 했습니다. 그러나 수년간의 노력과 발전을 거치면서 Git을 운영하는 도구는 점점 더 성숙해졌고, 반대 여론도 점차 가라앉았습니다. 2013년 시장 조사에 따르면, 전 세계 오픈 소스 프로젝트의 30%가 버전 관리를 위해 Git으로 전환했습니다. 이는 놀라운 시장 점유율로, Git에 분명 놀라운 기능이 있다는 의미이며, 제대로 공부할 필요가 있습니다!

Git의 아키텍처는 전적으로 Linus Torvalds가 Linux 커널과 같은 대규모 프로젝트를 유지 관리한 경험과 파일 시스템 최적화에 대한 풍부한 경험을 바탕으로 합니다. 이 때문에 Git에는 다음과 같은 중요한 설계가 포함되어 있습니다.

* 비선형 개발 모델(분산 개발 모델)에 대한 강력한 지원
  * Git에는 버전 변경의 이력 경로를 표시하는 그래픽 도구를 포함하여, 빠른 브랜치와 병합 메커니즘이 있습니다.
  * Git은 브랜치와 병합을 매우 강조하므로, 버전 관리 과정에서 끊임없이 브랜치와 병합 작업을 수행하게 됩니다.
  * Git의 브랜치 메커니즘은 매우 가볍고 부담이 없습니다. 각 브랜치는 특정 커밋을 가리키는 참조 포인터일 뿐입니다.
* 분산 개발 모델
  * Git 개발에 참여하는 모든 사람은 완전한 개발 이력을 갖게 됩니다.
  * 개발자가 Git 리포지토리를 처음 복제(clone)하면, 이는 해당 Git 리포지토리의 "완전한 백업"과 완전히 동일합니다.
  * 전체 리포지토리의 모든 변경된 파일과 이력 기록은 로컬 리포지토리에 저장됩니다.
* 기존 운영 체제와의 호환성
  * Git 리포지토리는 실제로 각종 관련 구성 파일과 각종 blob 개체 파일이 들어 있는 폴더일 뿐입니다.
  * Git 리포지토리는 어떤 방식으로든 게시할 수 있으므로, HTTP, FTP, rsync, SSH, 심지어 Git 프로토콜까지 Git 리포지토리에 접근하는 매체로 사용할 수 있어 호환성이 매우 높습니다.
* 대규모 프로젝트의 효율적인 처리
  * 완전한 리포지토리가 로컬 머신에 복제되고, 리포지토리에는 완전한 파일과 버전 변경 기록이 포함되어 있으므로, 버전 관리에서 각종 파일 작업의 속도는 원격으로 직접 접근하는 것보다 수백 배 빠릅니다.
  * 이는 또한 Git 버전 관리가 프로젝트가 커지고 파일이 많아져도 느려지지 않는다는 것을 의미합니다.
* 이력 기록 보호
  * Git 버전 관리 과정에서 각 커밋은 해시 ID 번호를 생성하고, 변경 과정의 각 버전은 이 해시 ID를 참조합니다. 해시 ID가 일치하지 않으면 Git은 작동하지 않습니다. 따라서 프로젝트가 커지고 리포지토리 사본이 더 많이 복제될수록, 파일 내용이나 버전 기록을 변조하기가 거의 불가능해집니다.
  * **기억하세요: 모두가 완전한 리포지토리를 가지고 있습니다. 원본을 변경하면 모두의 리포지토리를 더 이상 원본 리포지토리로 병합할 수 없으므로, 버전 기록을 임의로 변조하기가 거의 불가능합니다.**
* 툴킷 기반 설계
  * Git은 일련의 도구 소프트웨어(명령줄 도구)로 설계되었습니다. 다양한 도구를 쉽게 조합하여 사용할 수 있어 유연성이 큽니다.
* 플러그인 가능한 병합 전략
  * Git에는 잘 설계된 "불완전 병합" 메커니즘과 병합을 완료할 수 있는 여러 알고리즘이 있으며, 최종적으로 자동 병합을 완료할 수 없는 이유를 사용자에게 알리거나 수동 병합이 필요함을 알려 줍니다.
* 수동적 가비지 수집 메커니즘
  * Git을 사용할 때 현재 작업을 중단하거나 이전 작업을 복원하고 싶다면 가능합니다. 잘못된 명령어를 사용하거나 명령어 실행 도중 충돌이 발생할까 걱정할 필요가 없습니다.
  * Git의 가비지 수집 메커니즘은 실제로 파일 시스템에 남아 있는 쓸모없는 파일들입니다. 이 가비지 수집 메커니즘은 이러한 쓸모없는 개체가 일정 기간 누적된 후에만 자동으로 실행되며, 직접 명령어를 내려 정리할 수도 있습니다. 예: git gc --prune
* 개체의 정기적인 패킹
  * Git에서 말하는 "개체"는 실제로 리포지토리의 파일을 나타냅니다. 버전 변경 과정에서 프로젝트의 코드나 기타 파일이 업데이트됩니다. 업데이트될 때마다 파일 내용이 다르기만 하면 새로운 "개체"가 생성되고, 내용이 다른 이 모든 파일이 보존됩니다.
  * 프로젝트가 커지고 버전이 많아질수록 개체도 점점 많아질 것이라고 상상할 수 있습니다. 각 파일을 개별적으로 압축하여 파일을 더 작게 만들 수는 있지만, 파일이 너무 많으면 파일 접근 효율은 여전히 점점 떨어집니다. 따라서 Git의 설계에는 오래된 "개체" 그룹을 packfile로 자동 패킹하여 파일 접근 효율을 높이는 메커니즘이 있습니다.
  * 새로 추가된 파일은 여전히 단일 파일로 존재하는데, 이는 Git 리포지토리의 "파일"이 Git "개체"이지만, 가끔씩 다시 패킹해야 한다는 것을 의미합니다.
  * 아마도 Git은 다시 패킹과 같은 작업을 자동으로 수행하겠지만, 직접 명령어를 내려 실행할 수도 있습니다. 예: git gc
  * Git이 유지 관리하는 파일 시스템이 완전한지 확인하려면 다음 명령어를 실행할 수 있습니다: git fsck

Git의 분산 버전 관리 시스템에 대해 몇 가지를 다시 강조하겠습니다.

* Git은 모두가 리포지토리의 완전한 사본을 가지고 있기 때문에 서버 측 지원 없이도 버전 관리를 완전히 운영할 수 있습니다.
* 모두가 리포지토리의 완전한 사본을 가지고 있기 때문에, 버전 변경을 커밋할 때마다 로컬 리포지토리에만 커밋하므로 커밋 속도가 매우 빠르고 네트워크 연결도 필요 없어 개발 시간을 크게 절약할 수 있습니다.
* 모두가 리포지토리의 완전한 사본을 가지고 있으므로, Git 버전 관리를 사용할 때 "권한 제어"라는 개념은 존재하지 않습니다. 모든 구성원이 리포지토리를 복제할 수 있고, 어떤 권한 제한 없이 로컬에 변경 사항을 커밋할 수 있습니다. Git을 사용할 때 설정할 수 있는 유일한 권한은 업스트림 리포지토리나 원격 리포지토리에 접근할 권한이 있는지 여부입니다.
* 다른 사람과 변경된 버전을 교환해야 한다면, 언제든지 "병합"을 통해 할 수 있습니다. Git은 매우 강력한 병합 추적 기능을 갖추고 있습니다.
* 여러 사람의 버전을 병합하려면, 공유 리포지토리에 대한 권한이나 접근 권한만 있으면 됩니다.
  **예를 들어: 같은 서버에서는 폴더 권한을 통해 공유할 수 있고, SSH를 통해 다른 서버의 Git 리포지토리에 원격으로 접근할 수도 있으며, 웹 서버를 통해 Git 리포지토리를 공유할 수도 있습니다.**
