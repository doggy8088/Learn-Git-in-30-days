# Day 18: 커밋된 버전 이력 수정하기 Part 1 (reset & amend)

Git을 사용해 버전 관리를 할 때 우리는 `git commit`을 사용해 많은 버전을 만듭니다. Git은 분산 버전 관리 시스템이므로, Subversion이나 TFVC 같은 중앙 집중식 버전 관리 시스템과 비교하면 Git은 버전 관리에 대한 권한 설계가 덜합니다. Git은 "버전 기록을 수정"하는 메커니즘을 더 많이 제공하여, 다른 사람과 버전을 "공유"하기 전에 미리 정리할 수 있게 해 줍니다.

## 버전 관리 기본 원칙

버전 관리를 수행할 때는 Git, Subversion, TFVC 중 무엇을 사용하든, 좋은 버전 기록을 유지하면 각 버전의 업데이트 이력을 추적하는 데 도움이 됩니다(그럴 필요가 있을 때). 제 개인적인 경험으로는, 프로젝트에서 소프트웨어 개발 과정을 추적할 기회나 의지가 있는 경우가 드뭅니다. 우리 프로젝트 중 상당수는 수천 개의 버전 기록이 누적되어 있는데, 누가 그 이력을 조사할 시간이 있겠습니까?

그러나 실제로는 소프트웨어 버그가 발생하면, 버그의 실제 원인을 찾기 위해 특정 버그의 이력 기록을 추적해야 합니다. 이때가 바로 버전 관리가 가장 큰 가치를 발휘하는 순간입니다.

따라서 좋은 "버전 기록"을 유지하는 방법도 매우 중요합니다. 다음은 공유할 몇 가지 관리 원칙입니다.

* 작은 기능 수정마다 버전을 만들어 변경 사항을 추적하기 쉽게 합니다
* 수많은 수정을 누적한 뒤에 "큰 버전"을 만드는 일은 절대 하지 않습니다
* 기능을 논리적이고 순서대로 수정하여, 관련 버전 수정이 추적하기 쉽게 순차적으로 커밋되도록 합니다

그러나 사람은 실수를 합니다. 팀의 모든 사람이 항상 위의 원칙에 따라 버전 관리를 할 수 있다고 누가 보장할 수 있겠습니까? "생각나는 대로 수정"하지 않는 사람이 누가 있겠습니까? 이러한 요구 사항은 비현실적이 됩니다. 따라서 버전이 원격 서버에 제출될 때 이미 완벽한 상태가 되도록 "버전을 수정"하는 메커니즘이 필요합니다.

## 커밋 이력을 수정하는 이유

지금까지는 "원격 리포지토리"의 세부 사항을 언급하지 않았으므로, 대부분의 Git 작업은 여전히 로컬 작업, 즉 작업 디렉터리에서의 버전 관리에 중점을 두며, 이 리포지토리는 여러분의 `.git/` 디렉터리에 위치합니다. 그러나 곧 "원격 리포지토리"의 활용을 논의하게 될 텐데, 그때는 한 명 이상의 사람이 리포지토리를 가지게 되고 더 많은 세부 사항에 주의를 기울여야 합니다.

모든 사람이 임의로 커밋 이력을 수정할 수 있게 한다는 것은 Subversion이나 TFVC에 익숙한 사람들에게는 이상하게 들릴 수 있는데, 이는 모든 사람이 중앙의 버전 관리 서버에 연결해 중앙 집중식 리포지토리를 사용하는 데 익숙했기 때문입니다. 누군가가 임의로 이력 기록을 조작할 수 있다면, 그것을 여전히 버전 관리라고 부를 수 있을까요?

사실 Git 버전 관리에서도 개념은 같습니다. 같은 리포지토리를 여러 사람이 공유하는 한, 누군가가 임의로 버전을 조작하면 Git 버전 관리도 제대로 작동하지 않게 됩니다.

그렇다면 어떤 사용 시나리오에서 버전 기록을 수정해야 할까요? 다음 사항들을 참고할 수 있습니다.

지금 [A] -> [B] -> [C] 세 개의 버전이 있다고 가정합니다.

* 버전 [C]가 잘못 커밋된 것을 발견하고 이 버전의 모든 변경 사항을 삭제해야 할 수 있습니다
* [C]를 커밋한 뒤에 이 버전에는 테스트 코드만 있다는 것을 발견하고 삭제하고 싶을 수 있습니다
* 일부 버전 기록 메시지에 오타가 있어, 파일 변경 이력에는 영향을 주지 않고 메시지 텍스트를 수정하고 싶을 수 있습니다
* 버전 진화가 더 논리적이 되도록 이 버전들의 커밋 순서를 [A] -> [C] -> [B]로 조정하고 싶을 수 있습니다
* 버전 [B]가 커밋하기 전에 중요한 파일을 포함하는 것을 잊었다는 것을 발견하고, 이후에 이 변경을 보완하고 싶을 수 있습니다
* 브랜치를 "공유"할 계획일 때 코드 결함을 발견하고 공유하기 전에 수정할 수 있습니다

## 커밋 이력 수정의 중요 참고 사항

Git이 "버전 이력 기록을 수정"하는 메커니즘을 유지하는 것은, 주로 여러분이 어느 정도 "자체적으로 버전을 관리"한 뒤에 버전 기록의 다양한 정보를 직접 정리할 수 있기를 바라기 때문이며, 그래야 버전을 "게시"한 후에 다른 사람들이 이 버전에 어떤 수정을 했는지 더 명확히 이해할 수 있습니다.

따라서 버전 이력 기록을 수정할 때는 몇 가지 사항에 특별히 주의를 기울여야 합니다.

* 리포지토리에는 많은 브랜치가 있을 수 있습니다(기본 브랜치 이름은 `master`입니다)
* Git 소스 코드를 공유하는 최소 단위는 "브랜치"입니다
* 다른 사람과 "공유"하지 않은 한, 브랜치의 버전을 임의로 수정할 수 있습니다
* **특정 브랜치를 다른 사람과 "공유"한 후에는, 그 "공유된" 버전 이력 기록을 더 이상 수정하지 마세요!**

## git commit --amend 이해하기

`--amend` 옵션을 사용하면 가장 최근의 커밋을 수정할 수 있습니다. 이는 다음과 같은 경우에 유용합니다.

* 커밋 메시지를 변경하고 싶을 때
* 일부 파일을 포함하는 것을 잊었을 때
* 마지막 커밋의 작은 실수를 수정해야 할 때

### 마지막 커밋 메시지 변경하기

```
git commit --amend -m "New commit message"
```

### 마지막 커밋에 파일 추가하기

```
# Make changes or add forgotten files
git add forgotten-file.txt

# Amend the commit
git commit --amend --no-edit
```

`--no-edit` 플래그는 기존 커밋 메시지를 유지합니다.

### 대화형 Amend

편집기에서 커밋 메시지를 편집하려면 다음을 사용합니다.

```
git commit --amend
```

이렇게 하면 구성된 편집기가 열리고, 거기서 커밋 메시지를 수정할 수 있습니다.

## git reset 이해하기

`git reset`은 다음을 수행할 수 있는 강력한 명령어입니다.

* 현재 브랜치 포인터 이동
* 스테이징 영역(인덱스) 수정
* 작업 디렉터리 수정

reset에는 세 가지 모드가 있습니다.

1. **--soft**: HEAD를 이동하고, 스테이징 영역과 작업 디렉터리는 변경하지 않습니다
2. **--mixed**(기본값): HEAD를 이동하고, 스테이징 영역을 리셋하며, 작업 디렉터리는 변경하지 않습니다
3. **--hard**: HEAD를 이동하고, 스테이징 영역과 작업 디렉터리를 리셋합니다

## Soft Reset

브랜치 포인터를 이동하지만 변경 사항은 스테이징된 상태로 유지합니다.

```
git reset --soft HEAD~1
```

이렇게 하면 마지막 커밋이 취소되지만 변경 사항은 스테이징 영역에 남아 다시 커밋할 준비가 됩니다.

## Mixed Reset

브랜치 포인터를 이동하고 변경 사항의 스테이징을 해제합니다.

```
git reset HEAD~1
# or
git reset --mixed HEAD~1
```

이렇게 하면 마지막 커밋이 취소되고 변경 사항의 스테이징이 해제되지만, 변경 사항은 작업 디렉터리에 그대로 남아 있습니다.

## Hard Reset

커밋과 모든 변경 사항을 완전히 버립니다.

```
git reset --hard HEAD~1
```

**경고**: 이는 변경 사항을 영구적으로 버립니다. 주의해서 사용하세요!

## 특정 커밋으로 Reset하기

어떤 커밋으로도 reset할 수 있습니다.

```
# Using commit hash
git reset --hard a1b2c3d

# Using relative reference
git reset --soft HEAD~3
```

## 파일 스테이징 해제하기

변경 사항을 잃지 않고 파일의 스테이징을 해제하려면 다음을 사용합니다.

```
git reset HEAD file.txt
# or
git restore --staged file.txt
```

## Reset으로부터 복구하기

실수로 reset한 경우, 보통 reflog를 사용해 복구할 수 있습니다.

```
git reflog
git reset --hard HEAD@{2}
```

## Reset과 Revert의 비교

중요한 차이점:

* **reset**: 이력을 다시 씁니다(로컬의, push되지 않은 커밋에 사용)
* **revert**: 변경 사항을 되돌리는 새 커밋을 만듭니다(공유된 이력에 안전)

## 일반적인 사용 사례

### 마지막 커밋 취소하고 변경 사항 유지하기

```
git reset HEAD~1
```

### 마지막 커밋 취소하고 변경 사항 버리기

```
git reset --hard HEAD~1
```

### 하나의 커밋을 여러 개로 나누기

```
git reset HEAD~1
git add file1.txt
git commit -m "First part"
git add file2.txt
git commit -m "Second part"
```

### 최근 몇 개의 커밋 변경하기

```
git reset --soft HEAD~3
# Make changes
git commit -m "Combined commit"
```

## 경고와 모범 사례

1. **공개된 이력은 절대 reset하지 마세요**: 공유 리포지토리에 push된 커밋은 reset하지 마세요
2. **--amend를 신중하게 사용하세요**: push되지 않은 커밋만 amend하세요
3. **대안을 고려하세요**: 공유된 이력에는 대신 `git revert`를 사용하세요
4. **두 번 확인하세요**: 특히 `--hard`를 사용하기 전에
5. **reflog를 알아 두세요**: 실수로부터 여러분을 구해 줄 수 있습니다

## 오늘의 요약

`git commit --amend`와 `git reset`은 로컬 커밋 이력을 수정하는 강력한 도구입니다. `--amend`는 마지막 커밋을 빠르게 수정하는 데 완벽하고, `reset`은 여러 커밋에 대해 더 많은 제어를 제공합니다. 그러나 둘 다 신중하게 사용해야 하며, 특히 다른 사람과 공유된 커밋에 대해서는 더욱 그렇습니다.

오늘 배운 Git 명령어와 매개변수를 다시 정리하겠습니다.

* git commit --amend
* git commit --amend --no-edit
* git reset --soft
* git reset --mixed
* git reset --hard
* git reset HEAD~n
* git reflog
