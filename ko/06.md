# Day 06: Git 데이터 구조 파헤치기 - 개체 구조

Git의 데이터 구조에서 "개체"는 "변경 불가능한(immutable)" 파일 유형입니다. "개체 저장소"에 저장된 모든 파일은 보통 들어가기만 하고 나오지 않으며, 그 내용이 수정되지도 않습니다. 그 이유는 파일 내용을 변조하면 새 내용으로 계산한 SHA1 해시 값이 원래 개체의 파일 이름과 달라져 Git이 계속 실행되지 못하게 되고, 상대적으로 Git 리포지토리에 일정 수준의 보호를 제공하기 때문입니다. 이 글에서는 Git의 개체 구조를 더 자세히 소개하고, 마지막에는 영상을 통해 개체가 생성되는 과정과 논리를 자세히 설명하겠습니다.

## 개체 데이터베이스에 대하여

이전 글에서 언급했듯이, 블롭 개체든 트리 개체든 모두 개체이며, 이 개체들은 이른바 "개체 저장소(object storage)"에 저장됩니다. 이 "개체 저장소"는 기본적으로 "리포지토리"의 objects 디렉터리에 있으며, 다음 그림과 같습니다.

![이미지](figures/06/01.png)

그러나 Git 리포지토리의 각 "개체"는 "파일 내용"에 대해 SHA1 해시 연산을 수행하여 해시 값을 계산하고, 이 해시 값을 개체의 이름(파일 이름)으로 사용합니다. 8a6b275638f3cf164395e65066a1132bb36b7896를 예로 들면, Git은 먼저 처음 두 문자(8a)를 디렉터리로 삼고, 나머지 해시 값을 파일 이름(6b275638f3cf164395e65066a1132bb36b7896)으로 사용합니다. 이 개체들의 실제 디렉터리와 파일도 .git\objects 디렉터리에 배치되며, 다음 그림과 같습니다.

## 개체 유형

이 "개체 데이터베이스"에는 4가지 유형의 개체가 있습니다.

1. **blob 개체**: 이것은 작업 디렉터리에 있는 파일의 "내용"이며, 내용뿐입니다. git add 명령어를 실행하면 이 새 파일들의 내용이 즉시 blob 개체로 기록됩니다. 파일 이름은 개체 내용의 해시 결과이며, 그 밖의 정보는 없습니다. 파일 시간, 원래 파일 이름, 기타 파일 정보와 같은 정보는 다른 유형의 개체(즉, 트리 개체)에 저장됩니다.

2. **tree 개체**: 이 유형의 개체는 특정 디렉터리 아래의 모든 정보를 저장합니다. 여기에는 해당 디렉터리 아래의 파일 이름, 대응하는 blob 개체 이름, 심볼릭 링크, 또는 다른 트리 개체가 포함됩니다. 트리 개체는 다른 트리 개체를 포함할 수 있으므로, 트리 개체를 탐색하는 것은 실제로 파일 시스템의 "폴더"와 같습니다. 간단히 말해, 트리 개체는 특정 버전 아래 폴더의 스냅샷입니다.

3. **commit 개체**: 버전에 어떤 트리 개체가 포함되어 있는지를 기록하는 데 사용됩니다. 커밋 개체는 Git 커밋을 나타내며, 특정 커밋 버전에 어떤 트리 개체가 있는지, 그리고 버전 커밋 시간, 커밋 메시지 등을 기록합니다. 보통 이전 커밋 개체의 이름도 기록합니다(첫 번째 커밋 버전에만 이전 커밋 개체 이름이 없습니다).

4. **tag 개체**: 이것은 컨테이너로, 보통 특정 커밋 개체와 연결하는 데 사용되며(특정 blob 및 트리 개체와 연결할 수도 있습니다), 태그 이름과 같은 추가 참조 정보(메타데이터)를 저장합니다. 태그 개체의 가장 흔한 용도는 커밋 개체의 특정 버전에 이해하기 쉬운 이름을 표시하는 것으로, 특정 릴리스 버전이나 특별한 의미가 있는 버전을 나타낼 수 있습니다.

Git은 각 버전의 각 파일마다 대응하는 blob 개체를 만듭니다. 마찬가지로 blob 개체의 파일 이름도 위와 같은 방식으로 계산됩니다. 이 blob 파일들에서는 버전과의 관계를 전혀 볼 수 없습니다. 트리 개체(폴더의 스냅샷)와 커밋 개체(각 버전의 스냅샷)를 사용해야 이 blob들과 버전 사이의 관계를 연결할 수 있습니다.

모든 개체는 zlib 알고리즘으로 압축되며, 이는 파일 접근 효율을 효과적으로 높일 수 있을 뿐만 아니라, 향후 패킹할 때 델타 압축 알고리즘을 사용하여 공간을 절약할 수도 있습니다. 비슷한 blob을 자동으로 찾아 blob 사이의 차이를 자동으로 계산하고, 이 차이를 *packfile*이라는 파일에 저장하면 디스크 공간을 크게 절약할 수 있습니다. 보통 *packfile*은 .git\objects\pack 디렉터리에 배치되며, 다음 그림과 같습니다.

## 개체 구조의 장점

Git의 "개체" 설계가 얼마나 아름다운지 점차 이해하게 될 것입니다. 첫 번째 글에서 Git의 몇 가지 중요한 설계를 언급했습니다. "개체" 특성과 관련된 몇 가지 설계를 다시 나열하겠습니다.

* 대규모 프로젝트의 효율적인 처리
* 완전한 리포지토리가 로컬 머신에 복제될 뿐만 아니라, 모든 blob 개체가 "내용"을 통해 내용 주소 지정(content addressable)이 가능하므로, 서로 다른 버전 사이에서 같은 내용을 찾는 것이 매우 효율적입니다.
* 이력 기록 보호
* Git 버전 관리 과정에서 각 커밋은 커밋 개체를 생성하고, 이 커밋 개체의 이름은 커밋 개체의 내용을 통해 생성됩니다. 또한 커밋 개체는 트리 개체와 연결되고, 트리 개체의 이름은 트리 개체의 내용을 통해 생성됩니다. 트리 개체는 blob 및 트리 개체와 연결되고, 이 개체들의 이름도 내용을 통해 생성됩니다. 이렇게 층층이 연결되어 있으므로, 오늘 어떤 버전의 이력을 정말로 변조하고 싶다면 그 난이도는 상당히 높습니다!
* Git 리포지토리는 자주 복제되거나 포크되므로, 리포지토리가 복제되기만 하면 원본 리포지토리의 어떤 개체가 수정되더라도 이 복제된 리포지토리들을 다시 병합하기가 어려워지므로, 버전 기록을 임의로 변조하기가 거의 불가능합니다.
* 개체의 정기적인 패킹
* Git에서 말하는 "개체"는 실제로 리포지토리의 파일을 나타냅니다. 버전 변경 과정에서 프로젝트의 코드나 기타 파일이 업데이트됩니다. 업데이트될 때마다 파일 내용이 다르기만 하면 새로운 "개체"가 생성되고, 내용이 다른 이 모든 파일이 보존됩니다.
* 프로젝트가 커지고 버전이 많아질수록 개체도 점점 많아질 것이라고 상상할 수 있습니다. 각 파일을 개별적으로 압축하여 파일을 더 작게 만들 수는 있지만, 파일이 너무 많으면 파일 접근 효율은 여전히 점점 떨어집니다. 따라서 Git의 설계에는 오래된 "개체" 그룹을 packfile로 자동 패킹하여 파일 접근 효율을 높이는 메커니즘이 있습니다.
* 새로 추가된 파일은 여전히 단일 파일로 존재하는데, 이는 Git 리포지토리의 "파일"이 Git "개체"이지만, 가끔씩 다시 패킹해야 한다는 것을 의미합니다.
* 아마도 Git은 다시 패킹과 같은 작업을 자동으로 수행하겠지만, 직접 명령어를 내려 실행할 수도 있습니다. 예: git gc
* Git이 유지 관리하는 파일 시스템이 완전한지 확인하려면 다음 명령어를 실행할 수 있습니다: git fsck

## 오늘의 요약

Git에서 "개체"는 매우 중요하며, 그 특성 또한 매우 중요합니다. Git 명령어를 사용하는 과정에서는 보통 이 파일들을 직접 다룰 필요가 없지만, 이 개체들의 존재를 이해하면 Git의 작동 방식과 Git 특유의 설계 개념을 더 잘 이해하는 데 확실히 도움이 됩니다.
